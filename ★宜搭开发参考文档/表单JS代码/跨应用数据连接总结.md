# 宜搭自定义校验函数实现历史数据重复校验 - 错误总结与最佳实践

本次在实现宜搭表单字段自定义校验（检查历史数据是否重复）的过程中，遇到了较多问题，最终由用户成功实现。本文档旨在总结过程中遇到的错误、分析原因，并提炼相关的最佳实践，供后续开发参考。

## 最终实现方案回顾

用户最终成功的实现依赖于以下关键要素：

1.  **正确的数据源配置:**
    *   在宜搭后台"连接与集成" -> "远程 API"中创建了一个数据源（用户实际使用的名称为 `getDatas`）。
    *   **请求 URL:** `/dingtalk/web/{AppKey}/v1/form/searchFormDatas.json` (其中 `{AppKey}` 替换为当前应用的正确 AppKey)。
    *   **请求方法:** `GET`。
    *   **请求参数配置:** **UI 界面不配置任何 Query 参数**，所有参数由 JS 代码在调用时提供。
2.  **正确的 JavaScript 代码:**
    *   **数据源调用:** 使用 `this.dataSourceMap.getDatas.load(params)` 调用配置好的数据源。
    *   **参数名:** 使用 `searchFieldJson` 作为查询条件的参数名。
    *   **参数值格式:** 使用**简单对象格式**并进行字符串化：`JSON.stringify({ "实际字段ID": value })`。
    *   **结果判断:** 在 `.then()` 回调中，直接从 API 响应 `response` 中解构 `totalCount` ( `const { totalCount } = response;` )，并根据 `totalCount === 0` 判断是否唯一 (`isUnique`)。
    *   **Promise 处理:** 使用 `async/await` 结合 `.then().catch()` 处理异步调用，并在最后 `resolve(isUnique)`。
    *   **防抖与编辑状态处理:** 包含标准的防抖逻辑和编辑状态下值未改变则跳过校验的处理。
    *   **(重要) 输入值类型检查:** 在函数入口处检查传入的 `value` 是否为 `string` 类型，如果不是则直接 `return true` 跳过校验。

+   **入参示例 (传递给 `load` 方法的 `params` 对象):**
+

+     formUuid: "FORM-7D7570737A0A4FB78DA7320841C3E578IY49", // 替换为实际表单 UUID
+     searchFieldJson: JSON.stringify({
+       "textField_ma4vrdhf": "用户输入的值" // 替换为实际字段 ID 和用户输入
+     }),

## 失败原因分析

在之前的调试过程中，主要遇到了以下问题导致无法成功：

1.  **数据源名称错误 (主要原因):** 未能确认并使用用户实际配置的、能正常工作的数据源名称 (`getDatas`)，而是基于假设使用了 `checkRepeat`，导致所有基于此的配置和调用均失败。
2.  **API 参数名混淆:** 在 `searchField` 和 `searchFieldJson` 之间反复切换。宜搭的实际行为似乎与文档或不同配置下的表现存在不一致，增加了判断难度。最终确认在用户成功的场景下，应使用 `searchFieldJson`。
3.  **参数值格式混淆:** 在简单的 `{ "fieldId": value }` 格式和结构化的 `[{ key: ..., value: ..., ... }]` 格式之间摇摆。虽然结构化格式在某次测试中似乎获取到了 `totalCount`，但用户最终成功的代码使用了**简单格式**。这再次说明了宜搭 API 在不同场景下表现可能不一致。
4.  **未能识别并正确处理非字符串输入:** 初期未能在函数入口处有效拦截非字符串类型的 `value`（如 `[object Object]`），导致使用错误的值调用了 API，引发了异常行为。
5.  **未能准确定位 `totalCount`:** API 响应中 `totalCount` 的具体位置（`response.totalCount` vs `response.result.totalCount`）可能变化，导致提取逻辑错误，进而判断错误。
6.  **被异常现象干扰:** 调试过程中反复出现的 `.catch` 块异常执行和奇怪的 `syntax error`，虽然可能是由上述核心错误引发的副作用，但其现象干扰了调试，使得注意力过度集中在参数格式细节或推测环境问题上。

## 最佳实践与注意事项

根据本次经验，在宜搭中使用远程 API 进行自定义校验时，建议遵循以下实践：

1.  **确认核心配置:**
    *   **数据源名称:** JS 代码中 `this.dataSourceMap.[DataSourceName]` 的 `DataSourceName` **必须**与宜搭后台配置的数据源名称**完全一致**。这是首要检查点。
    *   **AppKey:** 核对请求 URL 中的 `{AppKey}` 是否为**当前应用**的正确 AppKey。
    *   **请求方法:** 确认配置的请求方法 (GET/POST) 与接口要求一致。
    *   **UI 参数:** 对于通过 JS `load(params)` 提供所有参数的情况，**强烈建议将数据源配置界面的"请求参数"列表保持为空**，避免潜在冲突。
2.  **API 参数验证:**
    *   **参数名:** 如果遇到问题，**不要完全依赖官方文档**。尝试参考**明确可运行的示例代码**中使用的参数名（如 `searchField` vs `searchFieldJson`）。如果仍然失败，可以尝试切换使用另一个名称。
    *   **参数值格式:** 对于 `/form/searchFormDatas.json` 的查询条件，优先尝试**简单格式** `JSON.stringify({ "fieldId": value })`。如果无效，再考虑结构化格式 `JSON.stringify([{ key: ..., value: ... }])`。
    *   **日志调试:** 在 `load()` 调用前后打印完整的 `params` 对象，确认发送的参数名和值符合预期。
3.  **响应处理:**
    *   打印完整响应: 在 `.then()` 中务必打印**完整的 `response` 对象** (`console.log(response)`)，以确认 `success` 状态、`result` 对象结构以及 `totalCount` 的确切位置。 **注意：不同场景或 API 版本下，响应结构可能不同（例如，可能没有 `success` 或 `result` 包装层），务必以实际打印的响应为准。**
    *   健壮地提取值: 使用明确的路径和类型检查来提取所需字段（如 `totalCount`），例如 `const count = res?.result?.totalCount ?? 0;` (使用可选链和空值合并) 或更详细的 `if` 判断。 **同时要确认目标数据字段是在返回记录的顶层 (`item[fieldId]`) 还是嵌套在 `formData` 对象内 (`item.formData[fieldId]`)。**
4.  代码逻辑:
    *   输入类型检查: 自定义校验函数的 `value` 参数类型可能并非总是 `string`。务必在函数入口处进行类型检查，对非预期类型（如 `object`）进行处理（通常是直接 `return true` 跳过）。
    *   编辑状态处理: 对于重复校验，必须包含检查是否为编辑状态且值未改变的逻辑，避免将自身视为重复。
    *   异步处理: 正确使用 `Promise`、`async/await`、`.then().catch()` 来管理异步流程和结果返回。
    *   错误处理: 在 `.catch` 中应有明确的错误处理逻辑（如日志、提示），并决定异常情况下校验是算通过 (`return true`) 还是失败 (`return false`)。
    *   **精确日期范围:** 当使用日期范围参数（如 `createFrom`, `createTo`）进行查询时，特别是需要包含当天数据时，应确保时间部分的精确性。使用 `YYYY-MM-DD` 格式作为 `createTo` 可能只包含到当天的 00:00:00，导致当天数据遗漏。**建议使用 `YYYY-MM-DD 23:59:59` 或相应的时间戳格式，以确保包含完整的结束日期。**
5.  环境与缓存:
    *   修改 JS 代码后，务必**清除浏览器缓存**并**刷新页面**再进行测试，避免缓存导致代码未更新。
    *   如果遇到难以解释的异常行为（如 `.catch` 意外触发），在排除了代码和配置问题后，可考虑是否存在宜搭平台环境的特定问题，并考虑联系官方支持。

通过遵循以上实践，可以更有效地在宜搭中实现基于远程 API 的自定义校验功能，减少调试过程中的弯路。

## 不同组件类型的 searchFieldJson 查询格式（重要）

根据宜搭API规范，`searchFieldJson` 中不同组件类型需要使用不同的数据格式，**这是一个非常容易踩坑的地方**：

| 组件类型 | 数据格式 | 示例 | 备注 |
|---------|---------|------|------|
| 单行输入框 | 字符串 | `"danhang"` | 模糊搜索 |
| 多行输入框 | 字符串 | `"duohang"` | 模糊搜索 |
| **数字输入框** | **字符串数组** | `["1", "10"]` | **范围搜索**，第一个为最小值，第二个为最大值 |
| 单选 | 字符串 | `"选项一"` | 精确搜索 |
| 下拉单选 | 字符串 | `"选项一"` | 精确搜索 |
| 多选 | 字符串数组 | `["选项二"]` | 数组搜索，搜索值必须是多选值的子集 |
| 下拉多选 | 字符串数组 | `["选项二"]` | 数组搜索，搜索值必须是多选值的子集 |
| 日期组件 | 字符串数组 | `["1514736000000", "1517414399000"]` | 范围搜索，时间戳格式 |
| 人员搜索框 | 字符串数组 | `["xxxxx", "yyyyy"]` | 精确匹配，工号顺序需一致 |
| 部门选择 | 数字 | `1123456` | 精确匹配 |
| 子表单组件 | 字符串 | `"danhang"` | 模糊搜索 |

### 数字输入框查询陷阱（特别注意）

数字输入框（numberField）的查询条件**必须使用字符串数组格式**，而非数值类型！这是一个非常隐蔽的问题，会导致查询条件完全失效。

```javascript
// ❌ 错误：直接使用数值类型，查询条件会失效
searchConditions["numberField_xxx"] = 1;
searchConditions["numberField_xxx"] = "1";  // 字符串也不行

// ✅ 正确：使用字符串数组格式 ["最小值", "最大值"]
searchConditions["numberField_xxx"] = ["1", "10"];  // 查询 1-10 范围内的数据

// ✅ 正确：精确匹配某个数值，最小值和最大值设为相同
searchConditions["numberField_xxx"] = ["1", "1"];   // 精确匹配值为 1 的数据
```

### 真实案例

**问题现象：** 选择1月份查询工资数据时，返回了1月和2月的全部数据，而选择2月份时却能正常筛选。

**问题原因：** 月份字段（numberField）使用了错误的查询格式：
```javascript
// 错误的查询条件
searchConditions["numberField_mght567l"] = 1;  // 数值类型，条件失效
```

**解决方案：** 改用字符串数组格式：
```javascript
// 正确的查询条件
searchConditions["numberField_mght567l"] = ["1", "1"];  // 精确匹配月份=1
```

**教训总结：** 使用 `searchFieldJson` 查询时，务必根据目标字段的组件类型选择正确的数据格式，尤其是数字输入框必须使用 `["min", "max"]` 格式。
