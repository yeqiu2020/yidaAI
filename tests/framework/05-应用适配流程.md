# 应用适配流程（宜搭版）

**版本：** 1.0
**定位：** **核心文档** — AI 拿到宜搭应用后，如何分析应用特性并构建等效测试框架的流程
**目标读者：** AI（执行适配的智能体）

---

## 总览

```
Step 1: 应用分析      → 输出应用架构摘要（表单/流程/报表/页面清单）
Step 2: 能力域识别    → 输出能力域清单（宜搭版）
Step 3: 范式定义      → 输出应用范式定义 + 能力分层清单
Step 4: 测试边界划定  → 输出测试边界决策树 + 伪问题判定依据
Step 5: 用例库生成    → 输出分文件的测试用例库
Step 6: Smoke集选取   → 输出 Smoke 回归集（含工具链Smoke + 应用Smoke）
Step 7: 能力覆盖矩阵  → 输出能力-用例映射矩阵
Step 8: 提示词适配    → 输出 7 个可直接使用的提示词
Step 9: 文档初始化    → 输出完整测试框架目录
```

---

## Step 1：应用分析

### 1.1 分析目标

理解待测宜搭应用的表单结构、流程设计、报表配置、自定义页面和业务规则。

### 1.2 分析方法

1. **读取应用项目目录**：用 `LS` 查看应用目录结构（如 `进销存/`）
2. **读取应用配置文件**：
   - `系统配置清单.md`：应用ID（appId）、表单UUID、组件ID
   - `组织及应用信息.md`：应用列表、原型页面访问地址
   - `表单清单.md`：表单名称、类型（普通表单/流程表单）、分组
3. **读取字段结构**：
   - `01需求梳理/字段清单.md`：每个表单的字段定义、类型、校验、默认值
4. **读取业务规则**：
   - `01需求梳理/规则清单.md`：公式、业务关联规则、字段联动、条件显示
5. **读取 Schema（如有）**：
   - 通过 get-schema skill 同步表单 Schema JSON
6. **识别应用类型**：
   - 普通表单 vs 流程表单
   - 是否含子表单、关联表单
   - 是否含报表、自定义页面
   - 是否含业务规则（跨表INSERT/UPDATE/DELETE/UPSERT）

### 1.3 输出格式

```markdown
## 应用架构摘要

- **应用名称：** {名称}（如"进销存"）
- **应用ID：** {appId}（从系统配置清单读取）
- **应用类型：** {纯表单应用 / 表单+流程 / 表单+流程+报表 / 全功能}
- **表单清单：**
  - 普通表单：{N}个（列表）
  - 流程表单：{N}个（列表）
- **子表单：** {有/无}，共 {N} 个表单含子表
- **关联关系：** {N} 个关联字段，依赖关系图
- **业务规则：** {N} 条公式，{N} 条业务关联规则，{N} 条字段联动
- **报表：** {有/无}，共 {N} 个报表
- **自定义页面：** {有/无}，共 {N} 个
- **测试目标URL：** {原型页面访问地址}（从组织及应用信息.md读取）
- **工具链健康检查命令：** `npm test`（项目根目录）
```

## Step 2：能力域识别（宜搭版）

### 2.1 识别目标

根据宜搭应用的表单结构、流程设计、规则配置，识别应用的核心能力域，作为测试用例库的分文件依据。

### 2.2 宜搭版通用能力域清单

| 能力域 | 典型模块 | 适用场景 | 执行工具 |
|--------|---------|---------|---------|
| 表单与字段 | 字段类型、校验、默认值、数据标题、必填 | 所有有表单的应用 | data-tester |
| 公式与计算 | 字段公式、报表公式、计算逻辑 | 有公式的应用 | data-tester (API) |
| 业务规则 | 跨表INSERT/UPDATE/DELETE/UPSERT、字段联动 | 有业务规则的应用 | data-tester + 验证 |
| 流程审批 | 流程设计、节点、审批人、自动审批 | 有流程表单的应用 | playwright-cli / data-tester |
| 关联数据 | 关联表单、数据联动、被填充字段 | 有关联字段的应用 | data-tester (6步闭环) |
| 权限控制 | 权限组、字段可见性、操作权限 | 大多数应用 | playwright-cli |
| 子表单 | 子表数据、子表公式、子表关联 | 有子表单的应用 | data-tester |
| 数据展示 | 列表、筛选、报表、自定义页面 | 有报表/页面的应用 | playwright-cli |
| JS动作代码 | 表单动作、字段联动、条件显示 | 有JS代码的应用 | js-action-tester |
| 集成自动化 | 连接器、逻辑流、外部API | 有集成的应用 | data-tester / playwright-cli |

### 2.3 输出格式

```markdown
## 能力域清单

| 序号 | 能力域 | 对应表单/模块 | 用例文件名 | 执行工具 | 预估用例数 |
|------|--------|-------------|-----------|---------|-----------|
| 01 | 表单与字段 | 所有表单 | 02-表单与字段测试.md | data-tester | 15-30 |
| 02 | 公式与计算 | 含公式的表单 | 03-公式与计算测试.md | data-tester (API) | 10-20 |
| 03 | 业务规则 | 含规则的表单 | 04-业务规则测试.md | data-tester | 10-20 |
| 04 | 流程审批 | 流程表单 | 05-流程审批测试.md | playwright-cli | 8-15 |
| 05 | 关联数据 | 含关联字段的表单 | 06-关联数据测试.md | data-tester (6步闭环) | 8-15 |
| 06 | 权限控制 | 所有表单 | 07-权限控制测试.md | playwright-cli | 8-15 |
| 07 | 子表单 | 含子表的表单 | 08-子表单测试.md | data-tester | 8-15 |
| 08 | 数据展示 | 报表/自定义页面 | 09-数据展示测试.md | playwright-cli | 5-10 |
| 09 | JS动作代码 | 含JS代码的表单 | 10-JS动作测试.md | js-action-tester | 5-10 |
```

## Step 3：范式定义（宜搭版）

### 3.1 定义目标

分析宜搭应用的设计范式，确定"哪些能力应有手动入口、哪些应自动化、哪些有意不做"。这决定了测试边界和伪-6~伪-9 伪问题的判定依据。

### 3.2 宜搭应用范式类型

| 范式类型 | 特征 | 测试边界影响 |
|---------|------|-------------|
| **纯表单应用** | 只有普通表单，无流程/报表 | 测试表单CRUD、字段、校验、公式 |
| **表单+流程应用** | 含流程表单 | 增加流程审批、节点、自动审批测试 |
| **全功能应用** | 表单+流程+报表+自定义页面+集成 | 全面测试所有能力域 |
| **AI生成应用** | 由 form_creator 等skill自动构建 | 必须区分"应有手动入口"和"应由AI生成" |

### 3.3 能力分层清单构建

对每个能力域，AI 需判断其属于以下哪类：

| 类别 | 含义 | 宜搭示例 | 测试策略 |
|------|------|---------|---------|
| **应有手动入口** | 宜搭平台设计器手动配置更高效的能力 | 表单设计器、流程设计器、报表设计器 | ✅ 缺失可报 ISS（但通常是用户未配置，非bug） |
| **应自动化（AI工具链）** | 由 AI 工具链生成更高效的能力 | 字段生成、表单创建、公式生成、代码生成、配置同步 | ✅ 测试生成结果是否正确，❌ 不测试"是否有手动编辑器" |
| **协同** | 同时提供手动和自动入口 | 字段既可AI生成也可设计器手动配置 | ✅ 分别测试两条路径 |
| **有意不做** | 与项目范式冲突，有意不实现 | 通过API改已有表单字段（规则25）；宜搭平台自身bug；要求AI工具有手动编辑器 | ❌ 不得报 ISS |
| **暂未实现** | 与范式不冲突，未来可能实现 | 高级BI分析、复杂权限矩阵引擎 | 仅当用户要求时记录为需求 |

### 3.4 判断依据

> **核心判断框架：** 不用"简单 vs 复杂"作为分界，而用**"描述成本 vs 操作成本"**：
> - 描述成本高、操作成本低 → 应有手动入口（宜搭设计器配置更高效）
> - 描述成本低、操作成本高 → 应自动化（AI生成更高效）

### 3.5 输出格式

```markdown
## 应用范式定义

- **范式类型：** {纯表单 / 表单+流程 / 全功能 / AI生成}
- **范式核心判断原则：** 宜搭平台提供设计器手动配置，AI工具链负责自动生成。测试以"生成结果是否正确"为主，不测试"是否有手动编辑器"。

## 能力分层清单

### 应有手动入口的能力（宜搭设计器配置）
| 能力 | 应有入口位置 | 说明 |
|------|------------|------|
| 表单字段结构 | 宜搭表单设计器 | 用户在设计器中拖拽配置 |
| 流程节点设计 | 宜搭流程设计器 | 用户在流程设计器中配置 |
| 报表布局 | 宜搭报表设计器 | 用户在报表设计器中配置 |

### 应自动化的能力（AI工具链生成）
| 能力 | 自动化路径 | 测试边界 |
|------|-----------|---------|
| 表单批量创建 | form_creator | 测试创建结果是否正确，不测试"是否有手动创建按钮" |
| 公式生成 | formula-generator | 测试公式计算结果，不测试"是否有公式编辑器" |
| 代码生成 | code-expert | 测试代码执行效果，不测试"是否有代码编辑器" |
| 配置同步 | config-sync / get-schema | 测试同步结果是否正确 |

### 有意不做的能力（不得报 ISS）
| 不做的能力 | 不做的原因 | 误报示例 |
|-----------|----------|---------|
| 通过API修改已有表单字段 | 规则25禁止 | "测试发现公式错误，要求API自动修复" → 伪-6 |
| 宜搭平台自身bug | 归宜搭平台，非应用问题 | "宜搭设计器卡顿" → 伪-6 |
| AI工具的手动编辑器 | AI工具是生成器，不是编辑器 | "formula-generator没有公式编辑器" → 伪-7 |
| 复杂权限矩阵引擎 | 简单表单不需要 | "普通表单没有RBAC引擎" → 伪-8 |

### 暂未实现的能力
| 能力 | 当前状态 |
|------|---------|
| {如有} | {说明} |
```

## Step 4：测试边界划定

### 4.1 该测什么

| 测试对象 | 范围 |
|---------|------|
| 表单运行时能力 | 数据提交、字段校验、公式计算、关联数据、子表操作 |
| 业务规则执行 | 跨表INSERT/UPDATE/DELETE/UPSERT、字段联动、条件显示 |
| 流程运行时 | 流程启动、节点审批、自动审批、撤回、状态流转 |
| 权限运行时 | 权限组可见性、字段可见性、操作权限 |
| JS动作执行 | 表单动作代码、字段联动、条件显示 |
| 数据展示 | 列表筛选、报表渲染、自定义页面交互 |
| 工具链生成结果 | AI生成的字段/公式/代码/规则是否正确 |
| 负面与边界 | 异常输入、校验边界、并发提交、关联异常 |

### 4.2 不该测什么

| 禁止测试的内容 | 原因 |
|-------------|------|
| 通过API修改已有表单字段 | 规则25禁止 |
| 宜搭平台自身bug | 归宜搭平台，非应用问题 |
| 未配置的功能（非"有意不做"） | 应记录为需求，不是 bug |
| AI工具的手动编辑器 | AI工具是生成器，不是编辑器（伪-7） |
| 第三方库的内部行为 | 不属于应用测试范围 |
| 宜搭设计器内未实现的占位符 | 已明确为占位符 |

### 4.3 "功能缺失"判断决策树

```
遇到"功能缺失"现象
    ↓
查询《能力分层清单》
    ↓
属于哪一类？
    ├─ 应有手动入口（宜搭设计器） → 用户未配置？→ 提示用户配置，不报 ISS
    │                              → 设计器不支持？→ 记录为需求
    ├─ 应自动化（AI工具链） → AI未生成？→ ✅ 可报 ISS（工具链问题，分配FW编号）
    │                       → 已生成但不正确？→ ✅ 可报 ISS
    ├─ 协同 → 缺失AI生成？→ ✅ 可报 ISS
    ├─ 有意不做 → ❌ 不得报 ISS（伪-6 范式越界）
    ├─ 暂未实现 → 仅当用户要求时记录为需求
    └─ 都不属于 → ❌ 不得报 ISS（伪-8 重量级预期）
```

## Step 5：用例库生成

### 5.1 生成目标

根据能力域清单，为每个能力域生成测试用例文件。

> **⚠️ 每个应用单独生成用例，但使用共享模式库加速：**
> - 从 `11-共享用例模式库/`（35个模式）选取适用模式
> - 替换占位符为该应用的实际值（字段清单、规则清单、系统配置清单）
> - 输出到 `{应用目录}/测试文档/测试用例库/`
> - 模式库不生成用例本身，只提供场景模板和断言逻辑

### 5.2 用例编号规范（宜搭版）

```
{能力域前缀}-{序号}
```

示例：`YD-FORM-01`（表单与字段）、`YD-FORMULA-03`（公式）、`YD-RULE-02`（业务规则）、`YD-FLOW-01`（流程）、`YD-REL-01`（关联）、`YD-PERM-01`（权限）、`YD-SUB-01`（子表）、`YD-VIEW-01`（数据展示）、`YD-JS-01`（JS动作）

### 5.3 用例生成要求

**生成流程（使用共享模式库）：**

1. **读取模式库索引**：`11-共享用例模式库/README.md`，获取 35 个模式的概览
2. **根据应用能力域选取模式**：按 Step 2 的能力域清单，选取对应的模式 ID
   - 数据提交能力域 → P01~P03
   - 公式与联动能力域 → P04~P10
   - 流程审批能力域 → P11~P12
   - 业务规则能力域 → P13~P14
   - 校验与规则能力域 → P15
   - 关联与填充能力域 → P16~P17
   - 子表单能力域 → P18~P19
   - 多表单依赖 → P20
   - UI交互能力域 → P21~P23
   - 负面用例 → P24-N~P30-N
   - 工具链健康 → P31~P35
3. **实例化每个模式**：替换占位符为该应用的实际值
   - `{表单名称}` → 从字段清单读取
   - `{应用ID}` → 从系统配置清单读取
   - `{表单UUID}` → 从系统配置清单读取
   - `{公式表达式}` → 从规则清单读取
   - `{预期值}` → AI 根据公式/规则推导
   - 其他占位符同理
4. **生成应用专属用例文件**：输出到 `{应用目录}/测试文档/测试用例库/`

**质量要求：**

1. **每个能力域 8-35 个用例**，根据能力复杂度决定
2. **负面用例占比 ≥ 15%**（每个文件至少 2 个负面用例）
3. **每个用例必须包含**：
   - 编号和场景描述
   - 优先级（P0/P1/P2）
   - 测试层级（UI E2E / 宜搭 API / 工具链单元）
   - **执行工具**（data-tester / js-action-tester / playwright-cli）
   - 前置条件
   - 操作步骤（精确到每一步）
   - 预期结果（附产品依据：字段清单路径/规则清单路径/Schema）
   - 可验证断言（量化，非"显示正确"）
4. **负面用例必须带可量化断言**
5. **预期结果必须附产品依据**（字段清单/规则清单/Schema），无依据的标注"待确认"

### 5.4 用例详情格式

```markdown
### YD-FORMULA-01：{场景描述}

- **编号：** YD-FORMULA-01
- **优先级：** P0
- **测试层级：** 宜搭 API
- **执行工具：** data-tester (API)
- **前置条件：**
  - 表单"{表单名}"已创建（UUID: {从系统配置清单读取}）
  - 公式"{公式描述}"已配置（依据：规则清单.md 第X行）
  - 关联表单"{目标表单}"已有数据（至少1条）
- **操作步骤：**
  1. 调用 data-tester 的 submitAIGeneratedData 提交数据
  2. 数据中包含触发公式的输入值
  3. 提交后等待 2 秒
  4. 调用 searchFormDatas.json 回查该记录
- **预期结果：**
  - 公式字段值 = {预期计算结果}
  - 依据：规则清单.md 第X行 / 字段清单.md 第Y行
- **可验证断言：**
  - API 返回的 formData 中，公式字段 `{fieldId}` 的值 = `{预期值}`
  - 非 null / 非 NaN / 非 Infinity
```

### 5.5 最小回归集

除了分能力域的用例文件，还需生成一个 `01-最小回归集.md`：
- 规模：30-45 项
- 从每个能力域选取最高价值的 P0 用例
- 每次**工具链 skill 变更后优先执行**
- 包含：表单提交/公式计算/关联数据/业务规则/流程启动/权限可见性/子表操作/JS动作 各 3-5 项
- **包含工具链 Smoke**：运行 `npm test` 作为第1项

## Step 6：Smoke 集选取

### 6.1 Smoke 集构成（宜搭版）

| Smoke 类型 | 内容 | 执行方式 | 数量 |
|-----------|------|---------|------|
| 工具链 Smoke | `npm test`（Jest 单元测试） | 命令行 | 1项 |
| 应用核心 Smoke | 应用核心 P0 场景 | data-tester / js-action-tester / playwright-cli | 25-35项 |
| 负面 Smoke | 核心负面场景 | 同上 | 4-6项 |

### 6.2 选取原则

- P0 优先
- 用户路径优先
- 核心能力优先（表单提交、公式计算、关联数据、流程启动）
- 回归价值高（历史上出过问题的场景优先）
- 可稳定执行（前置条件清晰）
- **负面 Smoke 占比 ≥ 15%**
- 规模 30-40 项

### 6.3 Smoke 门禁规则

- 工具链 Smoke（npm test）必须 100% PASS
- 应用核心 Smoke 必须 100% PASS
- 负面 Smoke 必须 100% PASS
- 任何 FAIL 不得归档
- SKIP 率 ≤ 20%

## Step 7：能力覆盖矩阵

### 7.1 矩阵结构（宜搭版）
