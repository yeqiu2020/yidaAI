# 测试场景设计原则（宜搭版）

**版本：** 1.0
**定位：** 宜搭应用测试用例设计的核心指导思想

---

## 一、核心原则：问题本身必须合理

测试的目的是发现问题，但**问题本身必须是"真问题"**——即在逻辑上是成立的、可复现的、有修复价值的。

### 宜搭版关键区分

| 情况 | 是否合理 | 说明 |
|------|---------|------|
| 字段清单中已配置校验规则，测试该规则是否生效 | ✅ 合理 | 前置条件已满足，测试有针对性 |
| 字段清单中未配置校验规则，却测试该功能为何不工作 | ❌ 不合理 | 前置条件未满足，测试无意义 |
| 规则清单中已配置业务规则，测试跨表联动是否生效 | ✅ 合理 | 规则已配置，测试验证其正确性 |
| 规则清单中未配置业务规则，却测试跨表联动为何不工作 | ❌ 不合理 | 应先配置规则再测试 |
| 公式已配置，测试公式计算结果是否正确 | ✅ 合理 | 公式已存在，测试验证其正确性 |
| 公式未配置，却测试字段为何不自动计算 | ❌ 不合理 | 应先配置公式再测试 |
| 关联表单已有数据，测试关联字段是否能正确关联 | ✅ 合理 | 前置数据已准备 |
| 关联表单无数据，却测试关联字段为何为空 | ❌ 不合理 | 应先生成关联数据（data-tester 依赖顺序）|

## 二、五项设计原则

| 原则 | 说明 | 宜搭示例 |
|------|------|---------|
| **前置条件满足** | 测试某功能前，必须确保该功能已配置/已实现 | 测试校验规则前，先确认字段清单中已配置该规则 |
| **问题可复现** | 发现的问题必须能通过明确步骤复现 | "提交表单后公式字段为空"而非"有时候公式不计算" |
| **逻辑贯通** | 问题描述的前因后果必须逻辑成立 | 不能说"未配置公式却测试不计算" |
| **有修复价值** | 问题必须值得修复 | 公式计算错误值得修复，字段顺序微差不值得 |
| **场景可独立** | 每个测试场景应能独立执行 | 每个场景自带数据准备步骤（data-tester 生成数据）|

## 三、测试场景 vs 问题的关系

> **测试场景是"通过场景来排查问题"的手段，不是问题本身。**

```
测试场景（Test Scenario）
    ↓ 通过执行场景（data-tester 提交数据 / js-action-tester 执行动作）
发现现象（Phenomenon）
    ↓ 分析判断（读字段清单/规则清单对比）
形成问题（Issue）
    ↓ 修复（工具链层改脚本 / 应用层生成产物）
验证修复（Verification）
    ↓ data-tester 回查 / js-action-tester 回归
```

- **测试场景**：排查问题的载体，如"新增采购订单并提交审批"
- **现象**：执行场景后观察到的异常，如"提交后关联产品字段为空"
- **问题**：经过分析确认的真问题，如"关联字段instanceId与title错配（FW-XX）"
- 测试场景可以反复取用：同一场景在不同轮次可能发现不同问题

## 四、用例取用机制

### 4.1 取用标记

| 标记 | 含义 | 说明 |
|------|------|------|
| `未取用` | 从未被提取执行 | 常规新一轮探索测试只能从此类提取 |
| `已取用` | 已被提取执行过 | 仅用于回归/补测/Smoke/修复验证 |

### 4.2 取用规则

1. 常规新一轮探索测试每次提取约 **10 个** `未取用` 且前置条件满足的 P0 用例
2. 提取前必须检查每个场景的前置条件是否满足（字段已创建、公式已配置、规则已启用、关联数据已生成）
3. 被提取的用例标记为 `已取用`，但不删除、不移动
4. `已取用` 场景只可用于回归、补测、Smoke、修复验证、用户明确要求复测
5. 如 P0 的 `未取用` 不足，可提取 P1 的 `未取用`；不要重复提取 `已取用`
6. **每批次必须包含至少 2 个负面用例**
7. **负面用例占比建议 ≥ 20%**

### 4.3 执行工具标注

每个用例必须标注执行工具：

| 执行工具 | 适用场景 | 标注格式 |
|---------|---------|---------|
| data-tester (API) | 表单数据提交、公式计算、校验规则、关联数据回查 | `执行工具: data-tester (API)` |
| data-tester (浏览器) | 复杂数据提交场景、需模拟用户操作的数据提交 | `执行工具: data-tester (浏览器)` |
| js-action-tester | 表单JS动作、字段联动、条件显示、事件绑定 | `执行工具: js-action-tester` |
| playwright-cli | 完整用户路径、流程审批、权限可见性、页面交互 | `执行工具: playwright-cli` |

## 五、前置条件检查机制

每次提取用例时，出题方必须先检查该场景是否具备可测试前置条件：

| 检查项 | 宜搭版处理方式 |
|--------|--------------|
| 字段未创建 | 不交给测试方测试，标记 `前置条件待准备`；需 form_creator/form_designer 补充 |
| 公式未配置 | 先配置公式（formula-generator），不能把"不计算"当 bug |
| 业务规则未启用 | 先配置规则（business-rule），不能把"不联动"当 bug |
| 关联表单无数据 | 先用 data-tester 生成关联表单数据（按依赖顺序）|
| 测试数据缺失 | 先用 data-tester 准备测试数据 |
| 流程未配置 | 先配置流程（flow-settings），不能把"无法审批"当 bug |
| 会污染真实业务数据 | 必须使用独立测试应用或 E2E_ 前缀数据 |

## 六、负面用例要求

### 6.1 什么是负面用例

负面用例是测试宜搭应用在异常、边界、安全、并发等场景下的行为，验证应用能正确处理非正常输入和异常状态。

### 6.2 宜搭版负面用例类型

| 类型 | 示例 |
|------|------|
| 输入校验边界 | 输入超长文本、特殊字符、负数、非数字、空格 |
| 校验规则触发 | 输入不符合校验规则的值，验证是否被拦截 |
| 必填校验 | 留空必填字段提交，验证是否提示错误 |
| 关联数据异常 | 关联不存在的记录、关联已删除的记录 |
| 公式边界 | 除零、空值参与计算、日期越界 |
| 权限越界 | 普通成员尝试访问无权限的数据 |
| 流程异常 | 撤回已审批的流程、重复提交 |
| 并发提交 | 同一记录并发修改 |

### 6.3 硬性要求

- 每批次至少 **2 个**负面用例
- 每个负面用例必须带**可量化断言**（DOM 属性/API 字段/具体数值/控制台日志关键字）
- **禁止**"显示正确/工作正常"等不可证伪表述

### 6.4 量化断言示例（宜搭版）

| ✅ 可量化 | ❌ 不可量化 |
|----------|-----------|
| `API 返回 400，响应体包含 "校验失败"` | `校验被正确触发` |
| `公式字段值为 null，非 Infinity/NaN` | `计算结果正确` |
| `关联字段提交后回查为空字符串` | `关联失败` |
| `提交按钮 disabled 属性为 true` | `按钮被禁用` |
| `流程状态字段值为 "DRAFT" 未流转` | `流程未启动` |
| `控制台输出 "form validation error"` | `有错误提示` |

## 七、测试数据规范（宜搭版）

| 规范项 | 要求 |
|--------|------|
| 测试数据命名 | 统一使用 `E2E_YYYYMMDD_NNN_` 前缀（如 `E2E_20260716_001_测试产品`）|
| 数据隔离 | 禁止修改真实业务数据；优先使用独立测试应用 |
| 真实数据原则 | data-tester 生成的数据必须真实可信（真实地名、人名、业务场景），禁止"测试数据/test"等假数据 |
| 关联数据顺序 | 批量提交多表单时按依赖顺序：被关联表单先生成（如 产品信息→仓库信息→库存信息）|
| 失败数据保留 | 失败场景的数据需保留到问题验证完成 |
| 归档前清理 | 测试批次全部通过后用 data-clean 清理测试数据 |
| 子表数据 | 子表至少3行数据，各行有差异 |

## 八、测试层级标注

每个验证项记录结果时，必须标注测试层级：

| 层级 | 使用场景 | 执行工具 |
|------|---------|---------|
| UI E2E | 用户真实业务路径、JS动作、字段联动、条件显示、审批操作、权限可见性 | js-action-tester / playwright-cli |
| 宜搭 API | 表单数据提交、公式计算结果、校验规则触发、关联数据回查、流程状态 | data-tester (API) |
| 工具链单元 | skill 脚本内部函数（字段解析、marks计算、路径校验、HTTP封装） | Jest (tests/core, tests/features) |

**核心边界：** UI 业务路径（JS动作、字段联动、条件显示、流程审批）必须用 UI 操作验证；宜搭 API（数据提交、公式计算、关联回查）本身是测试对象时可用接口证据。

## 九、优先级定义

| 优先级 | 含义 | 宜搭示例 |
|--------|------|---------|
| 🔴 P0 | 阻塞核心流程，无法继续测试 | 表单无法创建、提交报错、公式全部错误、关联全部错配、流程无法启动 |
| 🟡 P1 | 重要功能异常，但有变通方案 | 部分公式错误、个别校验未触发、权限误判、页面加载失败 |
| 🟢 P2 | 非阻塞性问题，不影响主流程 | 字段显示格式、编码问题、排序微差、文案错误 |

### 风险驱动优先级（建议）

`风险分 = 影响面 × 业务阻塞度 × 发生概率 × 可探测难度`

| 优先级 | 标准 |
|--------|------|
| P0 | 阻塞核心链路、数据错乱、关联错配、越权泄露、不可恢复 |
| P1 | 影响重要功能或体验，但有绕行路径，或影响局部用户 |
| P2 | 低频、轻微体验、兼容性边缘问题 |
