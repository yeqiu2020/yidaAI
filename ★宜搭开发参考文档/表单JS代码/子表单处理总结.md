# 宜搭子表单动态校验实现过程问题总结

**目标:** 实现宜搭子表单中，"必填校验"字段根据同一行的"上传是否必填"和"图片上传"字段的值动态更新状态。

**遇到的主要问题及解决方案:**

1.  **问题：事件绑定目标与参数误解**
    *   **描述:** 最初对于将 `onChange` 事件绑定在子表单本身还是绑定在子表单内部组件（如下拉框、图片上传）上，以及对应的回调函数参数（如 `value`, `rowValue`, `rowIndex`, `item`, `extra`）的确切含义和可靠性存在混淆。尝试绑定到内部组件时期望 `item` 参数携带行上下文信息，但实际并未提供；尝试绑定到子表单时期望 `rowValue`/`rowIndex` 可靠，但实践证明并非如此。
    *   **原因:** 宜搭 JS API 的实际行为可能与直觉或部分文档说明存在差异，不同绑定方式、不同触发场景下的参数结构和可靠性需要通过实践和日志来验证。
    *   **最终方案:** 确定将 `onChange` 事件统一绑定到 **子表单本身** (`TableField`)，并主要处理其回调参数 `{ value, extra }`。

2.  **问题：回调参数 `extra` 中缺少可靠的行索引 `rowIndex`**
    *   **描述:** 即使将事件绑定到子表单本身，其 `onChange` 回调的 `extra` 参数在大多数情况下（特别是字段值改变时）并不包含能直接定位到触发变化行的 `rowIndex` 属性。
    *   **原因:** 这可能是宜搭 API 设计层面的限制，或者 `rowIndex` 只在特定类型的变化（如内部 API 调用）时才提供。
    *   **最终方案:** 在 `onTableChange` 函数中，不再强依赖 `extra.rowIndex` 来优化处理。采取了**遍历所有行**的策略：即无论 `extra` 中是否包含 `rowIndex`，都遍历 `value` (子表单完整数据) 中的每一行，执行校验逻辑并更新对应行的"必填校验"字段。
    *   **注意:** 此方案虽然能保证逻辑覆盖所有行和所有触发情况（字段修改、增删行等），但在子表单行数非常多时，性能会低于只处理单行的方式。

3.  **问题：`JSON.stringify` 序列化复杂对象时的循环引用错误**
    *   **描述:** 在尝试使用 `JSON.parse(JSON.stringify(...))` 对宜搭事件回调参数（如 `value`, `extra`）或 `this.$(fieldId).getValue()` 返回的对象进行深拷贝时，频繁遇到 `TypeError: Converting circular structure to JSON` 错误。
    *   **原因:** 宜搭传递的事件参数或 `getValue()` 返回的对象内部可能包含了对组件实例、DOM 节点或其他复杂内部结构的引用，形成了循环引用，标准的 `JSON.stringify` 无法处理。
    *   **最终方案:**
        *   **避免** 对来源不可靠或结构复杂的对象（特别是事件回调的原始参数 `value`, `extra`）直接使用 `JSON.stringify`。
        *   在需要修改数据副本时，优先对 **`this.$(tableFieldId).getValue()` 返回的结果** 进行 `JSON.parse(JSON.stringify(...))` 深拷贝，因为 `getValue()` 通常返回的是相对纯净的数据数组。
        *   将深拷贝操作包裹在 `try...catch` 块中，以便在拷贝失败时能够捕获错误并采取备用措施（例如，记录错误后中止操作，避免程序崩溃）。

4.  **问题：UI 状态更新滞后**
    *   **描述:** 当修改子表单内某个字段的值（如"上传是否必填"）后，依赖该值计算得出的另一字段（"必填校验"）的状态没有立即在界面上更新，需要等待下一次事件触发（如新增行）才刷新，表现出明显的滞后性。
    *   **原因:** `onTableChange` 事件触发后，其回调函数执行时，宜搭内部的状态更新可能尚未完全完成。此时立即调用 `getValue()` 获取数据或直接使用回调参数 `value` 可能得到的是更新前的数据。基于这个数据计算并调用 `setValue()` 更新回去，要么是无效操作，要么其效果被后续宜搭自身的渲染流程覆盖，导致看起来没有立即生效。
    *   **最终方案:** 在 `onTableChange` 函数的核心逻辑外层，使用 `setTimeout(() => { ... }, 0)` 进行包裹。将 **获取最新数据 (`getValue()`)、执行校验逻辑、调用 `setValue()`** 的整个过程都放在 `setTimeout` 的回调函数中执行。这样可以将我们的处理逻辑推迟到当前 JavaScript 同步任务和微任务队列清空之后，确保能获取到宜搭状态更新后的最新数据，从而解决 UI 更新滞后的问题。

**总结与建议:**

*   处理宜搭子表单的动态交互时，事件参数 (`value`, `extra`, `item` 等) 的具体内容和可靠性需要通过 `console.log` 结合实际操作进行仔细验证。
*   在无法精确获取变化行上下文的情况下，遍历所有行进行处理是保证逻辑完整性的可靠方法，但需注意潜在性能影响。
*   对宜搭返回的对象进行深拷贝时要格外小心循环引用问题，优先处理 `getValue()` 的结果并使用 `try...catch`。
*   当遇到 UI 更新不及时或状态滞后问题时，`setTimeout(..., 0)` 结合在回调中重新 `getValue()` 是一个有效的解决方案。
*   在整个调试过程中，添加详细的 `console.log` 输出是定位问题的关键手段。

# 本次 "领用明细物料标号赋值" 功能调试经验总结 (与关联表单数据填充时序相关)

**目标:** 子表单中，当"选择物料"（关联表单）字段变化后，自动将关联数据中的"物料标号（具体物料原值）"填充到子表单当前行的"物料标号（具体物料）"字段。

**遇到的核心问题及解决方案:**

1.  **问题：`onChange` 事件触发时，关联数据尚未回填到当前行**
    *   **描述:** 在"选择物料"字段的 `onChange` 事件回调函数（例如通过 `this.utils.legaoBuiltin.execEventFlow.bind(this, [customFunc])` 绑定）中，无论是直接访问 `this.item`（回调函数上下文 `this` 提供的当前行数据快照），还是立即调用 `this.$(subTableId).getValue().[this.index]`，都无法获取到由关联表单数据填充规则刚刚带过来的最新值（如"物料标号（具体物料原值）"）。这些途径获取到的往往是数据填充发生前的值（通常是空或旧值）。
    *   **原因:** 宜搭平台的关联数据填充机制与组件的 `onChange` 事件触发的JS回调在执行时序上存在异步。JS回调往往先于数据填充完成执行。
    *   **验证:** 通过在 `onChange` 回调中打印 `this.item` 和 `this.$(subTableId).getValue()` 的相关字段，可以清晰地观察到所需字段为空或未更新。

2.  **问题：`this.item` 是事件触发时的快照，不会自动更新**
    *   **描述:** 即便在 `onChange` 回调中使用 `setTimeout` 延迟处理，如果延迟后仍然依赖事件触发时传入的 `this.item` 对象，依然无法获取最新数据。
    *   **原因:** `this.item` 是 `onChange` 事件被触发那一刻的行数据状态的一个副本（或代理），宜搭后续对表单数据的实际回填操作不会直接修改这个已经传递给回调函数的 `this.item` 对象。

3.  **解决方案：`setTimeout` + 在回调中重新 `getValue()` 获取最新行数据**
    *   **步骤1: 保存上下文信息:** 在 `onChange` 回调函数（如 `handleMaterialChange(value, options)`）的顶层，首先保存必要的行上下文信息，最重要的是 `this.index` (当前操作行的索引)。
        ```javascript
        const rowIndex = this.index;
        const subTableComponent = this.$(SUB_TABLE_ID);
        ```
    *   **步骤2: 延迟执行核心逻辑:** 将所有的数据获取和赋值操作都包裹在一个 `setTimeout` 回调中。
        ```javascript
        setTimeout(() => {
          // ... 核心逻辑 ...
        }, 300); // 延迟时间，例如300毫秒，根据实际情况调整
        ```
    *   **步骤3: 在 `setTimeout` 回调中重新获取数据:** 这是最关键的一步。在延迟回调函数内部，必须通过 `subTableComponent.getValue()` 来获取整个子表单所有行的最新数据。
        ```javascript
        const allLatestSubTableData = subTableComponent.getValue();
        if (!Array.isArray(allLatestSubTableData) || !allLatestSubTableData[rowIndex]) {
          // 错误处理或日志记录
          return;
        }
        const latestCurrentRowData = allLatestSubTableData[rowIndex];
        ```
    *   **步骤4: 从最新行数据中提取所需值:** 从 `latestCurrentRowData` 中获取之前未能即时获取到的关联回填字段的值。
        ```javascript
        const originalMaterialCode = latestCurrentRowData[MATERIAL_CODE_ORIGINAL_ID_IN_SUBTABLE];
        ```
    *   **步骤5: 执行赋值并更新子表:** 基于获取到的 `originalMaterialCode`，更新目标字段，并使用 `subTableComponent.setValue()` 将包含已修改行的整个子表数据数组设置回去。
        ```javascript
        // ... 更新 targetRow ...
        // updatedSubTableData[rowIndex] = targetRow;
        // subTableComponent.setValue(updatedSubTableData);
        ```

4.  **关于 `this` 上下文的再确认:**
    *   通过 `this.utils.legaoBuiltin.execEventFlow.bind(this, [customFunc])` 方式配置的事件，`customFunc` 执行时的 `this` 对象确实会包含 `index` (当前行索引) 和 `item` (当前行数据快照)。这为定位操作行提供了便利，但要注意 `item` 的快照特性。

5.  **调试建议:**
    *   在 `onChange` 事件回调的开始、`setTimeout` 回调的开始，以及获取关键数据（如 `originalMaterialCode`）之后，添加详细的 `console.log`，打印 `this.item`、`latestCurrentRowData` 以及目标字段的值，有助于追踪数据在不同阶段的状态，判断数据填充是否按预期完成。
    *   如果延迟后数据仍未填充，可适当增加 `setTimeout` 的延迟时间进行测试。

**此案例说明：** 处理依赖于平台自动数据填充的即时JS交互时，必须考虑到填充操作的异步性，并通过延迟执行并在延迟后重新获取最新数据的方式来确保逻辑的正确性。
