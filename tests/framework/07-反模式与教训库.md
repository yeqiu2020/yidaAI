# 反模式与教训库（宜搭版）

**版本：** 1.0
**定位：** 宜搭应用测试中常见的反模式和 9 类伪问题，作为测试方和修复方的必读警示

---

## 一、宜搭版通用反模式

> **以下反模式从原方法论12条 + 宜搭开发测试特性提炼，适用于所有宜搭应用测试。**

### AP-1：在 loading 态抓取 DOM（宜搭版）

| 项 | 内容 |
|----|------|
| **错误行为** | 在宜搭表单提交、公式计算、流程流转、数据填充未完成时抓取 DOM/API 结果，判定"未计算/未流转/未填充" |
| **错误后果** | 大量伪-4（时序问题）伪问题，浪费修复方资源 |
| **正确做法** | 等待 `networkidle` + 至少 2 秒后再抓取；data-tester 提交后等待 searchFormDatas 返回再回查 |
| **违反自检** | ③ 异步等待、⑤ 现象可复现 |

### AP-2：凭推断报告宜搭 API 错误码

| 项 | 内容 |
|----|------|
| **错误行为** | 未实际调用宜搭 API（data-tester），仅凭推断或文档猜测 API 返回的错误码 |
| **错误后果** | 报告了不存在的错误码，修复方无法复现 |
| **正确做法** | 通过 data-tester 实际调用 API，记录完整的请求和响应（状态码 + 响应体） |
| **违反自检** | ① API 实证 |

### AP-3：凭 UI 表面判定"功能未实现"（宜搭版）

| 项 | 内容 |
|----|------|
| **错误行为** | 看到 UI 上没有某功能入口，或表单上字段为空，就直接判定"字段未创建/公式未配置/功能未实现"，不读字段清单/规则清单 |
| **错误后果** | 大量伪-2（未读源码）伪问题，功能实际已配置只是未触发显示条件 |
| **正确做法** | 读字段清单/规则清单/Schema 确认功能是否已配置；如果已配置，检查触发条件 |
| **违反自检** | ② 源码确认 |

### AP-4：用 API 调用替代 UI 业务路径（宜搭版）

| 项 | 内容 |
|----|------|
| **错误行为** | UI E2E 测试中（如测试JS动作、字段联动、条件显示），用 data-tester API 调用完成业务操作，然后验证 UI 显示 |
| **错误后果** | UI 业务路径中的 bug 被掩盖（JS动作触发、字段联动、条件显示等未被测试到） |
| **正确做法** | UI 业务路径（JS动作/联动/条件显示/流程审批）必须用 js-action-tester 或 playwright-cli 的 UI 操作完成；data-tester API 测试仅在 API 本身是测试对象时使用 |
| **违反自检** | ① API 实证（间接） |

### AP-5：测试应用有意不做的能力（宜搭版）

| 项 | 内容 |
|----|------|
| **错误行为** | 按传统思维测试宜搭应用有意不做的能力（如要求AI工具有手动编辑器、测试宜搭平台自身bug、要求通过API改已有表单字段） |
| **错误后果** | 伪-6（范式越界）伪问题，浪费测试和修复资源 |
| **正确做法** | 测试前查询能力分层清单，确认该能力属于"应有"范围；规则25禁止的不测 |
| **违反自检** | 范式三问①② |

### AP-6：以管理员身份测试非管理员权限（宜搭版）

| 项 | 内容 |
|----|------|
| **错误行为** | 以管理员身份测试普通成员的越权拦截，报告"权限未被拦截"；或不理解宜搭权限组设计 |
| **错误后果** | 伪-3（未理解产品设计）伪问题，管理员本就有全部权限 |
| **正确做法** | 测试权限拦截时，使用对应权限组的账号；读规则清单理解权限组设计 |
| **违反自检** | ④ 产品设计理解 |

### AP-7：测试不可复现的问题

| 项 | 内容 |
|----|------|
| **错误行为** | 报告"有时候公式不计算""偶尔关联失败"等无法稳定复现的问题 |
| **错误后果** | 修复方无法复现，无法修复，浪费时间 |
| **正确做法** | 确保问题可通过明确步骤稳定复现；如不稳定，标注 PENDING 并说明 |
| **违反自检** | ⑤ 现象可复现 |

### AP-8：修改提取用例以"修复"问题

| 项 | 内容 |
|----|------|
| **错误行为** | 核验方或修复方修改提取用例文件，使测试通过 |
| **错误后果** | 掩盖真实问题，测试失去意义 |
| **正确做法** | 核验方禁改用例；用例预期与字段清单/规则清单不符时，反馈出题方修订用例（伪-5） |
| **违反自检** | — |

### AP-9：修复时引入无关变更

| 项 | 内容 |
|----|------|
| **错误行为** | 修复 bug 时顺便重构 skill 代码、重命名变量、调整格式 |
| **错误后果** | 扩大修改范围，增加引入新问题的风险，难以追踪变更 |
| **正确做法** | 只改必要的行，最小改动原则 |
| **违反自检** | — |

### AP-10：未配置就测试不生效（宜搭版）

| 项 | 内容 |
|----|------|
| **错误行为** | 字段清单中未配置校验规则/公式/业务规则/流程，却测试该功能为何不工作 |
| **错误后果** | 前置条件不满足，测试无意义，产生 SKIP 或误判 FAIL |
| **正确做法** | 测试前检查字段清单/规则清单，先配置再测试 |
| **违反自检** | — |

### AP-11：负面用例不带量化断言

| 项 | 内容 |
|----|------|
| **错误行为** | 负面用例的预期写"显示正确/工作正常/被拦截"，无量化标准 |
| **错误后果** | 无法证伪，测试方可能主观判定通过 |
| **正确做法** | 负面用例必须带可量化断言（API 字段值/DOM 属性/具体数值/控制台日志关键字） |
| **违反自检** | — |

### AP-12：AI 自行归档

| 项 | 内容 |
|----|------|
| **错误行为** | AI 在未获得用户明确点头的情况下自行执行归档操作 |
| **错误后果** | 跳过用户门禁，可能遗漏未修复问题 |
| **正确做法** | 归档必须由用户审核 9 项清单后点头，AI 不得代为归档 |
| **违反自检** | — |

### AP-13：通过 API 修改已有表单字段（宜搭特有）

| 项 | 内容 |
|----|------|
| **错误行为** | 修复方通过 saveFormSchema 等 API 直接修改已有应用的表单字段内容（公式/代码/字段增删改） |
| **错误后果** | 可能导致线上应用被误改误删，造成不可逆的业务影响 |
| **正确做法** | 应用层修复只能"本地生成修复产物 → 用户手动粘贴到宜搭"（规则25）；只有新建表单才允许 API 操作 |
| **违反自检** | — |

### AP-14：关联字段未走6步闭环（宜搭特有）

| 项 | 内容 |
|----|------|
| **错误行为** | 测试关联字段时，不查询目标表单真实数据，直接推断 title；或提交后不回查验证 |
| **错误后果** | instanceId 与 title 错配，页面显示与实际跳转记录不一致 |
| **正确做法** | 关联字段必须走6步闭环：识别→查询完整数据→建立映射表→选取对应pair→提交前自查→提交后回查验证 |
| **违反自检** | ① API 实证、⑤ 现象可复现 |

### AP-15：批量提交不按依赖顺序（宜搭特有）

| 项 | 内容 |
|----|------|
| **错误行为** | 批量提交多表单数据时，不分析关联依赖，随意排序（如先提交库存信息再提交仓库信息） |
| **错误后果** | 关联字段无数据可填，提交失败或关联为空 |
| **正确做法** | 按依赖顺序：被关联的表单先生成（如 产品信息→仓库信息→库存信息） |
| **违反自检** | — |

### AP-16：测试数据不真实（宜搭特有）

| 项 | 内容 |
|----|------|
| **错误行为** | 使用"测试数据"、"test"、硬编码人名拼凑公司名等明显假数据 |
| **错误后果** | 数据不符合业务逻辑，公式计算/校验规则无法真实触发 |
| **正确做法** | data-tester 生成的数据必须真实可信（真实地名、人名、业务场景、合理数值） |
| **违反自检** | — |

## 二、9 类伪问题速查（宜搭版）

### 2.1 通用伪问题（伪-1 ~ 伪-5）

| 类别 | 名称 | 宜搭版判定标准 | 典型表现 | 违反自检 |
|------|------|--------------|---------|-----------|
| 伪-1 | 凭空捏造 | 报告了字段清单/规则清单中根本不存在的字段/公式/规则/功能 | "应该有XX字段但没有" → 字段清单中从未定义 | ②⑤ |
| 伪-2 | 未读源码 | 报告"字段未创建/公式未配置/规则未启用"前未读清单，实际已配置 | "公式未配置" → 规则清单中已配置 | ② |
| 伪-3 | 未理解设计 | 以管理员测试普通成员权限；或不理解宜搭权限组/流程节点/数据联动 | "管理员可越权" → 管理员本就有全部权限 | ④ |
| 伪-4 | 时序问题 | 在表单提交/公式计算/流程流转/数据填充未完成时抓取 | "公式未计算" → 实际是异步未完成 | ③⑤ |
| 伪-5 | 用例库问题 | 用例预期与字段清单/规则清单/Schema 不符 | "预期返回A实际返回B" → 用例预期写错 | ① |

### 2.2 范式类伪问题（伪-6 ~ 伪-9）

| 类别 | 名称 | 宜搭版判定标准 | 典型表现 | 违反自检 |
|------|------|--------------|---------|-----------|
| 伪-6 | 范式越界 | 测试宜搭应用有意不做的能力 | 要求API改已有表单；测试宜搭平台bug；要求未配置的功能 | 范式三问①② |
| 伪-7 | 角色错位 | 把应由宜搭平台/用户完成的工作当成AI工具应该做的 | 要求AI工具有手动编辑器；要求data-tester替代用户审批 | 范式三问③ |
| 伪-8 | 重量级预期 | 要求简单宜搭表单提供复杂企业级功能 | 要求简单CRUD表单有RBAC引擎；要求普通表单有BI分析 | 范式三问① |
| 伪-9 | 平衡失调 | 混淆"宜搭设计器手动配置"和"AI自动生成" | 要求AI生成的公式有手动编辑器；要求设计器自动生成代码 | 范式三问①③ |

### 2.3 伪问题判定决策树（宜搭版）

```
收到 ISS
    ↓
是否在能力分层清单的"应有"范围内？
    ├─ 否 → 是否在"有意不做"范围内？
    │       ├─ 是（如规则25禁止的、宜搭平台bug）→ 伪-6 范式越界
    │       └─ 否 → 是否要求简单表单提供复杂功能？
    │               ├─ 是 → 伪-8 重量级预期
    │               └─ 否 → 伪-9 平衡失调（可能）
    │
    └─ 是 → 检查五项自检
            ├─ ① 是否实际调用了宜搭API（data-tester）？
            │   └─ 否 → 伪-1 或退回补证
            ├─ ② 是否读了字段清单/规则清单？
            │   └─ 否 → 伪-2
            ├─ ③ 是否等待了公式计算/流程流转完成？
            │   └─ 否 → 伪-4
            ├─ ④ 是否理解了宜搭权限组/流程设计？
            │   └─ 否 → 伪-3
            └─ ⑤ 是否可稳定复现？
                └─ 否 → 退回，要求复现步骤

    额外检查：
    - 用例预期是否与字段清单/规则清单一致？
        └─ 否 → 伪-5 用例库问题
    - 测试预期是否与宜搭范式一致？
        └─ 否 → 伪-7 角色错位
    - 是否要求通过API改已有表单？
        └─ 是 → 伪-6 范式越界（规则25）
```

## 三、正确做法对照表（宜搭版）

| 场景 | ❌ 错误做法 | ✅ 正确做法 |
|------|-----------|-----------|
| 表单提交后抓取结果 | 立即抓取 DOM/API | 等待 networkidle + 2s，或 searchFormDatas 返回 |
| 验证宜搭 API 错误码 | 凭推断报告错误码 | 通过 data-tester 实际调用，记录完整响应 |
| 判定字段未创建 | 凭 UI 无字段判定"未创建" | 读字段清单/Schema 确认，检查触发条件 |
| 测试 JS 动作路径 | 用 data-tester API 提交后验证显示 | 用 js-action-tester 的 UI 操作完成全路径 |
| 测试权限拦截 | 用管理员账号测试越权拦截 | 用对应权限组账号测试 |
| 发现偶发问题 | 报告"有时候不工作" | 确定复现步骤，或标注 PENDING |
| 核验时发现问题 | 修改用例使测试通过 | 反馈出题方修订用例 |
| 修复工具链 bug | 顺便重构相关代码 | 只改必要的行 |
| 修复应用层公式 | 通过 API 直接改公式 | 生成公式JSON + 粘贴指引（规则25） |
| 测试未配置的功能 | 直接测试"不生效" | 先配置（读清单确认），再测试 |
| 负面用例预期 | "工作正常" | "API 返回 400，响应体包含校验失败" |
| 批次完成 | AI 自行归档 | 用户审核 9 项后点头归档 |
| 测试"有意不做"的能力 | 报告 ISS | 查询能力分层清单，不报 ISS |
| 关联字段测试 | 推断 title | 走6步闭环，查询真实 title |
| 批量提交多表单 | 随意排序 | 按依赖顺序：被关联表单先生成 |

## 四、教训累积机制

### 4.1 累积原则

- 每次出现误判、伪问题、过度修复、资源浪费的情况，必须追加新教训
- **教训不可删除，只能累积**
- 每条教训记录：错误行为、正确做法、违反的自检项

### 4.2 触发条件

| 触发类型 | 条件 | 动作 |
|---------|------|------|
| 强制触发 | 本批次伪问题率 > 30% | 必须追加教训 |
| 强制触发 | 触发熔断（>50% 或 >80%） | 必须追加教训 + 提交复盘报告 |
| 强制触发 | 违反规则25（通过API改已有表单） | 必须追加教训 + 立即回滚 |
| 可选触发 | 伪问题率 ≤ 30%，但出现 ≥ 2 个相同类别伪问题 | 建议追加教训 |
| 用户指定 | 用户认为有必要复盘时 | 必须追加教训 |

### 4.3 教训记录格式

```markdown
### 教训-{序号}：{简述}

- **发现日期：** {YYYY-MM-DD}
- **批次号：** {YYYYMMDD-NNN}
- **错误行为：** {具体描述}
- **错误后果：** {造成的浪费或风险}
- **正确做法：** {应该怎么做}
- **违反自检：** {①②③④⑤ / 范式三问}
- **伪问题类别：** {伪-X}
- **问题层级：** {工具链层 / 应用配置层 / 数据层}
- **根因分析：** {为什么会犯这个错误}
- **改进承诺：** {下一批次将如何避免}
```

### 4.4 教训使用方式

1. **测试方每次开始前**：必须阅读本文件，确认不重复已有教训
2. **修复方每次开始前**：必须阅读本文件，确认伪问题预筛覆盖已有教训
3. **出题方每次开始前**：必须阅读本文件，确认用例设计不触发已有教训
4. **新批次复盘**：对照本文件检查是否有新的教训需要追加

## 五、反模式检查清单

在每批次测试执行前，测试方必须对照以下清单自检：

| 检查项 | 对应反模式 | 自检结果 |
|--------|-----------|---------|
| 是否等待公式计算/流程流转完成后再抓取？ | AP-1 | ☐ |
| 是否实际调用了宜搭 API（data-tester）再报告错误码？ | AP-2 | ☐ |
| 是否读了字段清单/规则清单再判定功能是否配置？ | AP-3 | ☐ |
| UI 业务路径（JS动作/联动/条件显示）是否用 UI 操作完成？ | AP-4 | ☐ |
| 是否查询了能力分层清单确认测试范围？ | AP-5 | ☐ |
| 权限测试是否用了正确权限组的账号？ | AP-6 | ☐ |
| 报告的问题是否可稳定复现？ | AP-7 | ☐ |
| 负面用例是否带了量化断言？ | AP-11 | ☐ |
| 前置条件（字段/公式/规则/流程）是否已满足？ | AP-10 | ☐ |
| 关联字段是否走了6步闭环？ | AP-14 | ☐ |
| 批量提交是否按依赖顺序？ | AP-15 | ☐ |
| 测试数据是否真实可信？ | AP-16 | ☐ |

在每批次修复完成后，修复方必须对照以下清单自检：

| 检查项 | 对应反模式 | 自检结果 |
|--------|-----------|---------|
| 是否先做了伪问题预筛？ | AP-12 相关 | ☐ |
| 是否只改了必要的行？ | AP-9 | ☐ |
| 是否未修改提取用例？ | AP-8 | ☐ |
| 是否未自行归档？ | AP-12 | ☐ |
| 是否未通过API改已有表单字段？ | AP-13 | ☐ |
| 工具链修复是否运行了 npm test？ | — | ☐ |
| 应用层修复是否生成了粘贴指引？ | AP-13 | ☐ |
