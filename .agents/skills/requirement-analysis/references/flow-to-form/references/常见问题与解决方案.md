## 问题1：表单类型识别错误（高频错误，必须避免）

**现象**：将流程表单识别为普通表单，或反之。

**根本原因**：
- 没有逐个仔细观察图标细节
- 凭经验判断（如认为"订单"就是流程表单）
- 没有建立书面识别记录
- 没有进行交叉验证

**预防措施**：
1. **必须建立表单类型识别表**，书面记录每个表单的图标特征
2. **逐个检查**，禁止批量判断
3. **只看图标，不看业务含义**（不要根据"这是订单所以是流程表单"来判断）
4. **交叉验证**：统计普通表单和流程表单数量，检查是否合理
5. **使用自检清单**，确保每个检查项都完成

**识别标准**：
| 图标特征 | 表单类型 |
|---------|---------|
| 🔵 蓝色/灰色 + 📄 文档图标 | 普通表单 |
| 🟢 绿色 + ▶️ 播放/三角形图标 | 流程表单 |

**解决**：
- 逐个检查每个表单节点的图标颜色和形状
- 绿色背景 + 三角形 = 流程表单
- 蓝色/灰色文档图标 = 普通表单
- 建立书面识别记录，禁止凭记忆判断

## 问题2：基础档案与业务数据混淆（严重错误）

**现象**：
- 在产品信息表中添加"当前库存"、"安全库存"字段
- 在客户信息表中添加"预付款余额"、"已用额度"字段
- 业务规则直接更新基础档案的业务数据字段

**根本原因**：
- 混淆了"基础档案"和"业务数据"的概念
- 凭经验认为"产品表应该有库存字段"
- 没有理解业务流程中数据应该如何管理

**预防措施**：
1. **严格区分基础档案和业务数据**
   - 基础档案：静态属性（名称、规格、型号等）
   - 业务数据：动态交易数据（库存、金额、数量等）
2. **使用概念辨析检查清单**
   - 生成字段前完成检查清单
   - 确保基础档案不包含业务数据字段
3. **业务规则不更新基础档案的业务数据**
   - 库存数据通过聚合表计算
   - 或更新独立的业务表单（如库存信息表）

**识别标准**：
| 类型 | 特点 | 示例 |
|-----|------|------|
| 基础档案 | 静态、变更少、描述属性 | 产品信息、客户信息、供应商信息 |
| 业务数据 | 动态、频繁变更、记录交易 | 库存记录、订单、入库单、收款记录 |

**解决**：
- 从基础档案中移除业务数据字段
- 通过聚合表实时计算库存/财务数据
- 或创建独立的业务表单管理这类数据
- 更新业务规则，不直接修改基础档案

### 错误示例 vs 正确示例

#### ❌ 错误示例：产品信息表包含库存字段
```
产品信息表（错误）：
├─ 产品编号【流水号】
├─ 产品名称【单行文本】
├─ 规格型号【单行文本】
├─ 当前库存【数值】← ❌ 错误！产品信息不应该有库存字段
├─ 安全库存【数值】← ❌ 错误！这是库存管理范畴
├─ 存放仓库【关联表单】← ❌ 错误！产品可以存放在多个仓库
└─ ...
```

#### ✅ 正确示例：产品信息为纯基础档案
```
产品信息表（正确）：
├─ 产品编号【流水号】
├─ 产品名称【单行文本】
├─ 产品类别【下拉单选】
├─ 规格型号【单行文本】
├─ 单位【下拉单选】
├─ 参考采购价【数值】
├─ 参考销售价【数值】
├─ 产品状态【下拉单选：启用/停用】
└─ ...

库存信息表（独立表单，如流程图中有）：
├─ 库存编号【流水号】
├─ 仓库【关联表单-->仓库信息】
├─ 产品【关联表单-->产品信息】
├─ 当前库存【数值】
├─ 安全库存【数值】
└─ ...
```

### 业务规则错误/正确示例

#### ❌ 错误示例
```
规则：采购入库更新产品库存
- 目标表单: 产品信息 ← ❌ 错误！不应该更新基础档案
- 操作内容: 当前库存 = 当前库存 + 入库数量
```

#### ✅ 正确示例
```
方案A：通过聚合表计算库存（推荐）
- 聚合表名称: 产品库存统计
- 数据源: 采购入库、销售出库、库存盘点等
- 计算逻辑: 当前库存 = SUM(入库数量) - SUM(出库数量) ± SUM(盘点差异)

方案B：独立的库存信息表（如果流程图中有）
规则：采购入库更新库存信息
- 目标表单: 库存信息 ← ✅ 正确！更新业务数据表
- 操作内容: 当前库存 = 当前库存 + 入库数量

方案C：记录业务流水（如果流程图中没有库存信息表）
规则：采购入库记录
- 目标表单: 入库记录（子表或独立表单）
- 操作内容: 记录入库仓库、产品、数量、单价等信息
- 说明: 库存通过聚合表实时计算
```

## 问题3：遗漏表单

**现象**：流程图中有某个表单，但生成的字段清单中没有。

**原因**：
- 没有仔细扫描所有模块下的表单节点
- 某些表单名称与已有概念混淆（如"产品类别"可能被误认为只是字段而非表单）

**解决**：
- 逐个模块检查，确保每个带图标的节点都被记录
- 不要假设某个节点不是表单，只要有图标就是表单

### 常见遗漏场景及预防措施

| 场景 | 原因 | 预防措施 |
|-----|------|---------|
| 垂直排列的顶部表单 | 视线被下方更突出的表单吸引 | 从上到下逐行扫描，不跳过任何节点 |
| 蛇形排列的反向行 | 惯性思维从左到右 | 先判断每行排列方向，再按实际方向读取 |
| 相邻相似表单 | 如"报价"和"订单"都是销售类 | 建立书面清单，逐个标记确认 |
| 小字体/次要位置的表单 | 视觉优先级低 | 放大查看，不遗漏任何带📄或▶️图标的节点 |
| 模块边界处的表单 | 处于两个模块之间 | 明确模块边界，确认归属 |

## 问题4：模块顺序错误

**现象**：生成的模块顺序与流程图不一致。

**原因**：
- 按照个人理解重新排序了模块
- 没有按照流程图主线（最粗的线条）顺序识别
- 忽略了流程图中的中文大写序号

**解决**：
- **优先按照流程图中的中文大写序号排序**（一、二、三...）
- 如果没有中文序号，严格按照流程图视觉呈现的顺序
- 从中心节点开始，按顺时针或从左到右的顺序记录
- 不得根据个人理解重新排序
- **自检**：生成前检查模块顺序是否与流程图序号一致

### 蛇形（S形）顺序识别详解

流程图通常采用蛇形（S形）排列：第一行从左到右，第二行从右到左，第三行从左到右，以此类推。

例如：如果流程图布局为：
```
第一行：基础信息 → 库存管理
第二行：采购管理 ← 销售管理 ← 客户管理
第三行：财务管理 → 其他需求
```
则正确的模块顺序是：基础信息→库存管理→客户管理→销售管理→采购管理→财务管理→其他需求

**识别要点**：
- 仔细观察流程图的布局，确定每一行的排列方向
- 第一行通常从左到右；第二行通常从右到左（与第一行相反）；第三行通常从左到右；以此类推，形成S形走向
- **禁止**简单地按照"从左到右、从上到下"的顺序读取，必须按照实际的蛇形路径读取

## 问题5：表单名称不一致

**现象**：生成的表单名称与流程图中不完全一致。

**原因**：
- 擅自修改了表单名称（如简写、增删字）

**解决**：
- 表单名称必须与流程图中完全一致
- 禁止修改、简写或增删任何字
