# 分层修复原则（宜搭版）

**版本：** 1.0
**定位：** 修复方的工作指南——工具链层 vs 应用层、规则25约束、最小改动、修复可继承

---

## 一、修复方的角色定位

> **修复方只做三件事：伪问题预筛 → 修复真问题 → 工具链健康检查验证。**
> **修复方不做一件事：自行宣布"测试通过"。**

### 1.1 修复方职责边界（宜搭版）

| 允许 | 禁止 |
|------|------|
| 核验 ISS 是否为伪问题 | 自行宣布"测试通过" |
| 修改工具链 skill 脚本修复 bug（分配 FW 编号） | 代用户归档 |
| 生成应用层修复产物（公式/代码/配置）+ 粘贴指引 | 为"有意不做"类 ISS 擅自添加实现 |
| 执行工具链健康检查（npm test） | 为 P1/P2 问题引入新的 API 请求或运行时数据清洗 |
| 补充回归用例到覆盖矩阵 | 未做伪问题预筛就动手修复 |
| 调用 data-tester/data-clean 修复数据问题 | **通过 API 修改已有应用的表单字段内容（规则25）** |
| | 应用层修复不生成粘贴指引 |

### 1.2 修复方的核心 KPI

| KPI | 标准 | 说明 |
|-----|------|------|
| 回归零回退 | 修复后不引入新问题 | 所有回归用例必须通过 |
| 工具链健康检查 100% 通过 | `npm test` 执行通过 | Jest 单元测试 |
| 范式越界 ISS 退回率 100% | 伪-6~伪-9 类 ISS 必须退回 | 不为范式越界问题做实现 |
| 修复产物完整率 100% | 应用层修复必须含修复产物 + 粘贴指引 | 规则25约束 |
| 最小改动 | 不引入无关变更 | 不趁机重构、不扩大修改范围 |

---

## 二、问题三层分类（宜搭版）

### 2.1 为什么要分层

宜搭应用测试中存在三类问题：

| 类型 | 特征 | 修复策略 | 编号 | 规则25 |
|------|------|---------|------|--------|
| **工具链层** | AI 工具链 skill 脚本的通用逻辑缺陷，影响所有应用 | 修复 skill 脚本，所有应用受益 | 分配 FW 编号 | 不受约束 |
| **应用配置层** | 特定应用的字段/公式/规则/流程配置问题，只影响该应用 | 生成修复产物 + 粘贴指引，用户手动应用 | 不分配 FW 编号 | **受约束** |
| **数据层** | 应用中的业务数据错误/缺失/关联错配 | data-tester 重新提交或 data-clean 清理 | 不分配 FW 编号 | 不受约束（数据操作）|

### 2.2 分层判定流程

```
收到 ISS 问题
    ↓
问题根因是什么？
    ├─ 工具链 skill 缺陷（form_creator/formula-generator/data-tester 等的逻辑错误）
    │   → 分配 FW-XX 编号
    │   → 修改 skill 脚本（scripts/*.js）
    │   → 运行 npm test 验证
    │   → 补充回归用例到覆盖矩阵
    │   → 所有应用受益
    │
    ├─ 应用配置问题（字段/公式/规则/流程配置不正确）
    │   → 不分配 FW 编号
    │   → 生成修复产物（公式JSON/代码/配置）+ 粘贴指引
    │   → 用户手动粘贴到宜搭（规则25）
    │   → 记录处理方式
    │
    ├─ 数据问题（测试数据错误/缺失/关联错配）
    │   → 不分配 FW 编号
    │   → data-tester 重新提交正确数据
    │   → 或 data-clean 清理错误数据后重新提交
    │   → 回查验证
    │
    └─ 设计决策与测试预期不一致
        → 优先调整设计/配置以支持业务需求（HC9）
        → 不以"设计决策"为由搁置
        → 应用层调整走"生成产物+粘贴指引"流程
```

### 2.3 分层判定决策表

| 问题现象 | 可能层级 | 判定方法 | 修复方向 |
|---------|---------|---------|---------|
| 某功能在所有应用中都不工作 | 工具链层 | 检查 skill 脚本中该功能的实现 | 修复 skill 脚本 |
| 某功能只在当前应用中不工作 | 应用配置层 | 检查当前应用的字段清单/规则清单 | 生成修复产物 + 粘贴指引 |
| AI 生成的公式在所有应用中都算错 | 工具链层 | 检查 formula-generator 的 marks 计算 | 修复 formula-generator 脚本 |
| AI 生成的公式只在当前应用算错 | 应用配置层 | 检查该应用的公式配置 | 生成正确公式 + 粘贴指引 |
| 关联字段 instanceId 与 title 错配 | 数据层 | 检查 data-tester 提交时是否走了6步闭环 | data-tester 重新提交（走6步闭环）|
| 公式正确但字段为空 | 数据层 | 检查提交时是否遗漏该字段 | data-tester 重新提交补全字段 |
| 工具链脚本有逻辑但未被应用调用 | 工具链层 + 应用配置层 | 检查应用配置是否正确引用了工具链能力 | 修复配置（应用层）+ 完善工具链提示（工具链层）|

## 三、最小改动原则

### 3.1 核心理念

> **修复的目标是消除 bug，不是重构代码。**

### 3.2 最小改动规则

| 规则 | 说明 | 违反示例 |
|------|------|---------|
| 只改必要的行 | 修复 bug 涉及的最少代码行数 | 趁机重命名变量、调整格式 |
| 不引入新依赖 | 修复不得引入新的第三方包 | 为了修复一个格式问题引入 lodash |
| 不扩大修改范围 | 不修改与 bug 无关的文件 | 修复表单 bug 时顺便改了报表组件 |
| 不改变 API 契约 | 修复不得改变已有接口的输入输出 | 修复校验问题时改变了返回格式 |
| 不引入新的运行时开销 | P0/P1 修复不得引入新的 API 请求或数据清洗 | 修复显示问题时添加了实时数据请求 |

### 3.3 应用层修复的最小改动

> **应用层修复受规则25约束，"改动"= 生成新的配置产物，由用户手动粘贴替换。**

| 规则 | 说明 |
|------|------|
| 只生成必要的修复产物 | 不趁机重新生成整个表单/整个规则清单 |
| 不改变字段结构 | 修复公式错误时只改公式，不增删字段 |
| 不改变流程结构 | 修复流程节点问题时只改该节点，不重构流程 |
| 提供精确的粘贴位置 | 指明在宜搭设计器的哪个表单/哪个字段/哪个规则处粘贴 |

### 3.4 例外情况

| 情况 | 允许的偏离 | 条件 |
|------|-----------|------|
| P0 阻塞性问题 | 可引入必要的结构性调整 | 必须在 ISS 中说明原因 |
| 安全漏洞 | 可引入新的校验逻辑 | 不改变正常路径的行为 |
| 数据一致性 | 可引入事务/回滚逻辑 | 不影响正常路径性能 |
| 工具链共性问题 | 可重构 skill 脚本的公共逻辑 | 必须补充 Jest 单元测试 |

## 四、修复工作流（宜搭版）

### 4.1 标准修复流程

```
收到 ISS 问题列表
    ↓
Step 1: 伪问题预筛
    ├─ 逐条核验每个 ISS
    ├─ 按 9 类伪问题分类（见 03-质量治理机制.md）
    ├─ 伪问题 → 标注类别 + 违反自检项 → 退回核验方
    └─ 真问题 → 进入 Step 2
    ↓
Step 2: 根因分析 + 层级判定
    ├─ 确定问题层级（工具链层 / 应用配置层 / 数据层）
    ├─ 工具链层：定位到 skill 脚本的具体文件和行
    ├─ 应用配置层：定位到字段清单/规则清单的具体配置
    ├─ 数据层：定位到具体记录和字段
    └─ 确认修复方案（最小改动）
    ↓
Step 3: 执行修复（按层级分流）
    ├─ 工具链层 → Step 3A
    ├─ 应用配置层 → Step 3B
    └─ 数据层 → Step 3C
    ↓
Step 4: 验证
    ├─ 工具链层 → 运行 npm test
    ├─ 应用配置层 → 用户粘贴后，核验方回查
    └─ 数据层 → data-tester 回查验证
    ↓
Step 5: 补充回归用例
    ├─ 为每个修复补充回归用例
    └─ 更新能力覆盖矩阵
    ↓
Step 6: 更新问题跟踪
    └─ 将 ISS 状态更新为"已修复"
```

### 4.2 Step 3A：工具链层修复

```
1. 修改 skill 脚本（scripts/*.js）
2. 确保不引入新问题
3. 不扩大修改范围
4. 运行 npm test 验证
5. 如 npm test 失败 → 修复 → 重新运行
6. 分配 FW 编号
7. 补充 Jest 单元测试到 tests/core 或 tests/features
```

### 4.3 Step 3B：应用配置层修复（规则25约束）

```
1. 根据问题类型选择生成 skill：
   - 公式问题 → formula-generator
   - 代码问题 → code-expert
   - 字段结构问题 → form_designer（生成配置）
   - 业务规则问题 → business-rule
   - 流程问题 → flow-settings
2. 生成修复产物：
   - 公式：JSON 文件 + marks 计算说明
   - 代码：JS 代码文件
   - 配置：JSON 配置文件
3. 生成粘贴指引：
   - 指明在宜搭设计器的哪个位置粘贴
   - 提供具体的操作步骤（打开哪个表单 → 哪个字段 → 粘贴什么）
4. 输出给用户：
   - 修复产物文件路径
   - 粘贴指引文档
5. 用户手动粘贴后，通知核验方回查
```

**修复产物格式示例（公式修复）：**

```markdown
### 修复产物：{公式名称}

**问题 ISS：** ISS-{批次号}-XXX
**修复文件：** {应用项目目录}/修复产物/ISS-XXX-公式修复.json
**粘贴位置：**
1. 打开宜搭应用「{应用名称}」
2. 进入表单「{表单名称}」的设计模式
3. 找到字段「{字段名称}」（字段ID: {fieldId}）
4. 在公式编辑器中粘贴以下公式：

\`\`\`
{公式内容}
\`\`\`

5. 保存并发布
```

### 4.4 Step 3C：数据层修复

```
1. 识别数据问题类型：
   - 字段为空 → data-tester 重新提交补全
   - 关联错配 → 删除错误记录，走6步闭环重新提交
   - 数据重复 → data-clean 清理后重新提交
   - 数据错误 → data-clean 删除错误数据，data-tester 提交正确数据
2. 执行修复：
   - 调用 data-tester 的 submitAIGeneratedData 重新提交
   - 或调用 data-clean 的 clear-form-data 清理
3. 回查验证：
   - 调用 searchFormDatas.json 验证数据已正确写入
   - 关联字段验证 title 与 instanceId 是否匹配
```

### 4.5 伪问题预筛标准

修复方在收到 ISS 后，必须先做伪问题预筛，**不得跳过此步骤直接修复**：

| 伪问题类别 | 宜搭版预筛方法 | 处理 |
|-----------|--------------|------|
| 伪-1 凭空捏造 | 检查字段清单/规则清单中是否存在该功能 | 退回，标注"清单中不存在" |
| 伪-2 未读源码 | 读字段清单/规则清单确认功能是否已配置 | 退回，标注"已配置于 {清单路径}" |
| 伪-3 未理解设计 | 检查测试方是否理解宜搭权限组/流程节点设计 | 退回，标注"设计为 {说明}" |
| 伪-4 时序问题 | 检查测试方是否等待公式计算/流程流转完成 | 退回，标注"异步未等待" |
| 伪-5 用例库问题 | 检查用例预期与字段清单/规则清单是否一致 | 退回，反馈出题方修订 |
| 伪-6 范式越界 | 查询能力分层清单，确认是否"有意不做" | 退回，标注"范式越界" |
| 伪-7 角色错位 | 检查测试预期是否与宜搭范式冲突 | 退回，标注"角色错位" |
| 伪-8 重量级预期 | 检查是否要求简单表单提供复杂功能 | 退回，标注"重量级预期" |
| 伪-9 平衡失调 | 检查是否混淆"宜搭设计器配置"和"AI生成" | 退回，标注"平衡失调" |

## 五、修复可继承原则

### 5.1 核心理念

> **工具链层的修复应该让所有应用受益，而不只是当前应用。**

### 5.2 可继承修复的标准

| 标准 | 说明 |
|------|------|
| 修复在工具链层 | 修改的是 skill 脚本代码 |
| 修复有回归用例 | 补充的 Jest 单元测试进入 tests/core 或 tests/features |
| 修复不依赖应用配置 | 修复逻辑不依赖特定应用的字段/规则 |
| 修复有 FW 编号 | 可在问题跟踪中追踪 |

### 5.3 不可继承的修复

| 类型 | 处理 |
|------|------|
| 应用配置修复 | 记录处理方式，不进入 FW 修复索引 |
| 应用特定UI调整 | 记录处理方式 |
| 应用特定数据修复 | data-tester 修复后记录 |

### 5.4 共性问题溯源

> **当多个应用出现同类问题时，应溯源到工具链层修复。**

例如：
- 多个应用的关联字段都出现 instanceId-title 错配 → 溯源到 data-tester 的 submitter.js，修复 associationMeta 提取逻辑
- 多个应用的公式 marks 都算错 → 溯源到 formula-generator 的 formula_evaluator.js
- 多个应用的字段类型推断错误 → 溯源到 excel-to-form 的字段类型推断逻辑

## 六、修复禁止行为

### 6.1 绝对禁止

| 禁止行为 | 原因 |
|---------|------|
| **通过 API 修改已有应用的表单字段内容** | 规则25禁止，可能导致线上应用被误改误删 |
| 为"有意不做"类 ISS 擅自添加实现 | 违反应用范式，引入不需要的复杂度 |
| 为 P1/P2 问题引入新的 API 请求 | 可能引入性能问题和新的依赖 |
| 为 P1/P2 问题引入运行时数据清洗 | 可能影响正常路径性能 |
| 趁修复之名行重构之实 | 扩大修改范围，增加风险 |
| 工具链修复后不运行 npm test | 可能引入类型错误/单元测试失败 |
| 跳过伪问题预筛直接修复 | 浪费修复资源，鼓励伪问题 |
| 自行宣布"测试通过" | 只有核验方和用户才能判定通过 |
| 应用层修复不生成粘贴指引 | 用户无法应用修复 |

### 6.2 修复方常见错误

| 错误 | 正确做法 |
|------|---------|
| 收到 ISS 直接开始修复 | 先做伪问题预筛 |
| 应用层问题直接改 skill 脚本 | 应用配置问题修配置，不动工具链 |
| 工具链问题生成粘贴指引让用户改 | 工具链问题直接改脚本，用户无感知 |
| 修复时顺便重构相关代码 | 只改必要的行 |
| 工具链修复后不补充 Jest 测试 | 每个工具链修复必须有 Jest 回归用例 |
| 应用层修复不提供粘贴位置 | 必须指明在宜搭设计器的具体粘贴位置 |
| 通过 API 修改已有表单字段 | 生成修复产物 + 粘贴指引（规则25）|

## 七、修复验证清单

修复方在完成修复后，必须逐项确认：

| 验证项 | 标准 | 状态 |
|--------|------|------|
| 伪问题预筛 | 所有 ISS 已逐条核验 | ☐ |
| 真问题已修复 | 所有真问题已按层级修复 | ☐ |
| FW 编号分配 | 工具链层问题已分配 FW 编号 | ☐ |
| 最小改动 | 未引入无关变更 | ☐ |
| 工具链健康检查通过 | `npm test` 执行通过（如改了 skill 脚本）| ☐ |
| 修复产物完整 | 应用层修复含修复产物 + 粘贴指引 | ☐ |
| 回归用例补充 | 每个修复有对应回归用例 | ☐ |
| 能力矩阵更新 | 覆盖矩阵已更新 | ☐ |
| ISS 状态更新 | 状态已标记为"已修复" | ☐ |
| 禁止行为检查 | 未触发任何禁止行为（含规则25）| ☐ |
