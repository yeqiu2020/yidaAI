# 角色与工具协作机制（宜搭版）

**版本：** 1.0
**定位：** 定义宜搭应用测试过程中各角色、各 skill 工具的职责、隔离规则和制衡机制

---

## 一、多工具协作链路

> **核心目的：打破"一个 AI 自己出题、自己测、自己修、自己点头"的内在弊端。**
> **宜搭适配：测试方和修复方都可能是多工具协作，但角色边界必须清晰。**

```
[1. 发起方/协调方 主AI session]
    ↓ 读取应用配置，协调全流程
[2. 出题方 独立 session]
    ↓ 从用例库提取用例（含至少 2 个负面 + 量化断言）
    ↓ 每个用例标注执行工具（data-tester / js-action-tester / playwright-cli）
[3. 测试方 独立 session（跨厂商模型）]
    ↓ 根据用例类型调用对应 skill：
    ↓   · data-tester (API)      → 表单数据提交、公式计算、校验规则、关联数据
    ↓   · js-action-tester (UI)   → 表单JS动作、字段联动、条件显示
    ↓   · playwright-cli (E2E)    → 完整用户路径、流程审批、权限可见性
    ↓ 沟通记录 + 问题跟踪（四元统计）
[4. 修复方 当前 session]
    ↓ 伪问题预筛 → 修复真问题
    ↓   · 工具链层：修改 skill 脚本（form_creator/formula-generator/code-expert 等）
    ↓   · 应用层：生成修复产物（公式/代码/配置）+ 粘贴指引（规则25）
    ↓ 工具链健康检查（npm test）
[5. 核验方 同测试 session]
    ↓ 回归验证修复效果
    ↓   · data-tester 回查验证 → 字段是否写入、关联是否正确
    ↓   · js-action-tester 回归 → JS动作是否生效
    ↓ 禁改用例
[6. 归档 用户最终点头]
    ↓ 用户审证据链 + 数据清理
[批次完成]
```

### 角色职责矩阵（宜搭版）

| 环节 | 执行方 | Session | 模型 | 职责 | 禁止行为 |
|------|--------|---------|------|------|---------|
| 1. 发起 | 主 AI | 当前 session | — | 读取应用配置，协调全流程，初始化批次号 | 不参与出题判定 |
| 2. 出题 | 出题方 | 独立 session | 跨厂商模型 | 从用例库提取用例，标注执行工具，强制含负面用例 | 不得参与测试判定 |
| 3. 测试 | 测试方 | 独立 session | **跨厂商模型** | 调用 data-tester/js-action-tester/playwright-cli 执行测试，四元统计 | 不得修改 skill 源码、不得修改用例 |
| 4. 修复 | 修复方 | 当前 session | 跨厂商模型 | 核验 ISS，伪问题预筛，修复真问题（工具链层改脚本/应用层生成产物） | 不得自行宣布"测试通过" |
| 5. 核验 | 核验方 | 同测试 session | 跨厂商模型 | 回归验证修复效果，禁改用例 | 不得修改 skill 源码 |
| 6. 归档 | **用户** | — | — | 审证据链 + 数据清理，点头归档 | 不得由 AI 代为点头 |

## 二、skill 工具与角色映射

> **宜搭项目的核心特点：测试方和修复方都是多工具协作。**

### 2.1 测试方可调用的 skill

| skill | 测试模式 | 适用能力域 | 调用方式 |
|-------|---------|-----------|---------|
| **data-tester** | API + 浏览器 | 表单数据提交、公式计算、校验规则、关联数据回查、流程审批、子表数据 | `submitAIGeneratedData` / `searchFormDatas` / `result-validator.js` |
| **js-action-tester** | UI（Playwright） | 表单JS动作代码、字段联动、条件显示、事件绑定 | `test-runner.js` / `run-test.js` |
| **playwright-cli** | E2E（浏览器） | 完整用户路径、流程审批流转、权限可见性、页面交互、报表展示 | Playwright 脚本 |

### 2.2 修复方可调用的 skill

| 问题层级 | 适用 skill | 修复方式 | 规则25 |
|---------|-----------|---------|--------|
| 工具链层（skill脚本缺陷） | 直接修改对应 skill 的 scripts/*.js | 直接改代码，分配 FW 编号 | 不受约束 |
| 应用层-公式问题 | formula-generator | 生成公式 JSON + 粘贴指引 | 受约束，用户手动粘贴 |
| 应用层-代码问题 | code-expert | 生成代码 + 粘贴指引 | 受约束，用户手动粘贴 |
| 应用层-字段结构问题 | form_creator（仅新建表单）/ form_designer | 生成字段配置 + 粘贴指引 | 受约束，已有表单只能粘贴 |
| 应用层-业务规则问题 | business-rule | 生成规则配置 + 粘贴指引 | 受约束，用户手动配置 |
| 应用层-流程问题 | flow-settings | 生成流程配置 + 粘贴指引 | 受约束，用户手动配置 |
| 应用层-数据问题 | data-tester / data-clean | 重新提交或清理数据 | 不受约束（数据操作非字段修改）|

### 2.3 协调方（主AI）职责

主 AI session 作为发起方和协调方，负责：
1. 读取待测应用的配置文件（系统配置清单、字段清单、规则清单）
2. 初始化批次号
3. 分发出题提示词给出题方
4. 分发测试提示词给测试方，并根据用例类型建议调用哪个 skill
5. 接收测试结果，分发修复提示词给修复方
6. 接收修复结果，分发回归验证提示词给核验方
7. 协助用户完成归档门禁检查

## 三、角色 KPI 互斥

> **每个角色的考核指标相互制衡，防止"刷通过率"或"走过场"。**

| 角色 | 考核指标 | 互斥点 |
|------|---------|--------|
| 出题方 | 负面用例占比 ≥20%、量化断言完整率 100%、预期产品依据标注率 100%、执行工具标注率 100% | **不考核通过率**——不得预判用例能否通过 |
| 测试方 | FAIL 发现率、SKIP 率 ≤20%、伪问题率 ≤30%、ISS 自检附载率 100%、工具调用正确率 100% | **不考核"测得快"**——鼓励深入测试边界条件 |
| 修复方 | 回归零回退、工具链健康检查 100% 通过（npm test）、范式越界 ISS 退回率 100%、修复产物完整率 100% | **不考核"修得快"**——最小改动原则 |
| 核验方 | 回归验证覆盖率 100%、伪阳性识别率、伪问题分类完整率 100% | **不参与修复**——只验证不修 |
| 用户 | 归档门禁通过率 | **唯一决策归档** |

## 四、Session 隔离规则

### 4.1 为什么需要 Session 隔离

| 不隔离的问题 | 隔离后的效果 |
|-------------|-------------|
| AI 自己出题自己测 → 出简单的题 | 出题方不知道测试方会怎么测 |
| AI 自己测自己改 → 降低标准 | 测试方不知道修复方会怎么改 |
| AI 自己改自己判通过 → 放水 | 修复方不得自行宣布通过 |
| AI 自己归档 → 跳过门禁 | 归档必须用户点头 |

### 4.2 隔离实现方式

- **独立 session**：新开 AI 对话窗口，不共享上下文
- **跨厂商模型**：测试方和修复方使用不同 AI 厂商的模型
- **文件传递**：各 session 通过文件（提取用例/沟通记录/问题跟踪）传递信息，不直接对话

### 4.3 宜搭适配：测试方内部的多 skill 调用

> **重要：** 测试方在执行测试时，可能需要调用多个 skill（data-tester、js-action-tester、playwright-cli）。这些 skill 在**测试方的同一 session 内**调用是允许的，因为它们都是"测试执行"的工具，不涉及角色越界。

允许的测试方内部调用：
- ✅ data-tester 提交数据后，用 data-tester 回查验证
- ✅ js-action-tester 执行JS动作测试后，用 playwright-cli 验证页面效果
- ✅ 同一用例混合使用 API 和 UI 验证（API 准备数据，UI 验证展示）

禁止的跨角色调用：
- ❌ 测试方调用 formula-generator 修改公式（这是修复方的职责）
- ❌ 测试方调用 form_creator 修改表单结构（这是修复方的职责）
- ❌ 修复方调用 data-tester 自行宣布"测试通过"（只有核验方能判定通过）

### 4.4 身份标注规范

在沟通记录、问题跟踪的"角色/执行者"列，必须填**当前运行的 IDE/智能体产品名**（如 `Trae`、`Cursor`、`Claude Code`），**不是底层大模型名**。同时标注调用的 skill 名称（如 `Trae + data-tester`）。

---

## 五、测试方有限扩展权

测试方在执行测试时，如发现可疑点但提取用例未明确覆盖，可追加 **1-2 个验证步骤**：

1. 在沟通记录中标注 `[扩展验证]` 前缀
2. 说明扩展验证的触发原因
3. 扩展验证结果单独统计，不混入主用例通过率
4. 扩展验证发现的问题标注为 `[扩展发现]` 前缀

## 六、角色禁止行为汇总

### 出题方禁止

- ❌ 预判用例能否通过
- ❌ 参与测试判定
- ❌ 取用应用"有意不做"的能力对应的用例
- ❌ 不标注执行工具（data-tester/js-action-tester/playwright-cli）

### 测试方禁止

- ❌ 修改 skill 源代码
- ❌ 修改提取用例文件
- ❌ 自行宣布"测试通过"
- ❌ 用 API 调用替代 UI 业务路径通过（API 测试除外）
- ❌ 在 loading 态抓取 DOM 判定"无响应"（宜搭表单提交、公式计算均为异步）
- ❌ 凭推断报告宜搭 API 错误码（必须实际调用 data-tester）
- ❌ 凭 UI 表面现象判定"功能未实现"（必须读字段清单/Schema 确认）
- ❌ 调用修复类 skill（formula-generator/code-expert 等）修改应用

### 修复方禁止

- ❌ 自行宣布"测试通过"
- ❌ 代用户归档
- ❌ 为"有意不做"类 ISS 擅自添加实现
- ❌ 为 P1/P2 问题引入新的 API 请求或运行时数据清洗
- ❌ 未做伪问题预筛就动手修复
- ❌ 通过 API 修改已有应用的表单字段内容（规则25）
- ❌ 应用层修复不生成粘贴指引（必须本地生成 → 用户手动粘贴）

### 核验方禁止

- ❌ 修改 skill 源代码
- ❌ 修改提取用例（禁改用例）
- ❌ 参与修复
- ❌ 调用修复类 skill
