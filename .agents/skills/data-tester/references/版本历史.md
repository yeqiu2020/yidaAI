# data-tester 版本历史

> 来源：data-tester SKILL.md 下沉内容。正文只保留当前版本号，完整更新日志在本文件维护。

### v3.7.3 (2026-08-01)
- **【优化·新增功能】DateField（日期组件）自动填充当前时间**
  - 根因：DateField字段（创建时间等）在宜搭UI中默认值公式会触发，但API提交时不会自动填充。AI需要手动为每个日期字段生成时间戳，增加了AI的工作量且容易遗漏。
  - 修复：`submitAllWithAutoAssociations` 新增 DateField 自动填充——扫描所有表单Schema中的DateField字段，为AI未提供值的字段自动填充当前时间戳（`Date.now()`）。
  - 原则：只在AI未提供值时自动填充，如果AI提供了具体业务日期（如"需到货日期"），不会覆盖。
  - 同时支持子表内的DateField字段自动填充。
  - SKILL规则：新增专属硬规则第11条——"DateField在API提交时不会自动填充，必须赋值"
  - 文档更新：AI数据生成指南中"创建时间"相关说明简化，字段完整性检查说明更新，检查清单条目简化。
- **【严重·根因修复】EmployeeField（成员组件）字段值缺失**
  - 根因：EmployeeField字段（创建人、负责人等）在宜搭UI中会自动填充当前用户，但API提交时不会自动填充。AI不知道userId，导致这些字段为空。与被填充字段(dataFillingRules)同属"UI有自动行为、API没有"的陷阱。
  - 修复1：`submitAllWithAutoAssociations` 新增 EmployeeField 自动填充——扫描所有表单Schema中的EmployeeField字段，为AI未提供值的字段自动填充当前登录用户ID。
  - 修复2：`extractFieldValue` 新增 EmployeeField 类型处理——从formData格式`[{value: userId, label: "姓名"}]`中正确提取userId字符串，使被填充字段的负责人等成员字段能正确从源记录抄写。
  - SKILL规则：新增专属硬规则第10条——"EmployeeField在API提交时不会自动填充，必须赋值"

### v3.7.1 (2026-07-25)
- **【严重·根因修复】被填充字段值缺失 + 依赖表单幂等性缺失**
  - 根因1（字段空值）：被填充字段（dataFillingRules 填充的只读字段，如仓库名称、仓库地址等）在API提交时不会自动填充。v3.7.0 尝试了自动填充但代码有bug——`targetRecords.find(r => r.instanceId)` 中，`buildReverseTitleMap` 返回的值是 `formInstId`，而普通表单记录的 `r.instanceId` 可能为空，导致查找失败。修复为优先用 `r.formInstId` 匹配。
  - 根因2（数据翻倍）：v3.7.0 只为基础表单添加了幂等性检查，依赖表单（含关联字段的表单）仍会被重复提交。修复为依赖表单也添加幂等性检查。
  - SKILL规则：新增专属硬规则第9条——"被填充字段在API提交时不会自动填充，必须手动赋值"

### v3.6.1 (2026-07-25)
- **【严重·防调试失控】AI 编造无效区划代码导致 10+ 分钟临时脚本排查**
  - 根因：AI 生成地址数据时编造不存在的武汉区划代码（蔡甸区误写 420122，正确 420114），服务端只返回笼统报错；且失败后看不到提交载荷，AI 只能写临时调试脚本逐轮排查
  - 修复1：`AddressField` 本地预校验武汉区划代码（提交前即报精确错误并附合法代码表：420102 江岸 / 420103 江汉 / 420104 硚口 / 420105 汉阳 / 420106 武昌 / 420107 青山 / 420111 洪山 / 420112 东西湖 / 420113 汉南 / 420114 蔡甸 / 420115 江夏 / 420116 黄陂 / 420117 新洲）
  - 修复2：记录提交失败时直接打印该条的提交载荷（transformedData），无需再写调试脚本
  - 要求：**生成地址数据时，武汉各区必须使用上述合法区划代码，禁止编造**

### v3.6.0 (2026-07-25)
- **【严重·根因修复】关联填充静默失败 + 删除能力缺失导致 AI 自救失控（混元三 40 分钟事故）**
  - 根因1（静默失败）：`submitAllWithAutoAssociations` 在基础表单提交后立即查询 instanceId，宜搭搜索索引有数秒延迟窗口，撞上窗口时映射为空，函数仅打警告后继续提交"空关联"假成功数据
  - 根因2（无修复手段）：skill 无任何删除/清空函数，AI 失败后只能违规手写临时脚本自救
  - 根因3（CSRF 不对称陷阱）：创建 API 不需要 `_csrf_token`、删除 API 必须携带，AI 手搓删除全部静默失败（"假删除"），造成重复数据、又花 15 分钟清理
  - 修复1：instanceId 查询前显式等待（`indexWaitMs`，默认 2s）+ 按预期记录数轮询重试（`indexMaxRetries`，默认 5 次递增退避），超时直接抛错中止
  - 修复2：关联字段匹配不到目标记录时 fail-fast 中止并列出明细（`allowPartialFill=true` 可强制继续）；标题匹配增加模糊匹配降级
  - 修复3：基础表单提交失败时中止后续流程，避免产生无关联孤立数据
  - 修复4：新增 `deleteFormData`/`deleteInstance`/`clearFormData` 并导出——自动携带 `_csrf_token`、逐条校验删除结果、普通/流程自动分流，严禁 AI 手写删除脚本
  - 修复5：`searchFormDatas` 自动翻页（此前只取第 1 页 100 条，存量超限会导致映射不完整）
  - 修复6：formDataMap 中存在但 formOrder 未列出的表单显式告警（此前被静默丢弃）
  - 文档：场景2 新增"防翻车三原则"——唯一推荐姿势 / 严禁自行预解析标题 / 数据异常标准修复流程（清空→重跑）

### v3.5.0 (2026-07-25)
- **【严重·根因修复】模拟数据耗时从20分钟降至3分钟——新增一键自动关联提交函数**
  - 根因：v3.1.0~v3.4.0 逐版本修Bug时，每次都增加规则约束AI行为，导致 SKILL.md 膨胀到 600+ 行、6步关联流程需要 AI 手动编排4次脚本调用。AI 花 80% 时间在读文档和编排流程上，而非生成数据。
  - 修复1：新增 `submitAllWithAutoAssociations(projectDir, formDataMap, formOrder, associationConfig?, options?)` — 关联字段传标题字符串即可，函数自动完成：提交基础表单 → 查询 instanceId → 填充关联字段 → 提交依赖表单
  - 修复2：自动检测关联字段（从 Schema 的 AssociationFormField.associationMeta.formUuid 匹配目标表单），无需手动配置
  - 修复3：自动区分主表关联字段 vs 子表内关联字段（通过 isSubformColumn 标记），子表关联字段放入"表单名.子表名"分组
  - 修复4：精简 SKILL.md（630行→440行），6步关联流程折叠为简短引用，避免 AI 读到旧指令走回头路
  - 修复5：精简检查清单（11+8条→7+5条），删除已由函数自动保障的冗余条目
  - 效果：AI 只需"生成数据 + 调一个函数"，1次 RunCommand 完成，实测 3.8s

### v3.3.1 (2026-07-21)
- **【严重·根因修复】流程表单用 saveFormData 导致详情页打不开——新增表单类型自动检测 + startInstance 分流**
  - 根因：`submitter.js` 对所有表单一律调用 `/v1/form/saveFormData.json`。对普通表单正确，但对**流程表单**只写入表单数据、不创建流程实例上下文（无 instanceStatus、无 processCode、无 actioners），产生的记录 formInstId 为 `FINST-xxx` 格式（正常流程实例为 UUID 格式），详情页因缺少流程上下文而永远加载不出来（转圈/闪电符号）
  - 实证证据：A/B 对比测试——同一表单数据分别用 saveFormData 和 startInstance 提交，前者 instanceStatus=空❌，后者 instanceStatus=RUNNING✅；横向对比——本应用 3A703 表单通过正确路径提交的记录 instanceStatus=COMPLETED✅，而 756F 和目标表单通过 saveFormData 提交的记录 instanceStatus 全部为空❌
  - 修复1：新增 `getFormMeta(appId, formUuid)` — 通过导航列表 API 自动判定 formType(receipt/process) 和 processCode
  - 修复2：新增 `startInstance(appId, formUuid, processCode, data)` — 流程表单走 `/v1/process/startInstance.json` 发起真实流程实例
  - 修复3：`submitOne`/`submitBatch` 按 formType 自动分流：流程表单→startInstance，普通表单→saveFormData
  - 修复4：新增 `verifyProcessInstance()` 提交后完整性自检——流程表单抽查一条记录校验 instanceStatus 存在
  - 修复5：**安全机制**——表单类型探测失败时**绝不降级为普通表单**（那正是本次事故的成因），而是直接抛错拒绝提交
  - 修复6：导出 `getFormMeta`/`startInstance`/`verifyProcessInstance`/`getRequest`（v3.3.0 新增但未导出，已修复）
  - 修复7：新增专属硬规则8——流程表单严禁用 saveFormData；新增问题6排障条目
  - 用户疑虑澄清："以前流程表单也成功过"是因为那些数据通过**浏览器模式**或**手动提交**创建（正确发起了流程），而非通过 API 的 saveFormData

### v3.4.0 (2026-07-18)
- **【严重·防误用修复】buildTitleMap 方向误用导致15分钟耗时——新增反向映射函数**
  - 根因：`buildTitleMap` 返回 `{instanceId: title}`（正向），但 AI 实际场景往往是"已知 title 查 instanceId"，直接用 `warehouseMap[title]` 返回 undefined，导致关联字段instanceId为空，触发宜搭API报错"syntax error, expect [, actual {"，然后花10分钟排查
  - 修复1：新增 `buildReverseTitleMap(records)` 函数，直接返回 `{title: instanceId}` 反向映射
  - 修复2：新增 `findRecordByTitle(records, title)` 函数，按title直接返回完整记录对象（含formData），方便获取被填充字段值
  - 修复3：SKILL.md 第3步增加正向/反向映射选择表，明确各场景应使用的函数
  - 修复4：SKILL.md 第4步新增 `findRecordByTitle` 推荐用法示例（一次获取instanceId + formData）
  - 修复5：新增专属硬规则7——使用内置函数前必须先读其 JSDoc 注释，禁止凭函数名猜测返回结构
  - 效果：下次遇到相同场景，AI直接用 `buildReverseTitleMap` 或 `findRecordByTitle`，无需手动翻转映射，避免方向误用

### v3.3.0 (2026-07-17)
- **【严重·性能优化】多表单提交耗时从20分钟降至25秒——新增 `submitAllAIGeneratedData` 批量提交函数**
  - 根因：AI逐个表单调用 `submitAIGeneratedData`，每次都是独立的 RunCommand → 终端启动3s + 脚本7s + AI思考等待 = 5个表单×4分钟 = 20分钟。**脚本本身只需35秒，95%时间浪费在AI操作步骤上**
  - 修复：新增 `submitAllAIGeneratedData(projectDir, formDataMap, formOrder, options)` 函数，一次调用处理所有表单
  - 优化1：1次 RunCommand 代替5次，消除终端启动和AI思考等待
  - 优化2：去掉冗余的 `getExistingDataCount`（提交前后各1次→仅提交后1次），减少50%的count查询API调用
  - 优化3：delay从1000ms降到500ms，提交间隔缩短50%
  - 优化4：`discoverForms` 只调用1次（原来每个表单调1次 = 5次）
  - 新增专属硬规则：**多表单必须使用 `submitAllAIGeneratedData`，严禁逐表单调用 `submitAIGeneratedData`**
