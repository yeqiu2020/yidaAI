# `excel-to-form` Skill 综合评估报告

> **评估目的**：诊断该 skill 在弱模型（如 DeepSeek V4）执行时出现的质量问题（关联表单字段未识别、忘记填充、字段类型不对、说明遗漏）和性能问题（执行时长 7-15 分钟），区分"模型能力问题"与"skill 设计问题"，并提出优化方向。
>
> **评估状态**：仅评估，未做任何修改。
> **评估日期**：2026-07-23

---

## 一、总体结论

该 skill 的架构理念是先进的（preview → AI 一次性生成 override → 脚本一次应用 → 校验），但**当前实现存在多处"强模型才能驾驭"的设计假设**。用 DeepSeek V4 出问题，**不全是模型能力问题，很大程度是 skill 自身的设计复杂度和内部矛盾导致的**。

核心矛盾：skill 期望 AI 在单次输出中完成"跨表单关联识别 + 字段类型推断 + 选项值生成 + 填充规则 + 字段说明"等多维度决策，但对弱模型来说这种"并行多维度推理 + 大 JSON 一次性输出"负荷过重，且 skill 内部的参考文件之间存在直接矛盾，会主动误导 AI。

---

## 二、逐问题根因分析

### 问题 1：关联表单字段没有识别

**根因：认知负荷过载 + 缺乏脚手架**

SKILL.md 要求 AI 在一次 override 生成中完成 5 个维度的分析。对每个表单，AI 需要：
1. 扫描所有其他表单名称
2. 逐字段判断是否需要从其他表单选择记录
3. 同时处理数值字段、下拉字段、数据标题、字段状态

> SKILL.md 原文（逐表单分析）：
> ```
> 对每个表单，AI 一次性完成以下所有维度，将结果写入 field-types-override.json
> ```

对一个 10 个表单、每表 15 字段的系统，这意味着 AI 需要在单次输出中同时处理 **150 个字段 × 5 个维度 = 750 个微决策**。弱模型在这种场景下极易遗漏。

**关键问题**：preview 输出虽然列出了所有表单和字段，但**没有给出关联候选提示**。AI 必须自己做跨表单名称匹配——这本质上是程序更擅长的工作。

---

### 问题 2：忘记做填充

**根因：override 格式的可选字段太多，弱模型容易"写了 type + target 就认为完事了"**

> SKILL.md override 配置说明：
> ```json
> {
>   "采购订单": {
>     "供应商": {
>       "rename": "选择供应商",
>       "type": "关联表单",
>       "target": "供应商信息"
>     }
>   }
> }
> ```
> 字段说明：
> - `rename`：可选
> - `type`：设为"关联表单"
> - `target`：目标表单名称
> - `fillRules`：可选，不写则脚本自动从目标表单推导
> - `filledFields`：可选，不写则脚本自动从目标表单推导

虽然 v1.28.0 的自动推导机制（脚本 `autoGenerateFillRules` / `autoGenerateFilledFields`）已经在脚本层面做了兜底，但 **SKILL.md 里花了大量篇幅讲"何时需要手动写 fillRules/filledFields"**，这段内容反而会让弱模型困惑——它不确定自己处于哪种情况，于是干脆不写，指望脚本兜底。但脚本兜底依赖 `formFieldMap[override.target]` 正确匹配，如果 AI 把 target 表单名写错了（拼写不一致），整个自动推导就静默失败了。

---

### 问题 3：字段类型不对

**根因：类型推断逻辑分散在三处，且有矛盾**

类型推断逻辑存在于：
1. `excel_to_form.js` 的 `mapFieldType()`（脚本兜底）
2. `AI字段类型推断提示词.md`（AI 参考）
3. `field-type-guide.md`（AI 参考）

三者的关键词列表**不完全一致**：

| 关键词 | 脚本 mapFieldType | AI提示词.md | field-type-guide.md |
|-------|:-:|:-:|:-:|
| 价（单独） | ✅ | ❌（只有"价格"） | ✅ |
| 成本 | ✅ | ✅ | ❌ |
| 余额 | ✅ | ✅ | ✅ |
| 额度 | ✅ | ✅ | ❌ |
| 税额 | ✅ | ✅ | ❌ |
| 预算 | ✅ | ✅ | ❌ |
| 年限 | ✅ | ❌ | ❌ |
| 折扣 | ✅ | ✅ | ✅ |

弱模型看到不一致的关键词表，可能会对脚本已能正确推断的字段"画蛇添足"地写 override，或者反过来，对脚本推断不了的字段也不写 override。

---

### 问题 4：说明忘记写

**根因：`generateFieldDescription` 的逻辑分支太多，AI 无法预判脚本最终输出什么**

`generateFieldDescription` 函数有 **7 层优先级判断**：
1. 强制说明（由 `applyOverrides` 设置的 `_forceDescription`）
2. 当前表单 AI 覆盖配置中的选项
3. 从所有表单的 override 中查找（v1.32.0）
4. `typeHint` 包含关联/填充/公式/小数/单位等标记
5. `isOptions` 字段的选项
6. 流水号推断
7. 数值、下拉等其他推断分支

AI 无法预判最终输出是什么，于是可能会出现：
- AI 认为"脚本会自动推断数值说明"就没写 → 脚本的 `mapFieldType` 没识别出该字段是数值 → 说明变成 `-`
- AI 写了 `description` → 但被 `_forceDescription` 逻辑覆盖了

---

### 问题 5：执行时长 7-15 分钟

**根因：不是脚本慢，是 AI 的"思考 + 生成 + 校验循环"慢**

时间分解估算：

| 环节 | 耗时估算 | 说明 |
|------|---------|------|
| 读取 SKILL.md（410行） | 10-20s | 弱模型需要更多时间处理长 prompt |
| 运行 preview 脚本 | 2-5s | 很快 |
| AI 生成 override JSON | 3-8min | **最大瓶颈**：一次性输出大 JSON |
| 运行生成脚本 | 2-5s | 很快 |
| 运行 6 个校验脚本 | 10-30s | 串行执行 |
| 校验失败 → 修改 → 重新生成循环 | 2-5min | **第二大瓶颈** |

> SKILL.md 校验环节要求串行执行 6 个校验脚本：
> ```bash
> node scripts/ai-validator.js check-after-write <字段清单路径>
> node scripts/ai-validator.js check-duplicate-fields <字段清单路径>
> node scripts/ai-validator.js check-association-fields <字段清单路径>
> node scripts/ai-validator.js check-fill-targets <字段清单路径>
> node scripts/ai-validator.js check-readonly-fields <字段清单路径>
> node scripts/ai-validator.js check-serial-prefixes <字段清单路径>
> ```

6 个校验脚本串行执行，每个都要启动 Node.js 进程。如果弱模型第一次生成的 override 有问题（很常见），就会进入 **"改 override → 重新生成 → 重新校验"** 的循环，每轮 3-5 分钟，两轮就 10 分钟了。

---

## 三、发现的硬伤问题

### 硬伤 1：参考文件与 SKILL.md 直接矛盾

`AI字段类型推断提示词.md` 的"默认选项"部分和示例输出中，明确允许使用占位数据：

> AI字段类型推断提示词.md：
> ```
> ## 默认选项
> 不要套用行业选项。只有以下通用占位可以使用：
> - 状态：启用/停用
> - 分类/类别：类别1/类别2/类别3
> - 单位：个/件/套/其他
> ```
> 示例输出：
> ```json
> {
>   "基础资料": {
>     "分类": {
>       "type": "下拉单选",
>       "options": ["类别1", "类别2", "类别3"]
>     }
> ```

但 SKILL.md v1.32.0 明确禁止：

> SKILL.md：
> ```
> ❌ 【极其重要·v1.32.0】禁止使用占位数据作为任何字段的选项值，
>    包括但不限于"选项1/选项2/选项3"、"类别1/类别2/类别3"、"类型1/类型2/类型3"等。
> ```

**弱模型读参考文件会被直接误导，生成 SKILL.md 禁止的内容。**

---

### 硬伤 2：`parse_excel_full.js` 是 448 行死代码

`parse_excel_full.js` 是一个完全独立的旧版脚本，它：
- 用完全不同的解析方式（读单元格内的 JavaScript 代码字符串）
- 有自己重复的 `parseField`、`inferFieldType`、`validateFieldType` 等函数
- 硬编码 `"项目管理系统"` 和 `"1.0.0"`
- 仍然包含 `"类别1/类别2/类别3"` 等旧模式

这个文件没有被 SKILL.md 引用，没有被 `excel_to_form.js` require，纯属历史遗留。但它的存在会**让弱模型在浏览 scripts 目录时产生困惑**，不知道该用哪个脚本。

---

### 硬伤 3：引用了不存在的模板文件

SKILL.md 专属硬规则 4 要求输出与 `flow-to-form/references/字段清单模板.md` 一致：

> SKILL.md：
> ```
> 4. 【强制】脚本输出必须与 flow-to-form 标准模板一致 —
>    excel_to_form.js 的 generateFieldList 函数必须参照
>    flow-to-form/references/字段清单模板.md，确保包含以下结构元素：
>    - ## 📋 字段清单使用说明（前置说明，由 getFieldListUsageGuide() 生成）
>    - **数据标题：XXX**（每个表单必须有，由 inferDataTitle() 推断）
> ```

但 `flow-to-form/references/` 目录是**空的**（0 B），没有 `字段清单模板.md`。而且 `excel_to_form.js` 里也没有 `getFieldListUsageGuide()` 函数（说明内容是直接内联在 `generateFieldListMarkdown` 里的）。这条规则是过时的悬空引用。

---

### 硬伤 4：SKILL.md 版本日志占用大量篇幅

SKILL.md 末尾有版本更新日志，占了约 15 行。这对 AI 执行任务**没有任何帮助**，反而稀释了关键规则的注意力。弱模型容易把注意力分散到这些历史变更说明上。

---

### 硬伤 5：禁止事项多达 13 条

SKILL.md 中的禁止事项列表：

1. 禁止修改、覆盖、删除用户的源Excel文件
2. 禁止修改用户已填写的字段定义
3. 禁止在流程表单中手动添加审批字段
4. 禁止将流水号字段设为只读
5. 禁止将系统字段设为必填
6. 禁止遗漏子表字段解析
7. 禁止在Skill中直接处理Excel二进制文件
8. 禁止忽略Excel编码问题
9. 禁止将临时文件写入用户源文件目录
10. 禁止硬编码任何特定行业的字段知识库
11. 禁止在未添加被填充字段的情况下标注带填充规则的关联表单
12. 禁止脚本自动生成业务语义被填充字段
13. 禁止AI无必要地重写已正确内容
14. 禁止使用占位数据作为任何字段的选项值

其中至少 3 条是给脚本看的（不是给 AI 看的），比如"禁止脚本自动生成业务语义被填充字段"——AI 无法控制脚本行为，这条对 AI 来说是噪音。13+ 条禁止事项对弱模型来说太多了，容易"记不住第 11 条"。

## 四、优化空间总结

| 优化方向 | 影响面 | 难度 | 预期收益 |
|---------|-------|------|---------|
| **A. 修复 `AI字段类型推断提示词.md` 与 SKILL.md 的矛盾** | 消除选项值占位数据问题 | 低 | 高 |
| **B. 删除 `parse_excel_full.js` 死代码** | 减少目录浏览困惑 | 低 | 中 |
| **C. 删除 SKILL.md 版本日志和悬空引用** | 减少 prompt 长度和噪音 | 低 | 中 |
| **D. preview 增加"关联候选"和"建议类型"提示** | 把跨表单匹配交给脚本，减轻 AI 负担 | 中 | **极高** |
| **E. 脚本预生成 draft override，AI 只做审核修正** | 从"零开始生成"变为"审核修正" | 中高 | **极高** |
| **F. 合并 6 个校验脚本为 1 个** | 减少校验环节耗时 | 中 | 高 |
| **G. 精简禁止事项到 5-6 条核心规则** | 降低弱模型认知负荷 | 低 | 中 |
| **H. 把 5 维度分析改为分步引导（先关联，再数值，再下拉）** | 降低单次推理复杂度 | 中 | 高 |
| **I. SKILL.md 结构重组：执行优先级排序** | 弱模型更容易抓住重点 | 低 | 中 |

---

## 五、核心结论

**不全是 AI 模型能力的问题。** 这个 skill 的设计假设是"强模型能一次性完成 750 个微决策并输出完美 JSON"，这在 GPT-4 / Claude 级别模型上可能可行，但对 DeepSeek V4 这个级别来说负荷过重。

具体来说：
1. **关联字段遗漏** → 根因是跨表单名称匹配应该由脚本预处理，而非让 AI 全凭记忆
2. **忘记填充** → 根因是 override 格式可选字段太多 + 自动推导依赖 target 名精确匹配
3. **字段类型不对** → 根因是三处关键词表不一致 + AI 无法预判脚本最终输出
4. **说明忘记写** → 根因是 `generateFieldDescription` 的 7 层优先级判断太复杂
5. **执行慢** → 根因是大 JSON 一次性生成 + 校验失败循环，不是脚本本身慢

**最大的优化杠杆点是 D + E**：让脚本承担更多确定性工作（关联候选提示、建议类型、草稿 override），把 AI 的角色从"零开始生成"降级为"审核修正"，这样弱模型也能可靠执行。
