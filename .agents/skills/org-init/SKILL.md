# 组织初始化 (org-init)

## 功能概述

自动从宜搭平台获取以下信息并同步到本地配置：
1. **组织信息** - 组织名称、域名等
2. **应用列表** - 应用名称、应用 ID (appId)、应用类型

## 工作流程

### 1. 登录宜搭平台
- **打开浏览器**，访问宜搭登录页面
- **提示用户进行授权**：点击头像或扫码登录
- **选择组织**：如果用户有多个组织，会显示组织选择页面，等待用户手动选择
- **保存登录态**：保存 cookies、base_url、corpId 等信息到 `.cookies.json`

### 2. 访问宜搭「我的应用」页面
- 使用登录后的 baseUrl 访问：`https://{domain}/myApp`
- 等待页面完全加载

### 3. 提取应用信息
- 使用选择器 `.app-card, [class*="MyCreateAppCard"]` 查找应用卡片
- 从卡片中提取：
  - **应用名称** - 从标题元素获取
  - **应用 ID** - 从链接的 `href` 属性中提取 `APP_[A-Z0-9]+` 模式

### 4. 更新配置文件
- 读取当前工作目录的「组织及应用信息.md」
- 如果不存在，使用登录态信息创建默认配置文件
- 匹配应用名称，更新对应的 appId 列
- 如果找不到应用 ID，写入「请手动补充」

## 输出格式

更新后的「组织及应用信息.md」文件示例：

```markdown
## 应用列表

| 序号 | 应用名称 | 应用 ID (appId) | 应用类型 | 备注 |
|------|----------|----------------|----------|------|
| 1 | 叶秋功能演示 | APP_UUG8L7816Z4WOKB5FIPE | 普通应用 |  |
| 2 | 任务管理 | APP_ABC123DEF456 | 普通应用 |  |
| 3 | 测试应用 | 请手动补充 | 普通应用 |  |
```

## 错误处理

| 场景 | 处理方式 |
|------|----------|
| 未登录 | 提示用户重新运行脚本进行登录 |
| 页面加载失败 | 重试 3 次，每次间隔 5 秒 |
| 找不到应用卡片 | 输出警告，继续处理其他应用 |
| 提取不到应用 ID | 在表格中写入「请手动补充」 |
| 配置文件不存在 | 创建默认配置文件模板 |

## 组织信息获取策略（双重保险）

为了确保能获取到准确有效的组织信息，本 skill 采用**三重保险策略**：

### 第1重保险：组织设置页面
- **访问地址**: `{baseUrl}/platformManage/basicInfo`
- **获取信息**: 组织名称、Corp ID
- **可靠性**: ⭐⭐⭐⭐⭐ 最高
- **原理**: 直接访问宜搭的组织基本信息页面，从页面文本中提取组织名称和 Corp ID

### 第2重保险：工作台页面
- **访问地址**: `{baseUrl}/workPlatform`
- **获取信息**: 组织名称
- **可靠性**: ⭐⭐⭐⭐
- **原理**: 从工作台页面右上角的用户/组织信息区域提取组织名称

### 第3重保险：当前页面提取
- **获取信息**: 组织名称
- **可靠性**: ⭐⭐⭐
- **原理**: 从当前页面的标题或特定元素中提取组织名称

### Corp ID 获取策略
1. **优先从组织设置页面获取**
2. **如果获取失败或值为 "0"，从 Cookie 中获取**（Cookie 中的 `corp_id` 或 `tianshu_corp_id`）
3. **确保获取到有效的 Corp ID**

## 已知问题与解决方案

### 问题：组织信息错误（组织名称显示"首页"、域名显示"www.aliwork.com"）

#### 问题现象
配置文件中的组织信息全部错误：
- 组织名称：首页
- 域名前缀：www
- 完整域名：https://www.aliwork.com
- corpId：（空）

#### 问题根源
1. **登录时未正确选择组织**：用户在组织选择页面没有点击选择具体的组织，导致浏览器仍停留在 `www.aliwork.com` 域名
2. **base_url 提取逻辑缺陷**：脚本从页面 URL 提取 `base_url` 时，没有验证其有效性，直接将 `www.aliwork.com` 保存为组织域名
3. **Cookie 复用问题**：错误的 `base_url` 被保存到 `.cookies.json`，后续运行脚本时直接使用了这个错误的配置

#### 解决方案（已在 v1.0.10 中实现）
1. **新增 URL 验证函数** `isValidOrgBaseUrl()`：
   - 检查 URL 是否包含有效的组织标识（排除 `www`、`login`、`auth` 等前缀）
   - 确保 URL 格式为 `xxx.aliwork.com` 而不是 `www.aliwork.com`

2. **新增 base_url 提取函数** `extractValidBaseUrl()`：
   - 尝试多种方式获取有效的组织域名
   - 如果当前页面 URL 无效，尝试从页面中的应用链接提取
   - 如果仍无法获取，访问 `/myApp` 页面再次尝试

3. **增强 Cookie 验证逻辑**：
   - 在验证已有 Cookie 时，首先检查保存的 `base_url` 是否有效
   - 如果 `base_url` 无效（如 `www.aliwork.com`），直接判定为无效，强制重新登录

4. **登录流程增强**：
   - 如果无法提取到有效的 `base_url`，抛出错误提示用户确保已正确选择组织
   - 不再使用默认值 `https://www.aliwork.com` 作为 fallback

#### 预防措施
- 登录时务必在组织选择页面**点击选择**您的组织，不要停留在默认页面
- 如果看到组织信息显示"首页"，说明登录流程有问题，需要删除 `.cookies.json` 重新登录

### 问题：组织名称被覆盖为域名前缀（如组织名称和域名前缀都是"qfhefh"）

#### 问题现象
运行组织初始化后，「组织及应用信息.md」中原本正确的组织名称被覆盖，变得和域名前缀一模一样。

#### 问题根源
1. **login-manager.js 兜底逻辑缺陷**：三重保险都没抓到组织名称时（页面结构变化或加载超时都会导致），旧版代码直接用域名前缀当作组织名称写进登录态（`corpName: corpName || domainPrefix`）
2. **init-org.js 保护逻辑绕过**：`updateOrgInfo` 只把空值和"未知"视为无效，域名前缀看起来是个"正常值"，于是把原文件中正确的组织名称覆盖掉了

#### 解决方案（已在 v1.5.1 中实现）
1. **源头修复**（login-manager.js）：抓取失败时不再用域名前缀兜底，改为记录"未知"并输出警告
2. **下游防护**（init-org.js）：`updateOrgInfo` 和 `createDefaultOrgConfigFile` 将"corpName 等于域名前缀"也视为无效值，优先保留原文件中的组织名称（兼容旧版 `.cookies.json` 残留的污染值）

#### 设计原则（防再发）
- **抓取失败就明确标记为失败（"未知"），绝不用看似合理的推导值（域名前缀、页面标题等）伪装成真实数据**，否则下游无法区分真假，会覆盖正确的已有配置
- 更新配置文件时，对不确定的新值一律"保留原值优先"

#### 预防措施
- 如发现组织名称显示为"未知"，说明本次抓取失败但原值已丢失，手动在「组织及应用信息.md」中补充真实组织名称即可，后续初始化不会再覆盖它

### 问题：配置文件字段替换静默失败（日志显示已更新但文件内容未变）

#### 问题现象
脚本日志输出"组织信息已更新"并展示新值，但「组织及应用信息.md」中部分字段（组织名称、域名前缀、完整域名等）实际没有变化。

#### 问题根源
旧版替换正则写死了单空格（如 `/\| 组织名称 \|/`），而编辑器的 Markdown 格式化会把表格对齐填充成多空格（`| 组织名称   |`），导致 `content.replace` 匹配不到、静默跳过，日志却照常打印"已更新"。

#### 解决方案（已在 v1.5.2 中实现）
1. 所有表格字段替换改用通用函数 `replaceTableField`，正则容忍字段名前后任意空格（`\|\s*字段名\s*\|`）
2. 匹配不到字段行时输出明确警告，不再静默失败

#### 设计原则（防再发）
- 对 Markdown 表格做正则替换时，**必须容忍对齐填充的任意空格**（用户保存文件时格式化器随时可能重新对齐表格）
- 任何"替换/写入"操作都要校验是否真正命中，失败必须输出警告，禁止静默失败后照常报"成功"

### 问题：组织名称抓取长期失败（networkidle 超时 + 页面结构假设过时）

#### 问题现象
三重保险几乎总是抓不到组织名称（旧版被域名前缀兜底掩盖，v1.5.1 后表现为持续"未知"），删 Cookie 重新登录也无效。

#### 问题根源（探针脚本实测确认）
1. **`waitUntil: 'networkidle'` 永远等不到**：宜搭页面持续有后台请求，组织设置页 `page.goto` 30 秒超时抛异常被 catch 吞掉，提取代码根本没执行。"以前偶尔成功"就是偶尔网络恰好安静
2. **提取模式过时**：页面实际是标签与值分两行（`组织名称\n云途数字技术`），旧正则只匹配同行冒号格式；工作台标题分隔符是 `|` 不是 `-`，且页面无 `header` 元素，第二/三重保险也全部失效
3. **Cookie 有效时跳过抓取**：抓取只在重新登录时执行，登录态里的错误组织名称会一直沿用

#### 解决方案（已在 v1.5.3 中实现）
1. 新增 `fetchOrgInfoFromSettings()`：`domcontentloaded` + `waitForFunction` 等待"组织名称"文本渲染，按行提取（标签行的下一行即为值），兼容旧版同行冒号格式
2. Cookie 有效的快速路径新增**补抓机制**：登录态里组织名称缺失/为"未知"/等于域名前缀时，自动补抓一次并回写 `.cookies.json`，无需重新登录
3. 第二重保险的 `networkidle` 同步改为 `domcontentloaded`

#### 设计原则（防再发）
- **宜搭页面禁用 `waitUntil: 'networkidle'`**（后台请求不断，必超时），统一用 `domcontentloaded` + 等待目标文本/元素出现
- 抓取逻辑失效时，先用探针脚本 dump 真实页面文本再修正则，不要凭想象叠加匹配模式

## 版本历史

- v1.5.6 (2026-08-17) - **修复**：本地页面"刷新应用信息/刷新登录态"从两三秒变成十几二十秒，且刷新弹窗无日志输出
  - login-manager.js v1.0.16：Cookie 验证的 `waitUntil` 由 `networkidle` 改为 `domcontentloaded`（timeout 30s→15s）。**根因**：宜搭 SPA 持续后台请求，`networkidle` 永远等不到空闲，每次卡满超时才继续
  - init-org.js V1.5.1：(1) 由 sync_server 触发时（`YIDA_NO_OPEN_PORTAL=1`）跳过 `startServicesAndOpenPortal()`/`registerAutoStart()`，避免每次"刷新应用信息"额外弹出浏览器新窗口；(2) 配合 sync_server `/refresh-org-apps` 改为 SSE 流式，把同步过程日志逐条推给前端弹窗，让用户看到实时运行状态
  - **防复发**：宜搭页面禁用 `networkidle`；批量长任务（刷新应用信息等）用 SSE（EventSource）流式推送日志缓存，避免无反馈"假死"感
- v1.5.5 (2026-08-11) - **修复**：Cookie 验证误判失效导致每次刷新应用信息都弹出登录页面
  - login-manager.js：ensureLogin 验证方式改为与 api-client/login_manager.js 的 fetchPageInfo 一致（networkidle 超时不报错 → 检查重定向 → 循环提取 csrf_token），不再依赖 SPA 渲染完成后的页面文本
- v1.5.4 (2026-08-05) - **修复**：浏览器被关闭后脚本空转等待的问题
  - login-manager.js：新增 isBrowserClosedError() 检测浏览器关闭错误，handleLoginFlow 返回 browserClosed 标志
  - ensureLogin：检测到浏览器关闭后自动重新打开浏览器并重试登录，避免脚本空转10分钟后才退出
- v1.5.3 (2026-07-28) - **根因修复**：组织名称抓取长期失败
  - login-manager.js：新增 fetchOrgInfoFromSettings，弃用 networkidle（宜搭页面后台请求不断必超时），改用 domcontentloaded + 等待文本渲染，按"标签行下一行"提取组织名称/Corp ID
  - login-manager.js：Cookie 有效时若登录态组织名称无效，自动补抓并回写，无需重新登录
