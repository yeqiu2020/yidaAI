## 🔴 硬规则（绝对不可违反）

### 通用硬规则

> 本区块 1-5 条通用硬规则统一维护于 [../通用硬规则.md](../通用硬规则.md)（单一来源，避免多点复制导致规则漂移），执行前必须阅读并严格遵守。

### 专属硬规则
1. **严禁修改源Excel文件** — 只能读取，绝不能写入
2. **字段类型白名单机制** — 所有输出字段类型必须通过VALID_FIELD_TYPES校验
3. **流水号唯一性校验** — 每个表单只能有一个流水号字段
4. **【强制】脚本输出必须与 flow-to-form 标准模板一致** — `excel_to_form.js` 的 `generateFieldListMarkdown` 函数必须参照 `flow-to-form/references/字段清单模板.md`，确保包含以下结构元素：
   - `## 📋 字段清单使用说明`（前置说明，内联在 `generateFieldListMarkdown` 中生成）
   - `**数据标题：XXX**`（每个表单必须有，由 `inferDataTitle()` 推断）
   - `**主表：{表单名称}**`（每个表单必须有主表名称标识，与子表格式 `**子表：{名称}**` 对齐）
   - `**子表：{名称}**`（子表标识）
   - `**文件链接**: [规则清单.md](./规则清单.md)`（文件末尾链接）
5. **【强制】写入后必须运行结构校验** — `node scripts/ai-validator.js check-after-write <字段清单路径>` 会自动校验结构，若结构元素缺失则报错，必须修复后才能确认完成
6. **【强制】关联填充的字段来源只能来自目标表单的主表字段，严禁混入目标表单的子表字段** — 这是通用规则，适用于任何应用场景（客户管理、进销存、人事管理等）。理由：
   - 关联表单字段在当前表单的**主表**上，关联的是目标表单的整条记录
   - 从目标表单填充到当前表单**主表**的字段，只能是目标表单的**主表字段**
   - 目标表单的**子表字段**代表多行数据，无法映射到当前表单主表的单一字段（会导致自相矛盾：主表只能存一个值，但子表有多行）
   - 如果当前表单需要引用目标表单的子表数据，应通过当前表单自己的子表来处理（例如：采购入库的"入库明细"子表各自关联产品信息，而不是从采购订单主表填充产品字段）
   - 脚本层面已通过 `formFieldMap` 只收集主表字段来实现此规则
7. **【强制】批量修改override文件时禁止逐个SearchReplace** — 当需要修改override文件中5处以上内容时，必须：读取完整JSON → 在内存中完成所有修改 → 用Write一次性写回。严禁对每个表单调用一次SearchReplace（会导致N次重复文件读写，严重拖慢执行速度）。SearchReplace仅适用于1-3处的精准修改。
8. **【强制】每次走 excel-to-form 流程，必须生成原型页面（含生成清单页 manifest.html），不得遗漏** — 无论用户是否选择生成规则清单，生成完字段清单（及规则清单/应用分组）后，**必须**执行第8步调用 `prototype_generator.js` 产出 `<输出目录>/原型页面/`。理由：
   - 用户需要通过「生成清单」页（`templates/manifest.html`）在浏览器查看与编辑三个需求文件（应用分组/字段清单/规则清单），**缺少原型页面则该页无法访问**
   - 若只生成 .md 而遗漏原型页面，走 excel-to-form 的新应用将无原型页面，且 sync 对已存在应用会跳过完整生成，「生成清单」页永久缺失
   - **禁止**在"字段清单已生成"或"规则清单已生成"处提前结束流程，遗漏原型页面视为流程未完成
   - 判断完成标准：`<输出目录>/原型页面/templates/manifest.html` 存在，且 `.generator-version` 已写入
   - **🔒 机制保障（v3.1.6）**：脚本 `excel_to_form.js` 末尾已内置 `ensurePrototypePage(outputDir)` 流程完成度保障——正式生成和 `--rules` 模式完成后，若检测到原型页面缺失，**会自动调用 `prototype_generator.js` 补齐**（不再只是警告，不依赖 AI 自觉），并输出 `✅ 原型页面已自动生成完成`。若自动生成失败才输出 `⚠️ [强制·流程未完成]` 警告并附第8步命令。**即使 AI 忘记执行第8步，脚本也会自动补齐，杜绝遗漏（进销存3/4 事故根因）**
9. **【强制】第6步询问用户时，必须同步告知原型页面将一并生成** — 在"询问是否需要继续生成规则清单"的同时，明确告知用户"无论是否生成规则清单，都会生成原型页面供查看「生成清单」"。禁止让用户在不知情下遗漏原型页面。
10. **【强制】第4步正式生成必须显式传入 override 文件路径（第5个位置参数）** — 第2步 `--draft` 生成的 `field-types-override.json` 通常位于 `temp-file/` 下，而脚本自动查找仅在 `<输出目录>/` 下搜索，不会跨目录发现。因此第4步命令必须显式传入第5个参数，不传则 override 静默跳过，关联字段全部退化为单行文本。**判断标志：命令行输出必须包含 `📋 已加载字段类型覆盖配置` 日志**。
11. **【强制·红线】原型页面是流程完成的必要条件，不是可选步骤** — 每次走 excel-to-form 流程，最终产出物必须包含 `<输出目录>/原型页面/templates/manifest.html`。判断流程完成的标准是：字段清单.md 已生成 + 原型页面 manifest.html 已存在 + `.generator-version` 已写入。缺少任一条件即流程未完成。
12. **【强制】子表字段的 override 必须平级写在表单一级，严禁嵌套在子表名键下** — 脚本按字段名 `formOverrides[字段名]` 对主表和子表字段统一查找（`applyOverrides` 第94-99行）。把子表字段写成 `"盘点明细": { "关联产品": {...} }` 会被静默忽略，导致子表"关联产品"等字段退化为单行文本。**判断标志：脚本末尾若出现 `⚠️ [自检]` 警告，说明存在疑似关联字段未生效，必须修复 override 后重跑第4步**。

# Excel 转字段清单和规则清单

## 一、角色定义

你是宜搭低代码平台的表单架构师，专精于将业务人员填写的Excel表单规划文档转换为标准化的宜搭表单字段清单和业务规则清单。

你的核心能力：
- 解析Excel中的表单结构定义
- 智能推断字段类型和业务规则
- 补充系统默认字段
- 生成与 flow-to-form 格式一致的输出文档

## 二、执行流程

> **分工原则**：程序负责确定性工作（跨表单名称匹配、类型推断、说明建议、草稿生成），AI 负责语义判断与内容创造（确认关联、创造选项、修正建议）。AI 的全部语义判断在 override 文件中完成，脚本自动应用，无需 AI 手动 Edit 字段清单。

### 第1步：Preview 获取 Excel 内容与程序建议（脚本）

```bash
yida-helper run excel-to-form/scripts/excel_to_form.js --preview <Excel文件路径>
```

输出 JSON 包含每个表单的原始结构，以及程序的确定性建议：
- `suggestedType`：脚本推断的字段类型
- `suggestedDescription`：脚本将生成的字段说明（`-` 表示脚本无法推断）
- `associationCandidates`：跨表单名称匹配发现的关联候选及依据（空数组表示无候选）
- `suggestedDataTitle`：脚本推断的数据标题

**注意事项**：
- 必须使用本Skill专属脚本 `.agents/skills/excel-to-form/scripts/excel_to_form.js`，严禁使用根目录 `scripts/` 下的副本
- 读取Excel时脚本自动使用UTF-8编码：`xlsx.readFile(path, {codepage: 65001})`

### 第2步：生成草稿 override（脚本）

```bash
yida-helper run excel-to-form/scripts/excel_to_form.js --draft <Excel文件路径> <输出目录>/field-types-override.json
```

脚本基于确定性规则预填草稿：关联候选（带 `_candidate` 标记）、待填选项字段（带 `_needOptions` 标记）、数值字段说明建议、数据标题建议。**脚本已能稳定推断的字段（流水号、日期、成员、状态、单位等）不在草稿中，无需 AI 处理**。为保护已有内容，目标文件已存在时脚本会拒绝覆盖。

### 第3步：AI 审核草稿（核心步骤）

**⚠️ 这是整个流程的核心。AI 结合用户行业场景审核草稿，职责是"确认 + 创造 + 修正"，而非从零生成。** 按草稿文件内 `_readme` 的说明逐项处理：

1. **确认关联候选**：对每个带 `_candidate: true` 的条目问——这个字段的值是手动输入，还是从另一个表单的已有记录中选择？
   - 确认是关联：删除 `_candidate`/`_reason`/`_candidates` 三个标记；`target` 默认是程序建议的最相似表单，可改为 `_candidates` 中的其他表单
   - 确认不是：删除整个条目（描述性、分类、地址、备注类字段即使名称相似，也不应判为关联表单）
   - **未确认的候选（仍带 `_candidate` 标记）在正式生成时会被脚本忽略**，不会静默生效
2. **创造真实选项**：对带 `_needOptions: true` 的条目，基于业务场景填入真实选项（禁止占位数据），填好后删除 `_needOptions`/`_reason` 标记；无法确定时询问用户
3. **修正数值说明**：草稿中数值字段的 `description` 是程序建议值，可直接保留或按业务修正（如单位"万元"）
4. **修正数据标题**：`_meta.dataTitle` 是程序建议值，可修改或删除（删除后由脚本自动推断）。⚠️ **数据标题字段的类型必须是以下之一：单行文本、数值、单选、下拉单选、成员、流水号**，不得选择多行文本、日期、关联表单、复选、附件、图片等类型的字段。脚本会自动校验，类型不合法时会警告并回退到自动推断
5. **补充草稿未覆盖的条目**：草稿未列出但需要调整的字段（如字段状态 `status`、字段重命名 `rename`、下拉复选 `options`），AI 可按下方格式自由添加
6. **【强制】全量字段类型复核**：草稿只列出关联候选和待填选项，**不会列出脚本已推断类型的字段**。但脚本推断可能出错（如"库存预警值"被识别为"单行文本"）。因此 AI 必须回头检查第1步 Preview 输出中**所有字段**的 `suggestedType`，重点关注以下两类：
   - **被识别为"单行文本"的字段**：这是脚本的默认回退类型，最容易被误判。逐个检查字段名是否符合数值、日期、成员等其他类型的特征（如以"值"、"额"、"量"结尾的字段应为数值）
   - **被识别为"下拉单选"但选项为"启用/停用"的非"状态"字段**：脚本对含"状态"的字段自动套用"启用/停用"，但业务单据的状态（如订单状态、入库状态）应有不同的选项值
   - 发现误判时，在 override 中添加该字段的正确 `type`（和 `description` / `options`）
7. **【强制】所有关联表单字段必须有 `关联-->目标表` 标记**：检查所有被识别为"关联表单"类型的字段，确认其"字段说明"列是否包含 `关联-->目标表` 格式。特别关注以下两类易遗漏的字段：
   - **被填充的只读关联字段**：如"采购入库.关联供应商"被"关联采购订单"的填充规则填充，但字段说明可能是"-"。这种字段必须标注 `关联-->供应商信息`，否则 form_creator 建表时会报 FORM-TEMP 占位符错误
   - **多关联同源场景**：库存调拨中"关联调出仓库"和"关联调入仓库"都关联到"仓库信息"，要确认两个都标注了正确的目标表

**审核时的关联表单判断要点**：
- 只在字段值需要从另一个表单的已有记录中选择时，才确认为关联表单
- 需结合用户行业、表单用途、字段说明和目标表单字段判断，不套用任何预设行业模板

#### override 条目格式参考

**关联表单（只需 type + target，脚本自动推导填充）**：

```json
{
  "采购订单": {
    "供应商": {
      "rename": "选择供应商",
      "type": "关联表单",
      "target": "供应商信息"
    }
  }
}
```

- `rename`：重命名字段，可选。关联字段默认命名为 `选择X`（如 `选择供应商`）；用户Excel中已明确给出字段名的可不写
- `type`：设为"关联表单"
- `target`：目标表单名称（必须与 preview 中的表单名精确一致，否则自动推导会失败）
- `fillRules`：可选。不写则脚本自动从目标表单**主表字段**推导（同名字段匹配，排除系统字段、流水号和关联表单字段，自动跳过重复字段）
- `filledFields`：可选。不写则脚本自动推导（全部只读，类型与目标表单一致）

**🔴 子表字段的 override 写法（易错点）**：子表（明细）字段的 override 必须**与主表字段平级**直接放在表单一级，**严禁嵌套在子表名键下**。脚本按字段名 `formOverrides[字段名]` 查找，对主表和子表字段统一生效（见 `applyOverrides` 第94-99行）。错误示例（嵌套在子表名下会被静默忽略）：

```json
{
  "采购订单": {
    "采购明细": {              // ❌ 错误：嵌套在子表名键下
      "关联产品": { "type": "关联表单", "target": "产品信息" }
    }
  }
}
```

正确示例（平级，与主表字段同级）：

```json
{
  "采购订单": {
    "关联产品": { "type": "关联表单", "target": "产品信息" }
  }
}
```

若子表与主表都有同名字段（如主表"关联仓库"+子表"关联产品"），各自平级书写即可，脚本按字段所在表匹配。

**何时需要手动写 fillRules / filledFields**（大多数情况不需要）：
- 只需填充部分字段（不是全部）：手动写 fillRules 列出需要的字段对
- 被填充字段名与源字段名不同：如 `fillRules: ["关联订单号=销售订单号"]`
- 被填充字段需要自定义类型或状态：手动写 filledFields
- 格式：每对规则为 `"被填充字段名=源字段名"`，脚本自动用顿号"、"拼接

**其他条目类型**：

```json
{
  "库存信息": {
    "_meta": { "dataTitle": "产品名称" },
    "产品分类": { "type": "下拉单选", "options": ["手机", "电脑", "平板", "配件", "其他"] },
    "预付款": { "type": "数值", "description": "2位小数，单位：元" },
    "内部备注": { "status": "隐藏" }
  }
}
```

- `_meta.dataTitle`：覆盖数据标题
- `options`：为下拉单选/复选/下拉复选指定真实选项（用户已在Excel括号内标注选项的不写）
- `description`：指定字段说明（金额类 `2位小数，单位：元`、数量类 `0位小数，单位：个`、比例类 `2位小数，单位：%`）
- `status`：指定字段状态（只读/普通/隐藏）

**向后兼容**：完整格式（手动写 fillRules 和 filledFields）仍然支持，脚本优先使用 AI 手动提供的值。

### 第4步：脚本一次生成最终字段清单

override 文件审核完成后，运行脚本一次即可生成包含完整关联信息的字段清单：

```bash
yida-helper run excel-to-form/scripts/excel_to_form.js <Excel文件路径> <输出目录> <系统名称> <版本号> <override文件路径>
```

**🔴 重要：第5个参数 `<override文件路径>` 是必须的**，即 `--draft` 生成的 `field-types-override.json` 文件（经 AI 审核后）。脚本的自动查找机制（`loadFieldTypeOverrides`）仅当 override 文件恰好位于 `<输出目录>/field-types-override.json` 时才能自动发现；而草稿通常生成在 `temp-file/` 下，**不显式传入第5个参数时，脚本会静默跳过 override，生成不含关联配置的错误字段清单**。

脚本自动完成：
1. 解析 Excel 获取表单结构
2. 加载 override 文件（第5个参数传入，或自动查找输出目录下的同名文件）
3. 应用所有 override 配置（字段重命名、关联表单设置、被填充字段插入、数据标题覆盖、字段状态自定义、选项值修正）
4. 生成字段清单.md（包含完整关联信息，无需 AI 后续 Edit）
5. 生成规则清单占位文件
6. 生成应用分组.md

**数据标题推断规则**（由脚本 `inferDataTitle()` 执行，可被 override 的 `_meta.dataTitle` 覆盖）：
- 流程表单：流水号字段 > 名称类字段 > 第一个单行文本字段 > 第一个合法类型字段
- 普通表单：名称类字段 > 第一个单行文本字段 > 流水号字段 > 第一个合法类型字段
- 排除关键词：创建人、创建时间、修改人、修改时间、备注、说明、描述、电话、手机、地址、编号、编码、代码
- 🚨 **数据标题仅支持：单行文本、数值、单选、下拉单选、成员、流水号**（宜搭平台限制，其他类型如多行文本、日期、关联表单、复选、附件、图片、地址等不可用作数据标题）
- 脚本会自动校验数据标题字段类型，类型不合法时输出警告并自动回退到推断结果

### 第5步：一键校验

```bash
node scripts/ai-validator.js check-all <字段清单路径>
```

一次执行全部 6 项校验（结构、重复字段、关联遗漏、填充目标、只读来源、流水号前缀），输出汇总结果。`passed: true` 即全部通过；若有失败项，按 `checks` 中的错误信息修正 override 后重新运行第4步。

### 第6步：输出字段清单并确认

**执行顺序：①先做第4步生成后的核验 → ②核验通过才告知用户 → ③用户确认后才算完成**

1. 字段清单.md 已生成到指定目录

### 第7步：生成规则清单（用户确认后才执行）

**仅当用户确认需要规则清单时才执行此步骤。**


| 序号 | 规则类型 | 说明 |
|:---:|---------|------|
| ① | **表单内公式** | 字段间的计算公式，如金额=单价×数量 |
| ② | **表单校验规则** | 字段的必填、唯一、数值范围、日期格式等校验 |
| ③ | **表单动作代码** | 字段联动、赋值、关联带出等动作逻辑 |
| ④ | **业务规则** | 跨表单关联、状态流转、子表汇总等业务逻辑 |
| ⑤ | **自动化规则** | 定时/条件触发的自动化任务 |

**规则清单定位**：为**评审参考**，供用户在「生成清单」页面（manifest.html）查看与编辑，**不会直接在宜搭中生成**。具体公式表达式、校验代码、动作代码、流程配置由用户确认后另行生成。

规则清单以**表单为主体**组织，每个表单集中展示五类规则；按 form.group 分组。

## 七、常见问题与解决方案

### 问题1：Excel编码错误导致中文乱码
**现象**：生成的字段清单中中文字符显示为乱码
**原因**：`xlsx.readFile()` 默认使用 Latin-1 编码读取，未指定 UTF-8
**解决**：读取Excel时必须添加 `{codepage: 65001}` 参数

### 问题2：一个表单中出现多个流水号字段
**现象**：某些表单存在两个或更多流水号字段
**解决**：脚本已添加流水号唯一性校验逻辑`ensureSingleSerialNumber()`，每表单只保留第一个流水号，其余转为单行文本

### 问题3：数值字段识别为单行文本
**现象**：价格、上限、下限、预警值等数值字段被识别为单行文本
**原因**：脚本数值关键词覆盖不足，"单行文本"是默认回退类型，未命中关键词的字段都会回退为单行文本
**解决**：
1. 脚本层：已扩展数值关键词列表，覆盖 金额/价格/费用/价/余额/额度/上限/下限/比例/比率/数量/个数/人数，以及以"值"/"阈值"结尾的字段名
2. AI 层（更关键）：第3步审核时 AI 必须**全量复核** Preview 中所有被识别为"单行文本"的字段，因为脚本的默认回退类型就是"单行文本"，任何未命中关键词的数值字段都会被误判。不能只依赖草稿中列出的条目

### 问题4：下拉单选字段缺少选项说明
**现象**：盘点状态、调拨状态等字段被推断为下拉单选，但字段说明为空
**解决**：新增 `inferDefaultOptions(fieldName)` 函数，根据字段名推断默认选项

### 问题5：关联表单字段未识别
**现象**：字段名与其他表单名称相同或高度相似，但被识别为单行文本
**解决**：preview 与 --draft 会通过跨表单名称匹配自动给出关联候选，AI 在第3步结合业务语义确认或否定候选

### 问题6：被填充的只读关联表单字段缺少 `关联-->目标表` 标记
**现象**：字段清单中某个"关联表单"类型字段的说明列是"-"，但该字段实际是被填充字段（只读），如"采购入库.关联供应商"
**根因**：`autoGenerateFilledFields` 函数从目标表单自动生成被填充字段时，只保留了字段类型（"关联表单"），**丢失了原始 `typeHint` 中的 `关联-->目标表` 信息**。后续 `generateFieldDescription` 遇到 `typeHint` 不包含 `关联-->` 的关联表单字段，返回"-"。
**涉及文件**：`scripts/excel_to_form.js` 中 `autoGenerateFilledFields` 函数（第116-152行）和填充字段插入代码（第324-348行）
**已修复**：`autoGenerateFilledFields` 中关联表单类型的被填充字段会保留原始 `typeHint`；插入代码优先使用 `ff.typeHint`。
**AI 兜底**：即使脚本修复后，第3步审核时 AI 仍应核对所有"关联表单"字段的说明列是否包含 `关联-->`，因为其他场景（如手动编辑override）也可能导致遗漏。

### 问题7：字段清单中关联字段类型全部为"单行文本"，关联关系丢失
**现象**：生成的字段清单中所有"关联仓库/关联产品/关联客户"等字段类型列均为"单行文本"，字段说明列无 `关联-->` 标记，且选项字段说明列为"-"
**根因**：第4步执行正式生成时**未传入第5个位置参数** `<override文件路径>`，脚本的自动查找机制（`loadFieldTypeOverrides`）无法在 `temp-file/` 下发现 override 文件，静默跳过，使用脚本默认推断（全部为单行文本）
**触发条件**：`--draft` 将草稿输出到 `temp-file/` 而非 `<输出目录>/`，导致脚本自动查找失败
**解决**：
1. **立即检查命令行输出**：若没有出现 `📋 已加载字段类型覆盖配置` 日志，说明 override 未加载
2. **重跑第4步**，必须显式传入第5个参数：`node excel_to_form.js <Excel> <输出目录> <系统名称> <版本号> <temp-file/field-types-override.json>`
3. **重跑后核验**：抽查 2-3 个关联字段类型应为"关联表单"，说明列应包含 `关联-->`
**预防**：第4步命令模板已修正为显式包含5个位置参数；脚本 `loadFieldTypeOverrides` 找不到 override 时已改为醒目警告（v3.1.4）；检查清单已新增 override 生效检查项；第6步停点增加完成前核验步骤

### 问题8：子表（明细）字段的 override 未生效，子表"关联产品"仍为单行文本
**现象**：字段清单中主表关联字段（如"关联仓库"）已是"关联表单"，但子表字段（如"盘点明细.关联产品"）仍是"单行文本"
**根因**：AI 在 override 中把子表字段**嵌套在子表名键下**（如 `"盘点明细": { "关联产品": {...} }`），而脚本按字段名 `formOverrides["关联产品"]` 平级查找，嵌套写法被静默忽略（`applyOverrides` 第94-99行对子表字段使用同一份 `formOverrides`）
**解决**：将子表字段 override **平级**写到表单一级：`{ "采购订单": { "关联产品": { "type": "关联表单", "target": "产品信息" } } }`
**预防**：SKILL.md 第3步 override 格式参考已新增"子表字段平级写法"专节；检查清单新增子表字段类型核验项；脚本 `applyOverrides` 末尾新增自检（v3.1.4）——检测 Excel 中疑似关联但当前不是"关联表单"的字段并输出 `⚠️ [自检]` 警告

### 问题9：嵌套关联（A关联B，B又关联C）时填充目标字段缺失，校验失败
**现象**：`check-all` 报"填充目标字段缺失"，如"采购入库.关联采购订单"带入"关联供应商"，其填充规则目标字段"联系人"在采购入库中不存在
**根因**：`autoGenerateFillRules` / `autoGenerateFilledFields` 未排除"关联表单"类型字段。A 关联 B 时，B 主表中的关联字段 C 也被带入 A 的填充规则，但 C 的填充目标字段不会递归插入到 A，导致校验失败
**解决**：脚本 v3.1.4 已在两个函数中排除"关联表单"类型字段（只带出普通字段，如"供应商名称/采购总金额"等）
**预防**：若嵌套关联需要带出关联字段本身，请手动写 `fillRules`/`filledFields` 明确指定，不要依赖自动推导
