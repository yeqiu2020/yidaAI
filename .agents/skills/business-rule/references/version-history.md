# 版本历史（business-rule）

> 本文件由 SKILL.md 下沉而来。当前版本见 [../SKILL.md](../SKILL.md) 顶部。

- **v3.8.0**（2026-08-01，来源子表字段自动逐行迭代机制 + 禁止问子表行数——根因修复）：AI 在配置「采购入库→增加库存」业务规则时：① 错误判断"入库明细有多行，业务关联规则只执行一次无法逐行处理"，引导用户改用集成自动化；② 还向用户询问"子表通常有几条"。**根因**：硬规则21只说"支持子表字段引用"，但未说明引擎如何处理多行子表数据，且未约束"子表行数是多行"这一基本事实，导致 AI 误解并问出愚蠢问题。**修复**：硬规则21 新增条目「来源子表字段自动逐行迭代」，明确说明当公式引用了来源表的子表字段时，宜搭引擎会自动对子表每一行逐行迭代执行整条公式——不需要循环容器、不需要集成自动化；同步新增「禁止问用户"子表有几行"」条目，明确子表必然是多行，引擎自动逐行迭代，行数不影响公式正确性，严禁向用户询问子表行数。同步更新 examples-jinxiaocun.md 和 business-rule-functions.md。**教训**：① 严禁以"子表有多行"为由拒绝执行或引导用户改用集成自动化；② 子表必然是多行，禁止问用户子表行数

- **v3.7.2**（2026-07-28，卡点适用范围修正：UPDATE/DELETE 豁免）：用户指出硬规则7推论的本质——**只要 UPSERT（及 INSERT）的操作对象是目标表单的子表，就需要拆两条规则**（与来源是主表还是子表无关）；而 UPDATE/DELETE 仅作用于匹配到的已有记录，目标不存在时为空操作，无脏数据风险，不需配套规则。修正 `enforceSubTableCompanionGuard`：识别模板顶层函数，UPDATE/DELETE 写目标子表时自动豁免放行（消除 v3.7.1 的过度拦截），UPSERT/INSERT 仍强制要求 companionMainRule。回归验证：UPDATE 写子表→豁免；DELETE 子条件→豁免；UPSERT 写子表无配套→拦截（退出码 2）
- **v3.7.1**（2026-07-28，写目标子表必须配套主表前置规则——机器强制卡点）：`generate-rule-json.js` 新增 `enforceSubTableCompanionGuard`。**背景**：硬规则7推论（写目标子表必须拆两条规则）此前仅为文字说明，实战中被遗漏（单条写子表规则语法合法、宜搭校验通过，但目标记录不存在时插入主表字段全空的脏数据）。**修复**：生成阶段自动检测目标子表字段（value 形如 `FORM-xxx/fieldId` 且 display 含 ≥2 点号），未声明 `companionMainRule` 或其指向文件不存在时拒绝生成（退出码 2）；同步修订硬规则21补充"宜搭校验器只查语法不查业务完整性"例外。已用真实事故配置回归验证（无配套→拦截；纯主表→放行；已配套→放行并提示推送顺序）
- **v3.6.1**（2026-07-27，React 合成事件根因修复）：修复 push-rule.js 流程表单推送时「创建新流程」和「全局设置」按钮点击偶尔失效的问题。**根因**：原代码使用 Playwright 的 `page.click()`（原生鼠标事件）点击宜搭 React 按钮，无法触发 React 合成事件 onClick，导致创建新版本或打开全局设置失败，最终验证找不到规则。**修复**：步骤2「创建新流程」和步骤15验证时的「全局设置」按钮均改为 `page.evaluate(() => el.click())` 调用 DOM 原生 click()；同时放宽全局设置按钮选择器并增加等待时间，确保验证阶段能正确打开面板并读取规则表格。push-rule.js 版本升级为 v2.2.3
- **v3.6.0**（2026-07-25，循环创建根因修复）：修复 push-rule.js 步骤15验证时创建新流程版本导致无限循环的问题。**根因**：旧逻辑（v2.1.9）在发布后点击「创建新流程」生成新草稿来验证规则，但这个草稿会成为孤儿版本，下次运行脚本时被发现后又要删除旧规则→重新添加→发布→验证时又创建草稿，形成 V2→V3→V4→…无限循环。**修复**：验证时不再创建新流程版本，直接在当前已发布页面上验证规则是否存在（先尝试点击「全局设置」查看规则表格，如果不可用则用页面文本匹配兜底）。push-rule.js 版本升级为 v2.2.2
