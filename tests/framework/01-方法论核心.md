# 测试方法论核心（宜搭版）

**版本：** 1.0
**定位：** 宜搭应用测试方法论的顶层设计，所有其他文档的根基
**适用范围：** 用户通过本工具链构建的宜搭应用（表单/流程/报表/自定义页面）

---

## 一、测试目的

AI 驱动的宜搭应用测试的根本目的是：

1. **验证应用质量**：确保 AI 构建的表单、公式、规则、流程稳定可靠
2. **保障业务可用性**：覆盖用户真实业务场景，确保宜搭应用功能可用
3. **发现构建缺陷**：通过模拟真实操作，暴露 AI 生成过程中的问题（字段遗漏、公式错误、规则缺失、关联错配等）
4. **建立质量基线**：为应用持续迭代提供可量化的质量指标
5. **防止回归**：每次修复后确保不引入新问题
6. **反哺工具链**：发现工具链 skill 的共性问题，修复后让所有应用受益

---

## 二、测试原则

| 原则 | 说明 |
|------|------|
| **真实场景导向** | 所有测试用例必须模拟用户真实业务操作路径，不构造脱离实际的场景 |
| **UI 优先** | 用户业务路径必须用 UI 操作验证（js-action-tester / playwright-cli），禁止用 API 调用替代用户业务路径通过 |
| **分层定位** | 发现问题后，必须区分是工具链 skill 问题还是应用配置问题，优先修复工具链 |
| **回归驱动** | 每次修复后，必须回归该模块的全部测试项，确保不引入新问题 |
| **多轮迭代** | 测试是多轮迭代过程：发现问题→修复→回归→再测试，直到质量达标 |
| **覆盖优先** | 宁可测试项有重叠，也不允许遗漏关键场景 |
| **分层测试** | UI E2E / 宜搭API / 工具链单元 三个层级，各司其职 |
| **数据隔离** | 测试数据必须与真实业务数据隔离，使用 E2E_ 前缀命名 |
| **质量门禁** | P0 必须 100% 通过；工具链问题必须有编号和回归用例 |
| **负面用例强制** | 每批次至少 2 个负面用例，必须带可量化断言 |
| **独立审计** | 出题/测试/修复/核验/归档五方分离，用户作为最终门禁 |
| **跨厂商制衡** | 修复方与测试方使用不同 AI 模型 |
| **范式锚定** | 测试判断以宜搭应用范式为依据，不测试宜搭平台自身能力和"有意不做"的能力 |
| **规则25敬畏** | 应用层修复只能本地生成 → 用户手动粘贴，严禁通过 API 改已有表单字段 |

## 三、测试分层策略（宜搭版）

| 测试层级 | 适用对象 | 执行工具 | 通过标准 | 说明 |
|---------|---------|---------|---------|------|
| UI E2E | 用户业务路径、表单交互、JS动作、字段联动、条件显示、审批操作、权限可见性 | js-action-tester / playwright-cli | 浏览器 UI 行为符合预期 | 测试方执行真实用户路径，禁止用 API 替代 |
| 宜搭 API | 表单数据提交、公式计算结果、校验规则触发、关联数据回查、流程状态 | data-tester (API模式) | 接口返回数据符合预期，字段成功写入 | 当 API 本身是测试对象时允许使用接口证据 |
| 工具链单元 | skill 脚本的内部函数（字段解析、marks计算、路径校验、HTTP封装等） | Jest (tests/core, tests/features) | 函数/模块行为稳定，边界清晰 | 降低复杂底层能力完全依赖 UI 的成本，复用现有 Jest 测试 |

**核心边界：**
- UI 业务路径（JS动作、字段联动、条件显示、流程审批）必须由 UI 通过
- 宜搭 API（数据提交、公式计算、关联回查）可作为专项测试对象
- 工具链 skill 的内部逻辑由现有 Jest 单元测试覆盖

## 四、质量门禁与退出标准

| 类型 | 门禁标准 |
|------|---------|
| P0 用例 | 必须 100% 通过 |
| P1 用例 | 建议通过率 ≥95%，且不能存在阻塞主流程的问题 |
| P2 问题 | 可记录为遗留，但必须有风险说明和后续计划 |
| 工具链问题 | 必须分配编号（如 FW-XX），修复后所有应用受益 |
| 应用层问题 | 必须生成修复产物 + 粘贴指引，由用户手动应用 |
| 修复 | 必须有对应回归用例，并补充到覆盖矩阵 |
| 工具链健康检查 | 代码修改后 `npm test` 必须通过（Jest 单元测试） |
| Smoke 回归 | 归档前至少执行核心 Smoke 集，失败不得归档 |
| 未修复问题 | 必须明确原因、风险和后续计划 |
| 最终归档 | 本批次全部测试项通过，问题跟踪中无 `待修复`/`待验证` 项 |
| **四元统计** | 每批次必须按 PASS/FAIL/SKIP/PENDING 四元统计 |
| **SKIP 上限** | 单批次 SKIP 不得超过总用例数的 20%，超过即批次作废 |
| **负面用例** | 每批次至少 2 个负面用例，必须带可量化断言 |
| **用户归档门禁** | 用户审核 9 项清单后点头才能归档 |
| **伪问题率熔断** | >50% 需复盘，>80% 暂停测试方资格 1 轮 |
| **ISS 自检** | 每个 ISS 提交前必须附 5 项自检 + 范式三问 |

## 五、11 项硬约束（宜搭版）

> **以下 11 项是经过实战迭代验证的硬性约束，不可省略。**

### HC1：四元统计口径

每个用例必须标注 PASS / FAIL / SKIP / PENDING 之一，禁止仅用二元 PASS/FAIL 掩盖问题：
- `PASS`：通过
- `FAIL`：失败（发现真实 BUG）
- `SKIP`：前置条件不满足，跳过
- `PENDING`：自动化证据不足，待人工判定

### HC2：Session 隔离机制

出题/测试/修复/核验/归档 5 个环节必须由不同 AI session 执行，互不可见对方上下文。用户作为最终门禁，AI 不替用户点头。

> **宜搭适配说明：** 测试方可能调用多个 skill（data-tester / js-action-tester），这些 skill 在同一 session 内调用，但与出题方、修复方必须 session 隔离。

### HC3：用户归档门禁

批次完成后由用户审核 9 项清单（四元统计/SKIP上限/负面用例/证据链/修复回归/工具链健康检查/Smoke通过/数据清理/状态更新），全部通过才能归档。AI 不得自行归档。

### HC4：负面用例强制

每批次提取的用例中必须包含至少 2 个负面用例，且每个负面用例必须带可量化断言（DOM 属性/API 字段/具体数值/控制台日志关键字），禁止"显示正确/工作正常"等不可证伪表述。

### HC5：SKIP 上限 20%

SKIP 数量不得超过总用例数的 20%，超过即批次作废重提。

### HC6：测试方扩展权

测试方可对可疑点追加 1-2 步 `[扩展验证]`，但必须标注前缀、说明触发原因、单独统计，不混入主用例通过率。

### HC7：跨厂商模型制衡

修复方与测试方必须使用不同厂商的 AI 模型，避免"自己改自己卷"。

### HC8：角色 KPI 互斥

| 角色 | 考核指标 | 互斥点 |
|------|---------|--------|
| 出题方 | 负面用例占比 ≥20%、量化断言完整率 100% | 不考核通过率 |
| 测试方 | FAIL 发现率、SKIP 率 ≤20%、伪问题率 ≤30% | 不考核"测得快" |
| 修复方 | 回归零回退、工具链健康检查 100% 通过 | 不考核"修得快" |
| 核验方 | 回归验证覆盖率 100%、伪阳性识别率 | 不参与修复 |
| 用户 | 归档门禁通过率 | 唯一决策归档 |

### HC9：问题修复强制

所有发现的问题必须修复，不得以"设计决策""非工具链 bug"为由搁置。设计决策与测试预期不一致时，优先调整设计/配置以支持业务需求。

> **宜搭适配说明（规则25）：** 应用层问题（公式/代码/字段）受规则25约束，修复方式为"本地生成修复产物 → 输出粘贴指引 → 用户手动粘贴到宜搭"。修复方必须生成完整的修复产物和粘贴步骤，不得以"规则25禁止"为由搁置。工具链层问题（skill脚本）可直接修改代码。

### HC10：伪问题率熔断

伪问题率 = 伪问题数 / ISS 总数：
- ≤30%：正常归档
- >50%：测试方需提交方法论复盘报告
- >80%：暂停测试方资格 1 轮，重新学习自检后再恢复

### HC11：ISS 自检强制

每个 ISS 提交前必须附：
- **5 项自检**（宜搭版）：
  - ① API 实证：报告宜搭 API 错误前，必须**实际调用该 API**（data-tester）并记录完整响应。禁止凭推断报告错误码
  - ② 源码确认：报告"字段未创建/功能未实现"前，必须**读字段清单/Schema/规则清单确认**。禁止凭 UI 表面现象判定"未实现"
  - ③ 异步等待：报告"公式未计算/流程未流转/数据未填充"前，必须**等待异步操作完成**（宜搭表单提交、公式计算、流程流转均为异步）。禁止在 loading 态抓取
  - ④ 产品设计理解：测试权限/流程节点/数据联动前，必须**读字段清单和规则清单理解产品设计**。禁止以管理员测试普通成员权限
  - ⑤ 现象可复现：报告的异常现象必须能通过**明确步骤复现**。禁止报告无法复现或依赖缓存/时序的问题
- **范式三问**：
  - ① 该能力是否在宜搭应用能力分层清单的"应有"范围内？
  - ② 若在"有意不做"范围内，是否有用户明确要求？
  - ③ 测试预期是否按宜搭应用范式编写？

## 六、四步闭环流程（宜搭版）

```
第一步：提取场景用例（出题方，独立 session）
    ↓ 从用例库提取约10个用例（含至少2个负面用例）
    ↓ 每个用例标注测试层级和执行工具（data-tester/js-action-tester/playwright-cli）
第二步：执行测试（测试方，独立 session，跨厂商模型）
    ↓ 根据用例类型调用对应 skill 执行测试
    ↓ 四元统计，形成问题列表
第三步：核验修复（修复方，当前 session）
    ↓ 伪问题预筛 → 修复真问题
    ↓ 工具链层：直接改 skill 脚本
    ↓ 应用层：生成修复产物 + 粘贴指引（规则25）
    ↓ 循环直到全部通过
第四步：归档（用户最终点头）
    ↓ 9项门禁审核
[批次完成]
```

## 七、测试场景设计原则

> 详见 `04-测试场景设计原则.md`

1. **前置条件满足**：测试某功能前，必须确保该功能已配置/已实现（字段已创建、公式已配置、规则已启用）
2. **问题可复现**：发现的问题必须能通过明确步骤复现
3. **逻辑贯通**：问题描述的前因后果必须逻辑成立
4. **有修复价值**：问题必须值得修复
5. **场景可独立**：每个测试场景应能独立执行

**关键区分：**
- ✅ 合理：字段清单中已配置校验规则，测试该规则是否生效
- ❌ 不合理：字段清单中未配置校验规则，却测试该功能为何不工作

## 八、批次编号与问题编号

### 批次号格式

`YYYYMMDD-NNN`（如 `20260716-001`）

同一批次下所有过程文件使用同一批次号：
- 提取用例：`[进行中]提取用例-YYYYMMDD-NNN.md`
- 沟通记录：`[进行中]沟通记录-YYYYMMDD-NNN.md`
- 问题跟踪：`[进行中]问题跟踪-YYYYMMDD-NNN.md`

### ISS 问题编号格式

`ISS-YYYYMMDD-NNN-XXX`（如 `ISS-20260716-001-001`）

### 问题编号映射（宜搭版）

| ISS 编号 | 编号类型 | 说明 | 修复方式 |
|---------|---------|------|---------|
| 有 FW 编号 | 工具链层问题 | skill 脚本缺陷，修复后所有应用受益 | 直接修改 skill 脚本 |
| 无 FW 编号 | 应用配置问题 | 字段/公式/规则/流程配置问题，只影响该应用 | 本地生成修复产物 + 粘贴指引（规则25）|
| 无 FW 编号 | 数据问题 | 测试数据错误/缺失，可由 data-tester 修复 | data-tester 重新提交或清理 |

### 问题状态流转

```
待修复 → 修复中 → 已修复 → 待验证 → 已验证（通过）
                                    ↓
                                 待修复（未通过，回到起点）
```

## 十、版本演进原则

1. **方法论稳定**：11 项硬约束经过实战验证，不轻易修改
2. **内容可扩展**：测试用例库、能力矩阵、Smoke 集随应用演进持续补充
3. **教训只累积**：反模式库只增不删，避免同类错误反复出现
4. **范式可更新**：应用范式定义随业务演进更新，更新时同步更新测试边界
5. **工具链反哺**：应用层共性问题应溯源到工具链层修复，让所有应用受益
