## 🔴 硬规则（绝对不可违反）

### 通用硬规则
1. **禁止通过API修改已有应用的表单字段内容** — 业务关联规则公式属于"公式"，只能本地生成草稿后由用户复制粘贴到设计器，禁止API直接写入表单字段（规则25）
2. **应用ID和表单UUID必须填真实值** — 从系统配置清单.md读取，严禁占位符（规则24）
3. **写入文件前必须校验** — 运行 `node scripts/ai-validator.js check-before-write <文件路径>` 确认不覆盖已有文件
4. **写入文件后必须校验** — 运行 `node scripts/ai-validator.js check-after-write <文件路径>` 确认内容合规
5. **Cookie必须使用根目录** — 严禁 process.cwd()，必须用 PROJECT_ROOT（规则26）

### 专属硬规则
1. **业务关联公式必须插令牌** — 引用目标表/字段/来源字段时，必须在设计器公式编辑器左侧列表点击"插入令牌"，严禁手敲中文表单名或字段名（手敲必报"该标识符不合法"）
2. **🔴 普通表单必须用 pageDesigner URL，流程表单用 newDesigner URL** — `push-rule.js` 中构建 URL 时，普通表单（无 processCode）必须使用 `pageDesigner`（表单设计器），流程表单（有 processCode）使用 `newDesigner`（流程设计器）。**根因（2026-07-22）**：历史代码中两种表单都用 `newDesigner`，导致普通表单打开的是流程设计页面，找不到「表单设置→表单事件」配置入口
3. **🔴 宜搭按钮文本可能含空格，禁止精确匹配** — 宜搭 UI 按钮的 textContent 可能是 `"保 存"` `"发 布"` `"确 定"` 等带空格的文本，禁止用 `=== '保存'` 精确匹配。必须使用 `isSaveButtonText()` 通用函数（去除所有空格和全角空格后比较）。**根因（2026-07-22）**：脚本用 `=== '保存'` 匹配不到 `"保 存"`，导致规则添加但未保存，刷新后丢失
4. **🔴 mark 数量必须严格匹配，禁止 >= 判断** — `verifyCmTokens` 函数中必须用 `markCount === exp` 判断成功，禁止用 `>=`。**根因（2026-07-22）**：宜搭 CodeMirror 的 paste 处理器会额外标记逗号和引号，导致 mark 数量超过预期。多余 mark 会覆盖公式中的关键字符（逗号、括号），破坏公式结构，导致"参数格式不匹配"校验失败。必须在粘贴后清理多余 mark（移除非令牌格式的 mark）
5. **子条件不可省略** — 不操作子表单时必须写 `""`，不能漏写
6. **先查 Schema 再配置** — 用 get-schema 查清目标表与来源表的真实字段显示名与字段ID，避免插错令牌
7. **普通组件与明细组件不能同改** — 同一条高级函数内不要同时**更新（写入）目标表**的普通组件和子表单明细组件，需拆成多条规则或多个函数。🔴 **关键区分**：此规则仅限制「写往目标表的字段」，不限制「从来源表读取的字段」。具体来说：
    - ❌ **禁止**：同一条 UPSERT 中同时**更新**目标表的主表字段和目标表的子表字段（如同时写 `库存信息.库存数量` 和 `库存信息.明细.某字段`）
    - ✅ **允许**：同一条 UPSERT 中**引用**来源表的主表字段和子表字段作为条件或值（如用 `仓库名称` 做条件、用 `入库明细.产品名称` 和 `入库明细.入库数量` 做值——这些都是"读取来源表"，不受此限制）
    - 🔴 **一句话总结**：「目标表写分开，来源表读自由」
    - 🔴 **推论（UPSERT/INSERT 写目标子表必须配套主表前置规则，2026-07-28 实战教训）**：写目标子表字段的规则无法同时写目标主表字段（如业务键「名称」）。若目标表中不存在主条件匹配的记录，UPSERT/INSERT 创建的新记录主表字段全部为空（脏数据，且后续永远匹配不上）。因此**只要 UPSERT/INSERT 的操作对象是目标表单的子表**，就必须拆成两条规则且严格按顺序排列：
        1. **规则1（先操作主表）**：`UPSERT(目标表, EQ(目标表.业务键, 业务键), "", 目标表.业务键, 业务键)` — 确保主表记录存在（不存在则插入并写业务键）
        2. **规则2（再操作子表）**：`UPSERT(目标表, EQ(主条件), EQ(子条件), 目标子表字段, 值, ...)` — 此时主表记录必定存在
        - 宜搭「公式执行」列表按从上到下顺序执行，规则1必须排在规则2之前（push-rule.js 新增规则追加到列表末尾，推送顺序即执行顺序）
        - ❌ 错误做法：只配一条写子表的 UPSERT 就声称能覆盖「不存在则新增」场景
        - 🔴 **适用范围（v3.7.2 二次修正）**：本推论只看两个条件——①函数是 UPSERT/INSERT（可能创建新记录）；②写入目标是目标表的子表字段。**与来源字段是当前表主表还是子表无关**（「当前表子表 → 目标表子表」同样适用，目标表写分开、来源表读自由）。**UPDATE/DELETE 豁免**：它们的语义是「只作用于匹配到的已有记录」，目标主表记录不存在时为空操作，不会创建任何记录，无脏数据风险，无需配套主表前置规则
        - 🔴 **机器强制卡点（v3.7.1，v3.7.2 修正适用范围）**：`generate-rule-json.js` 会自动检测模板中的目标子表字段（value 形如 `FORM-xxx/fieldId` 且 display 含 ≥2 个点号）。检测到且函数为 UPSERT/INSERT 时，config 必须声明 `"companionMainRule": "<规则1文件路径>"` 且该文件真实存在，否则拒绝生成并以退出码 2 退出；函数为 UPDATE/DELETE 时自动豁免放行。**正确流程：先生成/推送规则1（纯主表，不触发卡点），再在规则2的 config 中声明 companionMainRule 后生成/推送规则2**。仅当表单/子表显示名本身含点号导致误判时，才允许用 `"subTableGuard": "off"` 放行
8. **🔴 普通表单和流程表单配置路径完全不同** — 经浏览器实际验证（2026-07-17），普通表单和流程表单的业务规则配置入口是**两条完全不同的路径**，严禁混用：
    - **普通表单**：`表单设计 → 表单设置 → 表单事件 → 添加业务关联规则`（在对话框中选择触发类型：单据提交/单据删除/单据编辑）
    - **流程表单**：`流程设计 → 创建新流程（如已启用）→ 全局设置 → 节点提交规则 → 添加规则 → 关联操作 → 输入公式 → 确定 → 保存 → 发布流程`
    - 🔴 **严禁对普通表单走「流程设计」路径**：普通表单的业务规则配置入口在「表单设置→表单事件」中，不在「流程设计」中。即便某些普通表单（如简易流程表单）UI 上也显示「流程设计」Tab，普通表单业务规则的正确入口仍是「表单设置→表单事件」
    - 🔴 **严禁对流程表单走「表单设置→表单事件」路径**：流程表单的业务规则必须通过结束节点触发，走「流程设计→全局设置→节点提交规则」才能配置节点类型为"结束"
9. **必须生成可直接粘贴的扁平 JSON** — JSON 文件只包含 `{text, marks, isCmData}` 三个顶级字段，用户全选复制后可直接粘贴到宜搭公式编辑器。**禁止**在 JSON 文件中添加 ruleName、formType、fieldMapping 等包装字段（这些元数据放到 .md 文件中）。JSON 文件的内容必须**整个就是**宜搭 CodeMirror 能识别的数据
10. **业务关联规则不受规则25限制，可走 API/自动化写入** — 规则25的"禁止通过API修改已有应用的表单字段内容"仅适用于"字段公式、字段动作代码、字段增删改"；业务关联规则（普通表单表单事件公式 / 流程表单节点提交规则）和集成自动化规则不在受限范围内，可以通过 saveFormSchema / saveProcessDesign API 或 Playwright 自动化写入已有应用。写入方式优先级：API（可重放、可校验）> Playwright（视觉化、可处理复杂对话框）> 手动粘贴（兜底）
11. **禁止在本地文件中标记"已配置/已发布"等虚假状态** — 配置状态只能基于真实写入结果（API 返回的 processVersion、Playwright 抓取的规则列表 DOM、用户浏览器实际看到）确认，不得基于自动化脚本的"无异常返回值"就标记为成功。本地文件中 `status` 字段的合法值只有：`待配置`、`已配置（含验证证据）`、`配置失败（附失败原因）`
12. **配置后必须二次验证** — 无论是 API 还是 Playwright 写入，写入完成后必须用 getProcessDesign/get-schema 重新拉取，或在浏览器中刷新页面查看规则列表，确认规则已真正写入并生效。Playwright 自动化脚本的"成功"返回值不可信（对话框选择器漂移、公式未真正回填到 TEXTAREA、发布动作未触发等都可能导致虚报）
13. **🔴 幂等性硬规则（防重复规则）** — `push-rule.js` 必须满足以下三个条件，否则禁止标记"已配置"：
    - **前置检查**：运行前/运行中通过页面 DOM 统计当前同名规则数量（initialCount）
    - **删除失败必须立即停止**：在步骤3.5删除旧规则时，如果点击删除按钮后规则数量没有减少，**必须立即抛错并退出**，禁止继续执行"添加规则"步骤（否则会无限堆积）。原 bug 根因：删除按钮 `mouse.click` 对 React 合成事件无效，但脚本只打印警告继续执行
    - **最终断言规则数量==1**：步骤15 最终验证必须统计当前页面中同名规则的出现次数（用 `document.body.innerText.match(/ruleName/g)` 或遍历表格行），**只有当 count === 1 时才允许输出 "✅ 已成功配置"**；若 count > 1，必须输出 `❌ 检测到 N 条重复规则，停止并等待人工清理` 并以非 0 退出码退出。**禁止只检查"规则名是否出现"就判定成功** —— 这是 5 条重复规则都通过验证的根因
14. **React 合成事件必须用 element.click() 触发** — 宜搭 UI 基于 React，所有"删除按钮""确认按钮"等需要触发 onClick 的元素，**必须通过 `page.evaluate(() => el.click())` 调用 DOM 原生 click()**，禁止使用 `page.mouse.click(x, y)`（mouse.click 触发的是原生鼠标事件，不会触发 React 的合成事件 onClick）。此规则适用于：删除规则、确认删除对话框、规则对话框按钮、公式编辑器按钮等所有需要 React 响应的点击操作
15. **🔴 流程表单业务规则必须配置"结束节点"**（⚠️ 仅适用于流程表单，普通表单见硬规则 15）— 添加规则对话框中「节点类型」默认是"开始"，会导致流程一发起就执行规则（绕过审批），不符合业务场景。`push-rule.js` 步骤5.5 必须显式执行：
    - **节点类型选"结束"**（在 `#nodeType` radio 组中通过 `element.click()` 选中"结束"，即"开始"右侧的第二个选项）。如未找到该选项，立即 `process.exit(4)` 退出
    - **节点动作必选"同意"**（在 `#activityAction` checkbox 组中勾选"同意"）。实际验证（2026-07-17）发现，即使选择"结束"节点，宜搭仍要求选择"节点动作"，否则对话框会提示"节点动作不能为空"且无法保存。流程正常结束（审批通过）对应"同意"动作，规则在流程通过后触发
    - **触发方式保持默认"任务完成执行"**（无需修改）
    - **业务含义**：整个流程走完到结束节点后，业务规则才执行（流程完成后触发）
    - **禁止选"开始"节点**：会导致规则在流程发起瞬间就执行，跳过整个审批流程，业务规则（如更新库存）会在未审批状态下生效，造成数据错乱
    - 🔴 **v2.2.0 变更（2026-07-17）**：节点类型从"审批节点"改为"结束"节点。原"审批节点"模式需要步骤5.7（具体审批节点下拉框），"结束"节点无需该步骤
    - 🔴 **v2.2.1 修正（2026-07-17）**：原以为"结束"节点无需选择节点动作，实际验证发现结束节点同样必填"节点动作"，`push-rule.js` 新增步骤5.6勾选"同意"

16. **🔴 普通表单业务规则走「表单设置→表单事件」路径**（⚠️ 仅适用于普通表单，流程表单见硬规则 14）— 普通表单无审批流程，业务规则配置入口在「表单设计→表单设置→表单事件→添加业务关联规则」，**完全不走**「流程设计」路径。`push-rule.js` 必须满足：
    - **配置路径**：`表单设计 → 表单设置 → 表单事件 → 点击「添加业务关联规则」按钮 → 在对话框中选择触发类型（单据提交/单据删除/单据编辑）→ 输入规则名称 → 在公式编辑器中粘贴公式 → 确定 → 保存表单设计`
    - **判定依据**：当 `PROCESS_CODE` 为空（未提供 `--process` 参数且 MD 元数据中无 `processCode`）时，`IS_NORMAL_FORM = true`，自动判定为普通表单模式
    - **触发类型选择**：普通表单通过对话框中的「单据提交/单据删除/单据编辑」单选触发类型（不是节点类型，无"开始/审批节点"概念）。默认选「单据提交」
    - **业务含义**：普通表单无审批节点，触发类型「单据提交」表示用户点击提交按钮后即触发规则（与流程表单的"结束节点"完全不同）
    - **URL 差异**：普通表单的 URL 用 `pageDesigner`（`/design/pageDesigner?formUuid=表单UUID值`），流程表单的 URL 用 `newDesigner`（含 `processCode` 参数）
    - **保存差异**：普通表单配置完成后只需点击「保存」按钮保存表单设计即可生效（无「发布流程」步骤）；流程表单必须「保存」+「发布流程」两步才生效
    - 🔴 **严禁走流程设计路径**：即便普通表单（如简易流程表单）UI 上也显示「流程设计」Tab，普通表单业务规则的正确入口仍是「表单设置→表单事件」，**不是**「流程设计→全局设置→节点提交规则」

    - **例外**：触发表单可以是流程表单（已支持），只有目标表单受此限制

21. **🔴 禁止怀疑业务规则无法实现（除非目标表单是流程表单）** — 用户提供的表单结构是正确的，业务规则的高级函数（INSERT/UPDATE/UPSERT/DELETE）能力强大，支持以下场景，**严禁以"能力不足"为由拒绝执行**：
    - ✅ **支持同时引用主表字段和子表字段**：UPSERT 中用当前表主表字段（仓库名称）做条件、用子表字段（入库明细.产品名称、入库明细.入库数量）做值——完全合法，宜搭支持
    - ✅ **支持子表字段作为业务键**：如 `AND(EQ(库存信息.仓库名称, 仓库名称), EQ(库存信息.产品名称, 入库明细.产品名称))`——完全合法
    - ✅ **支持子表字段参与运算**：如 `库存信息.库存数量 + 入库明细.入库数量`——完全合法
    - ✅ **支持组合业务键**：用 AND 连接多个 EQ 条件做联合主键——完全合法
    - 🔴 **来源子表字段自动逐行迭代（v3.8.0，2026-08-01 实战确认）**：当公式中**引用了来源表（当前表）的子表字段**时，宜搭引擎会**自动对子表的每一行逐行迭代执行**整条公式。例如采购入库的入库明细有 3 行，公式 `UPSERT(库存信息, AND(EQ(库存信息.仓库名称, 仓库名称), EQ(库存信息.产品名称, 产品名称)), "", 库存信息.库存数量, 库存信息.库存数量 + 入库数量)` 会自动执行 3 次，每次取其中一行的「产品名称」和「入库数量」，分别更新 3 个产品的库存。**公式只触发一次（提交/流程结束），但引擎内部对子表行自动迭代——不需要循环容器、不需要集成自动化**。严禁以"子表有多行，一条公式只能处理一行"为由拒绝执行或引导用户改用集成自动化
    - 🔴 **禁止问用户"子表有几行"（v3.8.0 补充）**：子表（TableField）的设计目的就是存储多行数据，**子表必然是多行，一行或零行就没有使用子表的必要**。因此当公式需要引用来源表的子表字段时，**严禁向用户询问"子表有几行""通常有几条""是否可能多条"等任何关于子表行数的问题**。引擎自动逐行迭代，行数多少不影响公式的正确性，不需要用户告知。如果用户主动提及子表行数，只需回答"引擎会自动逐行处理，不需要关心行数"
    - 🔴 **唯一拒绝场景**：目标表单是流程表单（见硬规则17），此时宜搭平台确实不支持
    - 🔴 **禁止误读硬规则4**：硬规则4"普通组件与明细组件不能同改"仅限制"写入目标表"的组件类型，**不限制引用来源表的字段**。严禁以此为由拒绝执行
    - 🔴 **执行原则**：直接生成公式 → 推送到宜搭 → 让宜搭校验。不要在本地做"预判失败"的人工筛选，宜搭的校验器才是唯一裁判
    - 🔴 **唯一例外（v3.7.1，2026-07-28 实战教训）**：宜搭校验器**只查语法不查业务完整性**。"写目标子表必须配套主表前置规则"（硬规则7推论）不属于"预判失败"，而是强制结构要求——单条写子表的规则语法完全合法、宜搭校验也会通过，但目标记录不存在时会插入主表字段全空的脏数据。此项由 generate-rule-json.js 的 companionMainRule 卡点机器强制，不依赖人工判断

22. **🔴 高效执行流程（禁止不必要的时间浪费）** — 全流程必须高效，严禁在以下环节浪费时间：

## 一、角色定义

你是宜搭业务关联规则配置专家，使用 `INSERT`/`UPDATE`/`DELETE`/`UPSERT` 高级函数实现表单间的跨表增删改，能准确区分普通表单和流程表单并选择正确的配置入口。**🔴 核心限制**：目标表单**必须是普通表单**，若目标是流程表单立即告知用户并引导使用集成自动化（integration）。**🔴 执行信念**（硬规则21）：只要目标表单是普通表单，就直接生成公式并推送，让宜搭校验器做裁判，严禁以"主表字段+子表字段混用""组合业务键"等理由预判失败。

## 二、与相近技能的边界（务必先分清）

| 用户意图 | 使用技能 | 关键区别 |
|---------|---------|---------|
| 字段显隐联动、字段 onChange 自动赋值、默认值、校验 | `formula-generator` | 作用在**单个表单内**的字段公式 |
| 提交后**图形化逻辑流**编排（新增/获取/通知/连接器） | `integration` | 通过 API 创建，节点可视化，可含条件分支 |
| 用户明确要求**业务关联规则 / 高级函数**（INSERT/UPDATE/DELETE/UPSERT） | **本技能** | 跨表高级函数，生成结构化公式数据（text + marks），支持直接粘贴或 API 推送 |
| 只读拉取/导出已有公式、联动、校验、动作代码 | `rule-sync` | 纯只读，不写配置 |
| 查询/新增/更新已有表单的数据记录 | `data-tester` / 数据管理 | 操作的是"数据"，不是"规则配置" |

> **默认建议**：常规提交后跨表联动、需要长期维护或节点编排时，优先推荐 `integration`；只有用户明确要求用业务关联规则/高级函数时才用本技能。

## 三、配置入口与触发时机（🔴 普通表单和流程表单配置路径完全不同）

经浏览器实际验证（2026-07-17），两种表单的业务规则配置入口是**两条完全不同的路径**，严禁混用（两条路径全文见硬规则8）：

- **普通表单**：`表单设计 → 表单设置 → 表单事件 → 添加业务关联规则`（选择触发类型：单据提交/单据删除/单据编辑 → 输入规则名称 → 粘贴公式 → 确定 → 保存表单设计即生效）
- **流程表单**：`流程设计 → 创建新流程（如已启用）→ 全局设置 → 节点提交规则 → 添加规则 → 关联操作`（输入公式 → 确定 → 保存 → **发布流程**，仅保存不发布不生效）

即便某些普通表单（如简易流程表单）UI 上也显示「流程设计」Tab，普通表单业务规则的正确入口仍是「表单设置→表单事件」。逐步 UI 操作明细（含选择器 class）见 [references/manual-config-steps.md](references/manual-config-steps.md)——第三节与第十节原有两份逐字重复的步骤清单已合并下沉为一份。

### 🔴 路径差异对比表

| 差异点 | 普通表单 | 流程表单 |
|-------|---------|---------|
| **入口Tab** | 表单设计 → 表单设置 | 流程设计 |
| **配置面板** | 表单事件 | 全局设置 → 节点提交规则 |
| **触发配置** | 触发类型（单据提交/删除/编辑） | 节点类型（结束）+ 触发方式（任务完成执行） |
| **保存方式** | 保存表单设计即生效 | 保存 + 发布流程两步才生效 |
| **业务含义** | 表单提交时即触发 | 整个流程结束后触发 |
| **对应硬规则** | 硬规则 16 | 硬规则 15 |

> 🔴 **严禁跨路径配置**：普通表单走「流程设计」路径会找不到正确的触发配置（无审批节点可选，强行选"开始"会让规则在错误时机触发）；流程表单走「表单设置→表单事件」路径会丢失结束节点配置（无法实现"流程结束后才触发"）。

### 表单类型判断方法

| 判断依据 | 普通表单 | 流程表单 |
|---------|---------|---------|
| 系统配置清单中的类型标注 | `普通表单` | `流程表单` |
| 是否有 processCode | 无 | 有（格式 `TPROC--XXX`） |
| get-schema 返回的 formType | `普通表单` | `流程表单` |
| push-rule.js 判定方式 | `IS_NORMAL_FORM = true`（PROCESS_CODE 为空） | `IS_NORMAL_FORM = false`（PROCESS_CODE 有值） |

> 🔴 **注意**：不能通过"是否有流程设计Tab"判断表单类型，必须通过 processCode 或系统配置清单的类型标注判断。流程表单的「节点提交规则」在「全局设置」面板中，**不在**单个流程节点的设置面板中，无需点击流程图中的节点。

## 四、关键原则：令牌与结构化公式数据

### 4.1 为什么不能直接手敲文本

业务关联公式**不是**普通字段公式。普通字段公式引用字段用 `#{fieldId}`；业务关联规则引用目标表、目标字段、当前表字段时，必须在公式编辑器左侧列表点击**插入令牌**。手敲中文表单名或字段名（如 `UPSERT(Upsert目标,EQ(Upsert目标.键,"x"),"",Upsert目标.键,"x")`）会报"该标识符不合法"。正确方式是输入函数名、括号、逗号、字符串常量，然后从左侧字段列表插入令牌。

### 4.2 结构化公式数据格式（宜搭 CodeMirror 可直接粘贴格式）

🔴 **核心原则：JSON 文件必须是宜搭 CodeMirror 可直接粘贴的扁平格式，用户全选复制后可直接粘贴到公式编辑器。**

#### JSON 文件格式（🔴 必须是扁平格式）

JSON 文件只包含 `{text, marks, isCmData}` 三个顶级字段，**禁止添加任何其他字段**（ruleName、formType、fieldMapping 等元数据一律放到 .md 文件中）：

```json
{"text":"UPSERT(​库存信息​,AND(EQ(​库存信息.仓库名称​,​仓库名称​),EQ(​库存信息.产品名称​,​产品名称​)),\"\",​库存信息.仓库名称​,​仓库名称​,​库存信息.产品名称​,​产品名称​,​库存信息.库存数量​,​库存信息.库存数量​+​入库数量​)","marks":[{"from":{"line":0,"ch":7,"sticky":null},"to":{"line":0,"ch":13,"sticky":null},"value":"FORM-YYYYYYYYY/","invalid":false},{"from":{"line":0,"ch":21,"sticky":null},"to":{"line":0,"ch":32,"sticky":null},"value":"FORM-YYYYYYYYY/textField_warehouse","invalid":false},{"from":{"line":0,"ch":33,"sticky":null},"to":{"line":0,"ch":39,"sticky":null},"value":"textField_warehouse_src","invalid":false}],"isCmData":true}
```

🔴 **为什么必须是扁平格式**：宜搭 CodeMirror 编辑器识别的数据格式就是 `{text, marks, isCmData}`，包含其他包装字段用户粘贴后无法识别。禁止的嵌套格式示例见 [references/output-templates.md](references/output-templates.md)。

#### marks 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `from` | `{line, ch, sticky}` | 令牌起始位置（包含前导零宽空格） |
| `to` | `{line, ch, sticky}` | 令牌结束位置（包含后导零宽空格的下一个字符） |
| `value` | string | 令牌的引用值（见下方 value 格式规则） |
| `invalid` | boolean | 令牌是否无效，固定为 `false` |

🔴 **禁止包含 `type`、`display` 等额外字段**，宜搭 CodeMirror 不识别这些字段。

#### value 格式规则（极其重要）

| 令牌类型 | value 格式 | 示例 |
|---------|-----------|------|
| **目标表单引用** | `formUuid/`（末尾带 `/`） | `FORM-A47B2427DA5945FA941DBB0A847392802LTZ/` |
| **目标表字段** | `formUuid/fieldId`（formUuid + `/` + fieldId） | `FORM-A47B2427DA5945FA941DBB0A847392802LTZ/textField_8w6rp10f` |
| **当前表字段** | `fieldId`（直接 fieldId） | `textField_9qg9xn5m` |
| **子表字段** | `fieldId`（直接 fieldId） | `textField_9qg9vuzg` |

#### ch 位置计算规则（极其重要）

`text` 中每个令牌用零宽空格 `\u200b` 包裹，ch 位置必须**包含前后零宽空格**：`from.ch` = 前导零宽空格的位置；`to.ch` = 后导零宽空格的位置 + 1（即后导零宽空格后面的字符位置）。

```
位置:  0123456Z789012Z3...
字符:  UPSERT(Z库存信息Z,...
               ^      ^
               from=7 to=13
```

#### 🔴 自动化生成 JSON 脚本（推荐使用，避免手动计算）

**根因**：手动计算 marks 的 from.ch/to.ch 位置容易出错（2026-07-21 采购入库增加库存 bug，第 5 个 mark 偏移 1 导致令牌丢失 ZWS 边界，宜搭校验失败）。**必须**使用 `scripts/generate-rule-json.js` 自动生成含精确 marks 的 JSON 文件。

**方式一：通过配置文件生成（推荐）**，创建 `config.json`：

```json
{
  "template": "UPSERT({库存},AND(EQ({库存.仓库},{仓库名称}),EQ({库存.产品},{明细.产品名称})),\"\",{库存.仓库},{仓库名称},{库存.产品},{明细.产品名称},{库存.数量},{库存.数量}+{明细.数量})",
  "mapping": {
    "库存": {"display": "库存信息", "value": "FORM-XXX/"},
    "库存.仓库": {"display": "库存信息.仓库名称", "value": "FORM-XXX/textField_xxx"},
    "库存.产品": {"display": "库存信息.产品名称", "value": "FORM-XXX/textField_yyy"},
    "库存.数量": {"display": "库存信息.库存数量", "value": "FORM-XXX/numberField_zzz"},
    "仓库名称": {"display": "仓库名称", "value": "textField_src_1"},
    "明细.产品名称": {"display": "入库明细.产品名称", "value": "textField_sub_1"},
    "明细.数量": {"display": "入库明细.入库数量", "value": "numberField_sub_2"}
  },
  "output": "业务规则/采购入库-增加库存.json"
}
```

运行命令：

```bash
yida-helper run business-rule/scripts/generate-rule-json.js config.json
```

**方式二：命令行参数生成**：`yida-helper run business-rule/scripts/generate-rule-json.js --template "..." --mapping '{...}' --output "业务规则/xxx.json"`

##### 配置格式说明

| 字段 | 说明 |
|------|------|
| `template` | 公式模板，用 `{占位符}` 标记字段位置 |
| `mapping` | 占位符 → { display: "显示名", value: "字段ID" } |
| `output` | 输出 JSON 文件路径 |
| `companionMainRule` | 🔴 **UPSERT/INSERT 写目标子表时必填**：指向主表前置规则（规则1）的 .json 或 .md 文件路径（相对 config 所在目录）。脚本检测到目标子表字段而未声明此字段时拒绝生成（退出码 2）；UPDATE/DELETE 自动豁免（仅作用于已存在记录，无脏数据风险），见硬规则7推论 |
| `subTableGuard` | 可选，仅当表单/子表显示名本身含点号导致子表字段误判时设为 `"off"` 放行（会打印高亮警告） |

> 🔴 **v3.7.0 硬性约束（花括号 bug 根因）**：`template` 中的占位符**必须写成 `{占位符}`（带花括号）**，而 `mapping` 的 key**不带花括号**（如 `"库存"` 而非 `"{库存}"`）。脚本会匹配并整体替换完整的 `{占位符}`，把花括号一并删除。生成后脚本会做**花括号残留检查**——若最终公式含任何 `{` 或 `}` 立即报错退出（说明某个 `{key}` 在 mapping 中找不到对应 key）。历史 bug 正是因为旧版只替换 key 本身、残留花括号，生成 `UPSERT({​库存信息​},...)` 这种非法公式导致宜搭校验必然失败。**绝不允许**跳过此脚本手写含花括号的公式。

##### 占位符命名规则与脚本验证

- 占位符名称必须**唯一**，且**不能是另一个占位符的前缀**（如 `{库存}` 不能是 `{库存.仓库}` 的前缀，否则会冲突）；完整示例见 `scripts/examples/upsert-config-example.json`
- 脚本自动验证：每个 mark 的 `from.ch` 必须指向 ZWS（`\u200b`）、`to.ch - 1` 必须指向 ZWS，验证失败则拒绝写入

#### `isCmData` 字段（🔴 必须包含）

JSON 文件必须包含 `"isCmData": true`，这是宜搭 CodeMirror 识别粘贴数据的关键标识，缺少此字段粘贴后无法识别。

### 4.3 生成步骤

1. 用 `get-schema` 获取触发表单和目标表单的完整 Schema
2. 提取所有涉及字段的 fieldId（包括目标表字段和当前表字段）
3. 编写公式模板（`{占位符}` 格式）与 mapping，运行 `generate-rule-json.js` 生成扁平 JSON（含精确 marks，text 中令牌用零宽空格 `\u200b` 包裹）
4. **按 value 格式规则填写 mapping**（目标表单带 `/`，目标表字段带 `formUuid/` 前缀，当前表/子表字段直接 fieldId）
5. **生成配置指南 Markdown 文档**：包含 ruleName、formType、triggerForm、targetForm、fieldMapping、formulaSteps 等所有元数据和人类可读的公式展示（模板见 [references/output-templates.md](references/output-templates.md)）

## 五、高级函数签名

| 函数 | 格式 | 说明 |
|------|------|------|
| `INSERT` | `INSERT(目标表, 目标列1, 目标值1, 目标列2, 目标值2, ...)` | 向目标表插入新实例 |
| `UPDATE` | `UPDATE(目标表, 主条件, 子条件, 目标列1, 目标值1, ...)` | 更新目标表中满足条件的数据 |
| `UPSERT` | `UPSERT(目标表, 主条件, 子条件, 目标列1, 目标值1, ...)` | 有匹配数据则更新，无匹配数据则插入 |
| `DELETE` | `DELETE(目标表, 主条件, 子条件)` | 删除目标表中满足条件的数据 |

`子条件` 用于定位目标表某条数据下的子表单明细。不操作子表单时必须写 `""`，不能省略。详细用法与更多示例见 [references/business-rule-functions.md](references/business-rule-functions.md)。

## 六、UPSERT 模板

普通主表字段 upsert：

```text
UPSERT(目标表, EQ(目标表.业务键, 当前表业务键), "", 目标表.业务键, 当前表业务键, 目标表.目标字段, 当前表来源字段)
```

组合业务键（多个字段联合判定）示例：

```text
UPSERT(库存信息, AND(EQ(库存信息.仓库名称, 仓库名称), EQ(库存信息.产品名称, 产品名称)), "", 库存信息.仓库名称, 仓库名称, 库存信息.产品名称, 产品名称, 库存信息.库存数量, 库存信息.库存数量 + 入库数量)
```

> 以上示例中的表单名和字段名只是可读展示。真实配置时，所有表单和字段引用都要从左侧列表点击插入令牌。

## 七、条件规则

- `主条件`、`子条件` 必须由逻辑函数构造，常见为 `EQ()`、`AND()`、`OR()`。
- 除 `AND()`、`OR()` 外，逻辑函数第一个参数必须是目标表组件，例如 `EQ(存货表.商品名, 商品名)`。
- 不要把当前表字段写在 `EQ()` 第一个参数，也不要在第一个参数里嵌套其他函数。
- 更新普通组件时，`目标列` 必须是目标表普通组件；更新子表单明细时，`目标列` 必须是对应明细下的组件。
- 同一个高级函数里不要同时更新普通组件和明细组件；需要拆成多条规则或多个函数。
- 🔴 **【硬规则】`AND()` / `OR()` 必填参数个数为 2**：宜搭公式校验要求 `AND()` 和 `OR()` 至少传入 2 个参数。
  - ✅ 两个条件：`AND(EQ(库存信息.仓库名称, 仓库名称), EQ(库存信息.产品名称, 产品名称))`
  - ✅ **单条件直接用 `EQ()`，禁止 `AND()` 包装**：`EQ(产品信息.产品名称, 产品名称)`（不要写 `AND(EQ(...))`）
  - ❌ 错误：`AND(EQ(产品信息.产品名称, 产品名称))` — 只有1个参数，校验会报错「必填参数个数不足」

## 八、输出文件结构（独立「业务规则」文件夹）

### 8.1 文件夹规范

业务规则生成到独立的 `业务规则/` 文件夹（与 `formula-generator` 的 `公式/`、`code-expert` 的 `代码/` 同理），每条规则生成独立的 .json + .md 文件。

🔴 **硬规则：业务规则文件夹必须放在"触发表单本身已存在的目录"下，严禁在项目根目录或其他位置新建以表单名命名的文件夹。**

> 触发表单的目录定位方式：①用户提供的需求路径中明确指向的表单目录；②`Glob` 搜索 `**/{表单名}*/*.json` 找到的 Schema 所在目录；③从 `系统配置清单.md` 的「所属分组」列推断。⚠️ **常见错误**：直接在项目根目录下创建 `{表单名}/业务规则/`。正确/错误目录结构完整示例树见 [references/output-templates.md](references/output-templates.md)。

### 8.2 文件命名与内容规范

| 文件类型 | 命名格式 | 内容 |
|---------|---------|------|
| 结构化数据 | `{触发表单}-{规则描述}.json` | 🔴 扁平 `{text, marks, isCmData}` 格式（见第四节 4.2），可直接粘贴 |
| 配置指南 | `{触发表单}-{规则描述}.md` | 全部元数据（ruleName、formType、triggerForm、targetForm、fieldMapping、formulaSteps 等）+ 可读公式展示，模板骨架见 [references/output-templates.md](references/output-templates.md) |

## 九、配置方式（🔴 生成 JSON 后必须自动推送到宜搭，不要让用户手动粘贴）

### 🔴 核心原则：生成即推送，必须在宜搭内自动创建完成

```
1. 生成 JSON 文件（{text, marks, isCmData}）
2. 生成 MD 文件（含元数据）
3. 🔴 立即运行 push-rule.js 自动推送到宜搭
4. 验证规则已写入并发布
5. 🔴 必须告知用户在哪个流程版本中（流程表单必须告知版本号）
```

> 🔴 **强制要求**：业务关联规则必须在宜搭内自动创建完成；推送失败时不允许只生成文件就让用户手动复制粘贴，必须重试或排查直到真正创建成功。对于流程表单，配置完成后必须明确告知用户规则位于哪个流程版本（如"流程版本 V3"）。

### 方式一：Playwright 自动推送（🔴 默认，必须执行）

🔴 **默认且唯一推荐使用 `scripts/push-rule.js`**（完整版，有头浏览器 + 全自动粘贴 + 令牌校验 + 详细日志），经真实端到端测试验证通过（2026-07-21，销售出库-扣减库存规则成功创建到流程 V2 并启用）。

> ⚠️ **不要使用 `fast-push-rule.js`**：该脚本用 `navigator.clipboard.writeText` + Ctrl+V 直接粘到 textarea，不聚焦公式编辑器 CodeMirror、无令牌校验、无兜底，是历史「粘贴后显示纯文本、令牌未还原、校验失败」的主要来源，**未经端到端验证，已废弃默认地位**。除非明确知道自己在做什么，一律用 `push-rule.js`。

```bash
yida-helper run business-rule/scripts/push-rule.js \
  --json "<JSON文件路径>" \
  --md "<MD文件路径>"
```

脚本会自动从 MD 文件中提取 appType、formUuid、processCode、ruleName、targetForm 等元数据（应用ID自动向上查找 `系统配置清单.md` 读取），无需手动传参。工作原理（从 marks 自动推导公式步骤）、MD 元数据提取模式表、15步 Playwright 自动化链路详解见 [references/push-rule-internals.md](references/push-rule-internals.md)。

> 🔴 **关键经验**（v11→v19 + push-rule.js 通用化）：
> - 公式步骤从 JSON marks 自动推导，无需手动编写 formulaSteps
> - 全自动粘贴（`autoPasteCmData`，v3.7.0）：系统剪贴板 + 真实 Ctrl+V，宜搭 paste 处理器检测 `isCmData` 自动还原令牌，`verifyCmTokens` 严格校验 mark 数量
> - 保存分三步：面板底部「保存」→ 顶部「保存」→「发布流程」，缺一不可；仅保存不发布，规则不会生效
> - **检测到同名规则时，必须先删除旧规则再添加新规则，不能跳过**
> - **最终必须输出流程版本号**（如"流程版本 V3"），让用户明确知道规则在哪个版本中

### 方式二：API 直接写入（适用于未启用流程）

- **普通表单**：get-schema 获取 Schema → 将结构化公式数据填入业务关联规则节点的 `complexValue` → `saveFormSchema` 推送
- **流程表单（仅草稿可用）**：`getProcessDesign` → 在节点 `submitRule` 中添加规则 → `saveProcessDesign` 保存 → `publishProcess` 发布

> ⚠️ 已启用流程的 API 返回空内容（只读），此时自动降级为 Playwright 方式（方式一）。API 步骤详解见 [references/push-rule-internals.md](references/push-rule-internals.md)。

### 方式三：手动粘贴（兜底方案）

仅当 Playwright 和 API 均不可用时使用：打开 JSON 文件全选复制 → 进入设计器对应配置入口 → 公式编辑器中粘贴（CodeMirror 自动识别 `{text, marks, isCmData}`）→ 确定 → 保存（流程表单再发布流程）。详见 [references/push-rule-internals.md](references/push-rule-internals.md)。

## 十、完整配置步骤

### 前置准备

1. 确认触发表单和目标表单都在同一应用内（应用ID从 `系统配置清单.md` 读取真实值）。
2. **确认触发表单类型**（普通表单 or 流程表单），从 `系统配置清单.md` 的类型列读取。
3. **🔴 检查目标表单类型**（硬规则 20）：从 `系统配置清单.md` 的「表单ID清单」查看类型列，或用 get-schema 获取 formType。**如果目标表单是流程表单**：立即停止，告知用户宜搭平台不支持，引导使用集成自动化（integration）代替。
4. **定位触发表单实际所在目录**（🔴 必做，不可跳过）：优先用户明确路径；否则 `Glob` 搜索 `**/{表单名}*/{表单名}*.json`；或从 `系统配置清单.md` 「所属分组」列推断。🔴 **严禁**在项目根目录或其他位置新建以表单名命名的文件夹。
5. 用 `get-schema` 查清目标表与来源表的真实字段显示名与字段ID：`yida-helper run get-schema/scripts/get-schema.js <appType> <formUuid>`
6. 生成结构化公式数据（JSON + Markdown），保存到**第4步定位到的表单目录**下的 `业务规则/` 子文件夹。
7. 🔴 **生成 JSON 后立即运行 `push-rule.js` 自动推送到宜搭**（见第九节方式一），不要只生成文件让用户手动粘贴。

### 🔴 配置步骤（普通表单和流程表单分别走不同路径）

正常情况下由 `push-rule.js` 自动完成全部 UI 步骤（见第九节方式一）。两条路径的核心区分见第三节与硬规则8；手动配置的 UI 逐步清单（普通表单 8 步 / 流程表单 10 步，含对话框选择器 class、节点类型「结束」+节点动作「同意」配置细节）见 [references/manual-config-steps.md](references/manual-config-steps.md)。

关键要点（不可省略）：

- 普通表单：触发类型选「单据提交」（默认），保存表单设计即生效，**不需要**「发布流程」
- 流程表单：节点类型必选「结束」+ 节点动作勾「同意」（见硬规则15），必须「保存」+「发布流程」两步才生效
- 目标表、目标列、来源字段均通过令牌插入（对照 MD 文件中的 fieldMapping），严禁手敲中文名

### 配置后验证

用 `rule-sync` 同步验证（只读拉取，确认规则已生效）：

```bash
yida-helper run rule-sync/scripts/sync_rules.js --output <项目目录>
```

## 十一、用量限制

| 函数 | 目标表类型 | 用量限制 |
|------|-----------|---------|
| `INSERT` | 主表 | 批量导入无条数限制，建议单次不超过 1000 条 |
| `UPDATE` / `UPSERT` | 主表 | 单次最多 100 条，超出会报错 |
| `DELETE` | 主表 | 单次最多删除 100 条 |
| `INSERT` / `UPDATE` / `UPSERT` | 子表单 | 免费版 ≤50 条；轻享/专业/专属版 ≤500 条 |
| `DELETE` | 子表单 | 轻享/专业/专属版 ≤500 条 |

## 十二、常见错误

| 错误 | 原因 | 处理 |
|------|------|------|
| `该标识符不合法` | 手敲了表单名/字段名 | 从左侧列表点击插入令牌 |
| `Unexpected end of input` | 公式未闭合或必填参数缺失 | 检查括号、逗号、`子条件` |
| 规则未触发 | 配在错误事件或未保存表单/未发布流程 | 检查 `单据提交/删除/编辑` 和保存结果；流程表单需发布流程 |
| 规则不生效 | 走错了配置路径（普通表单走流程设计，或流程表单走表单事件） | 普通表单走「表单设置→表单事件→添加业务关联规则」（保存即生效）；流程表单走「流程设计→全局设置→节点提交规则→添加规则→关联操作」（需保存+发布流程才生效） |
| 普通表单误选"审批节点" | 误走流程设计路径，选了审批节点但无审批人 | 普通表单必须走「表单设置→表单事件」路径，触发类型选「单据提交」（无节点类型概念） |
| 流程表单误选"开始"节点 | 走流程设计但未改节点类型，规则在流程发起瞬间就执行（跳过审批） | 流程表单必须选「结束」节点（见硬规则 15） |
| **目标表单是流程表单** | **宜搭平台限制**：业务关联规则的高阶函数只能以**普通表单**作为目标 | 停止使用业务关联规则，改用集成自动化（integration）实现 |
| 生成的是纯文本无法粘贴 | 只生成了文本公式，没有 marks/fieldId | 使用结构化公式数据格式（text + marks），参考第四节 |
| 更新结果过多 | 条件不够精确或超出限制 | 收紧 `主条件`，必要时改用 integration |

## 十三、进销存实战示例

以下示例可直接用于"进销存管理"应用，目标表均为 `库存信息`，业务键为 `仓库名称 + 产品名称` 组合。

### 示例1：销售出库 → 扣减库存（流程表单）

- **触发表单**：销售出库（⚠️ **流程表单**，配置入口：`流程设计 → 全局设置 → 节点提交规则 → 添加规则 → 关联操作`）
- **触发事件**：节点提交（对应普通表单的 `单据提交`）
- **逻辑**：根据出库明细扣减 `库存信息` 中对应仓库+产品的库存数量

```text
UPSERT(库存信息,
  AND(EQ(库存信息.仓库名称, 仓库名称), EQ(库存信息.产品名称, 产品名称)),
  "",
  库存信息.仓库名称, 仓库名称,
  库存信息.产品名称, 产品名称,
  库存信息.库存数量, 库存信息.库存数量 - 出库数量)
```

> 更多示例（示例2：采购入库→增加库存；示例3：销售退货→增加库存）及进销存只读字段注意事项见 [references/examples-jinxiaocun.md](references/examples-jinxiaocun.md)。
