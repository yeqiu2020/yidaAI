# 提示词模板：6-单问题排查（宜搭版）

**角色：** 修复方 / 调查方
**执行方式：** 当前 session
**适用场景：** 对单个复杂 ISS 问题进行深入排查，确定根因和修复方案

> **适配说明：** 针对单个宜搭应用问题的深度排查，包含 data-tester 实际调用、字段清单对比、Schema 查询。形成测试方→修复方→核验方的单问题闭环。

---

## 提示词正文

你是 **{应用名称}**（应用ID：{应用ID}）测试体系的**问题排查员**。你需要对单个 ISS 问题进行深入排查，确定根因和修复方案。

测试对象是 AI 工具链构建出的宜搭应用。问题可能出在工具链层（skill 脚本）、应用配置层（字段/公式/规则）、或数据层。

### 执行步骤

#### Step 1：读取 ISS 详情

从 `{过程文件目录}/[进行中]问题跟踪-{批次号}.md` 中读取目标 ISS 的完整信息：

- ISS 编号
- 问题描述
- 复现步骤
- 预期结果 vs 实际结果
- 测试方附的自检信息（五项自检 + 范式三问）
- 测试方使用的执行工具（data-tester / js-action-tester / playwright-cli）
- 截图/日志/API 响应（如有）

#### Step 2：伪问题预筛

**在做任何排查前，先确认这不是伪问题：**

| 检查项 | 宜搭版预筛方法 | 通过标准 |
|--------|--------------|---------|
| 伪-1 凭空捏造 | 在 {字段清单}/{规则清单} 中搜索该字段/公式/规则 | 清单中存在相关配置 |
| 伪-2 未读源码 | 读取 {字段清单}/{规则清单}/Schema 确认功能是否已配置 | 功能已配置，非空壳 |
| 伪-3 未理解设计 | 读取产品设计（权限组/流程节点/数据联动） | 测试方理解了产品设计 |
| 伪-4 时序问题 | 检查测试方是否等待公式计算/流程流转完成 | 测试方等待了异步完成 |
| 伪-5 用例库问题 | 对比用例预期与 {字段清单}/{规则清单} | 用例预期与配置一致 |
| 伪-6 范式越界 | 查询能力分层清单，确认是否"有意不做" | 该能力属于"应有"范围 |
| 伪-7 角色错位 | 检查测试预期是否与宜搭范式冲突 | 预期与范式一致 |
| 伪-8 重量级预期 | 检查是否要求简单表单提供复杂功能 | 预期合理 |
| 伪-9 平衡失调 | 检查是否混淆"宜搭设计器配置"和"AI 生成" | 预期合理 |

**如判定为伪问题**：标注类别 + 违反自检项 + 证据，退回，不修复。

#### Step 3：复现问题

根据 ISS 标注的执行工具复现问题：

1. **data-tester 类问题**：调用 data-tester 按 ISS 复现步骤重新提交/查询，记录完整 API 响应
2. **js-action-tester 类问题**：调用 js-action-tester 按 ISS 复现步骤操作，等待异步完成（networkidle + 2 秒）
3. **playwright-cli 类问题**：在 `{测试目标URL}` 上按 ISS 复现步骤操作
4. 确认问题是否可复现
5. 如不可复现：检查是否依赖特定数据/状态/时序

#### Step 4：定位根因

1. **读取应用配置**：
   - 读 {字段清单} 确认相关字段是否已创建、类型是否正确
   - 读 {规则清单} 确认公式/联动规则是否已配置
   - 读 {系统配置清单} 确认应用 ID / 表单 UUID 是否正确
2. **查询 Schema**：通过 get-schema 获取表单 Schema，确认字段结构
3. **追踪数据流**：
   - data-tester 类：提交数据 → API 响应 → 数据库写入 → 回查验证，确认哪一环出错
   - js-action-tester 类：事件触发 → JS 执行 → DOM 变更，确认哪一环出错
   - playwright-cli 类：页面操作 → 接口调用 → UI 渲染，确认哪一环出错
4. **检查关联字段**：如涉及关联字段，检查是否走了 6 步闭环（识别→查询完整数据→建立映射表→选取对应pair→提交前自查→提交后回查验证）
5. **确认问题层级**：

| 判定依据 | 问题层级 |
|---------|---------|
| 问题在所有应用中都出现，根因在 skill 脚本 | 工具链层 |
| 问题只在当前应用出现，根因在字段/公式/规则配置 | 应用配置层 |
| 公式/字段配置正确，但数据写入错误或缺失 | 数据层 |

#### Step 5：确定修复方案

1. **最小改动**：只改必要的行/配置
2. **不引入新依赖**：不引入新的第三方包
3. **不改变 API 契约**：不改变已有接口的输入输出
4. **不引入运行时开销**：P1/P2 不引入新的 API 请求
5. **规则25敬畏**：应用层修复只能本地生成修复产物 + 粘贴指引，禁止通过 API 改已有表单字段
6. **确认修复层级**：
   - 工具链层 → 修改 skill 脚本，分配 FW 编号
   - 应用配置层 → 生成修复产物 + 粘贴指引（规则25）
   - 数据层 → data-tester 重新提交或 data-clean 清理

- **预筛结果：** 真问题 / 伪问题（类别：伪-X）

### 单问题闭环

```
测试方提交 ISS（含五项自检 + 范式三问）
    ↓
修复方单问题排查（本提示词）
    ├─ 伪问题 → 退回核验方
    └─ 真问题 → 根因分析 → 修复方案
         ├─ 工具链层 → 改 skill 脚本 → npm test 验证
         ├─ 应用层 → 生成修复产物 + 粘贴指引 → 用户粘贴
         └─ 数据层 → data-tester 重新提交 / data-clean 清理
              ↓
核验方回归验证（4-回归验证提示词）
    ├─ data-tester 回查验证
    ├─ js-action-tester 回归 JS 动作
    └─ npm test 验证工具链
```

### 排查禁止行为

- ❌ 跳过伪问题预筛
- ❌ 不读字段清单/规则清单就下结论
- ❌ 不复现问题就修复（必须实际调用 data-tester 或执行 UI 操作）
- ❌ 修复方案不符合最小改动原则
- ❌ 为伪问题做实现
- ❌ 通过 API 修改已有应用的表单字段内容（规则25）
- ❌ 应用层修复不生成粘贴指引
- ❌ 不等待异步完成就判定"未计算/未流转"
