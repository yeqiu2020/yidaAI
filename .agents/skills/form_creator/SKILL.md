## 🔴 硬规则（绝对不可违反）

### 通用硬规则

> 本区块 1-5 条通用硬规则统一维护于 [../通用硬规则.md](../通用硬规则.md)（单一来源，避免多点复制导致规则漂移），执行前必须阅读并严格遵守。

### 专属硬规则
1. **saveFormSchema仅允许对新建表单调用** — 严禁对已有表单调用saveFormSchema
2. **创建失败必须回滚已创建的表单** — 避免留下空白表单
3. **同名表单跳过不删除** — 检测到同名表单时跳过创建，不删除后重建
4. **【强制】应用名称必须与本地项目文件夹名一致** — 调用 `create_from_markdown.js` 时，**严禁传入应用名称参数**（除非用户明确指定），让脚本自动使用本地项目文件夹名（`path.basename(outputDir)`）作为宜搭应用名称。**严禁从字段清单标题中提取应用名称传入**。字段清单标题中的"系统名称"（如"进销存管理系统"）仅用于文档展示，不等于宜搭应用名称。
5. **创建前必须核对字段清单关联关系和填充规则** — 执行 `create_from_markdown.js` 前，AI 必须人工核对字段清单中的关联字段和填充规则：
   - **关联字段核对**：检查每个"关联表单"字段的"字段说明"是否写成 `关联-->目标表单名`，目标表单名必须在字段清单中存在。**【v6.61.0强制】被其他关联字段填充的"只读关联表单字段"也必须标注 `关联-->目标表`，说明列绝不能只写`-`**（进销存3事故根源：漏标导致 FORM-TEMP 占位符残留，线上点"新增"报"表单不存在"）。脚本 v2.20.0 已内置建表前校验：漏标时按字段名推断（推断成功会打印 ⚠️ 告警，AI 看到后必须回头补全字段清单），推断失败直接中止建表
   - **填充目标核对**：检查每条填充规则中的"当前字段"是否在当前表单中存在（类型与源字段一致，状态为只读）
   - **填充语法核对**：检查填充规则格式是否为 `当前字段=源字段`，多个填充对之间使用顿号"、"分隔（脚本也兼容中文逗号"，"、英文逗号","、中文分号"；"、英文分号";"）
   - **填充规则格式规范**：填充规则统一写在关联表单字段的"字段说明"列中，格式为：`关联-->目标表单名；填充：当前字段A=源字段A、当前字段B=源字段B`。被填充字段名和源字段名**可以不同**（如`关联订单号=销售订单号`），脚本会用源字段名在目标表单精确匹配，用被填充字段名在当前表单找对应组件。
   - **注意**：可先用 `node scripts/ai-validator.js check-fill-rule-syntax <字段清单路径>` 校验填充规则语法（=号格式与分隔符）；但语义正确性（目标表单名是否存在、填充目标字段是否匹配）仍需 AI 在读取字段清单时逐条人工核对。校验脚本位于仓库根目录 `scripts/ai-validator.js`（真实存在），与通用硬规则 3/4 一致。

6. **【强制·v6.53.0新增，v6.61.0扩展】关联配置失败必须报告用户** — `create_from_markdown.js` 在 `updateAssociationFields` 阶段会收集所有"解析到规则但未成功配置"的字段（v6.61.0起也包括"目标表单未匹配到已建表单"的关联字段），并在最后输出"⚠️ 关联填充规则配置失败汇总"。AI执行完毕后**必须**检查输出日志：
   - 若看到 `❌ ${表单}.${字段}: 数据填充规则为空` 或 `⚠️ 未匹配：...` 日志，说明填充规则部分失败
   - 若看到 `[5/10] 建表后自检` 阶段输出 `❌ 自检发现 ... FORM-TEMP占位符残留`，必须立即处理（按日志指引修表+补字段清单），绝不允许当作成功交付
   - 必须主动告知用户哪些字段未配置成功、原因是什么、如何修复
   - **严禁静默忽略失败**——不能只报告"创建成功"而隐藏填充失败的事实

7. **【强制·v6.58.0修正】子表内关联字段填充机制说明** — 子表内关联字段的填充规则必须使用 `mainRules`（主表填充规则）：
   - **【关键区分】** 数据填充规则有两种，用途完全不同：
     - **mainRules（主表填充规则）**：关联表单的**主表字段** → 填充到当前表单任意位置（**含子表的每一行**）。这是最常用的场景，**设计器完全支持配置**
     - **tableRules（子表填充规则）**：关联表单的**子表字段** → 填充到当前表单的子表。**设计器不支持此配置**（会提示"关联表单在子表内时，不支持子表填充规则"）
   - **【正确做法】** 当关联字段位于子表内，且数据来源是关联表单的**主表字段**时（如：产品信息的主表字段→填充到盘点明细子表的每一行），必须使用 `mainRules`。form_creator 的 `buildDataFillingRules` 已修正为：所有关联带出字段（无论位于主表还是子表）统一使用 `mainRules`
   - **⚠️ 禁止错误使用 tableRules**：除非数据来源确实是关联表单的**子表字段**（极罕见场景），否则一律使用 `mainRules`
   - **✅ 设计器可正常配置**：使用 `mainRules` 后，子表内关联字段在设计器的「数据填充」面板中可以正常显示和编辑「主表填充规则」，与手动创建的效果一致

8. **【强制·v6.60.0新增】脚本执行后禁止过度验证** — `create_from_markdown.js` 或 `add_form_to_app.js` 执行完成后，AI 的后置验证步骤上限为 **5次工具调用**，仅允许以下3项验证：
   - **验证1**：Read 系统配置清单.md — 确认应用ID和表单UUID数量正确（1次Read）
   - **验证2**：Glob `**/*.json` — 确认JSON文件数量与表单数一致（1次Glob）
   - **验证3**：Glob `**/组件ID清单.md` — 确认组件ID清单数量一致（1次Glob）
   - **以下操作一律禁止**（除非用户明确要求或脚本日志报错）：
     - ❌ Grep/Read JSON文件中的 AssociationFormField、dataFillingRules、mainRules、behavior 等字段细节
     - ❌ Grep/Read 流水号公式（SERIALNUMBER 表达式）
     - ❌ Grep/Read 数据标题配置（dataTitle/titleField）
     - ❌ Read README.md
     - ❌ Glob 查找 temp-file 目录（与 form_creator 任务无关）
     - ❌ 重复 Glob 查找同一种临时文件（field_config.js 只查1次）
     - ❌ TodoWrite（简单验证任务不需要）
   - **关联填充规则验证策略**：只检查脚本执行日志输出，若日志中无"⚠️ 关联填充规则配置失败汇总"或"❌ 数据填充规则为空"字样，即视为成功，**不得深挖JSON文件验证**
   - **时间预算**：验证环节目标 ≤ 2分钟。若发现自己在做 JSON 字段级验证，立即停止——这是过度验证的信号

## ⚠️ 触发条件（必须严格判断）

### ❌ 禁止自动调用场景（非常重要！）

**当用户说以下话时，绝对不要自动调用此skill：**

| 用户说的话 | 正确的处理方式 | 错误的处理方式 |
|-----------|--------------|--------------|
| "创建一个项目" | 只创建项目目录结构和字段清单.md | ❌ 不要自动生成JSON和宜搭应用 |
| "新建一个项目叫XXX" | 只创建项目文件夹和基础文档 | ❌ 不要调用form_creator |
| "帮我搭建一个项目" | 询问用户是否需要生成表单 | ❌ 不要自动执行生成脚本 |
| "我要做进销存" | 先了解需求，再询问是否生成表单 | ❌ 不要直接生成所有表单 |
| "初始化XXX系统" | 只创建项目目录结构 | ❌ 不要调用form_creator |

### ✅ 允许调用场景（必须满足明确的触发词）

**场景1：创建新应用 + 所有表单（create_from_markdown.js）**

| 用户说的话 | 说明 |
|-----------|------|
| "根据这个字段清单生成表单" | 用户提供了字段清单文件，明确要求生成 |
| "帮我把这些字段生成宜搭表单" | 明确要求生成表单配置 |
| "生成JSON文件并创建到宜搭" | 明确要求执行创建 |
| "用流程图生成表单" | 提供了流程图，要求生成表单 |
| "创建应用" + 提到表单 | 创建新应用并生成表单 |

**场景2：向已有应用添加单个表单（add_form_to_app.js）**

| 用户说的话 | 说明 |
|-----------|------|
| **"在XX应用中创建一个表单"** / **"在XX应用中添加表单"** | 向已有应用添加单个表单 |
| **"给XX应用增加一个表单"** / **"在XX应用里新建表单"** | 向已有应用添加单个表单 |
| **"直接创建这个表单"（在已有应用目录下）** | 上下文感知：在已有应用中创建 |

### 🔑 关键区分原则

| 场景 | 触发关键词 | 上下文特征 | 调用的脚本 |
|------|-----------|-----------|-----------|
| **仅创建项目** | "创建项目"、"新建系统"、"搭建项目" | 无表单相关 | ❌ **不调用此skill** |
| **创建新应用+所有表单** | "生成表单"、"创建应用" | 提供完整字段清单（多表单） | `create_from_markdown.js` |
| **向已有应用添加单个表单** | "创建**这个**表单"、"直接创建"、"在XX应用中添加表单" | 已设计单个表单或在已有应用目录下 | `add_form_to_app.js` |

**记忆口诀：**
- **"这个"**表单 = 单个 = `add_form_to_app.js` 添加到当前应用
- **"应用"** / **"所有"**表单 = 多个 = `create_from_markdown.js` 创建新应用
- **"在XX应用中"** = 明确指定 = `add_form_to_app.js` 添加到指定应用

### 🔑 关键原则

1. **用户说"创建项目" ≠ 生成表单**：创建项目 = 创建目录 + 编写需求文档；生成表单 = 执行脚本 + 创建宜搭应用
2. **必须询问确认**：如果用户没有明确说"生成表单"，必须先询问，例如："您是要先创建项目结构，还是要直接生成宜搭表单？"
3. **分阶段执行**：第一阶段创建项目目录 + 字段清单；第二阶段（用户确认后）生成JSON + 创建宜搭应用
4. **区分创建新应用 vs 向已有应用添加表单**：前者用 `create_from_markdown.js`（新应用+所有表单），后者用 `add_form_to_app.js`（单个表单到指定应用）

### 单表模式 vs 项目模式

- **单表模式**：用户只提到一个表单（可含子表）→ 输出到 `02宜搭场景案例库/宜搭表单/`
- **项目模式**：用户提到"系统"/多个表单/提供Markdown字段表路径 → 输出到项目目录
- 详细判断条件与目录结构见 [references/workflow-details.md](references/workflow-details.md)

## 标准执行路径（v6.19.0简化流程）

### 场景1：创建新应用 + 所有表单

**唯一步骤：执行 `create_from_markdown.js`。禁止AI直接手动编写JSON文件，禁止用 Write 工具写JSON表单配置。**

```powershell
node .agents/skills/form_creator/scripts/create_from_markdown.js "<字段清单.md绝对路径>"
```

> ⚠️ **严禁传入应用名称参数**（第二个参数）！脚本自动用项目目录名作为应用名称（专属硬规则4）。

脚本自动完成：
```
字段清单.md
    ↓ 解析字段清单 → 创建宜搭应用 → 按依赖排序创建所有表单（普通+流程+子表）
    ↓ 更新关联字段配置 → 更新组织及应用信息
    ↓ 调用 config-sync 整体同步（当作已有应用处理）
    ↓
【完成】✅ 宜搭在线应用（可立即使用）
        ✅ 本地所有文件由 config-sync 统一生成（JSON、系统配置清单.md、组件ID清单.md）
```

**核心原则：先在宜搭创建，再同步回来。创建完成后就是"已有应用"，使用同步已有应用的逻辑。**

**v6.19.0起不再需要**：❌ 先运行 `generate_from_markdown.js` 生成本地JSON；❌ 提前创建本地文件；❌ 单独同步每个表单。（历史双模式流程见 [references/workflow-details.md](references/workflow-details.md)）

**执行前必做（专属硬规则5）**：人工核对字段清单中所有关联字段的 `关联-->目标表` 标记与填充规则语法；可选运行 `node scripts/ai-validator.js check-fill-rule-syntax <字段清单路径>`。

**执行后必做（专属硬规则6、8）**：检查脚本日志中的"⚠️ 关联填充规则配置失败汇总"与"[5/10] 建表后自检"FORM-TEMP残留告警；后置验证≤5次工具调用（Read系统配置清单.md + Glob JSON数量 + Glob组件ID清单数量）。

### 场景2：向已有应用添加单个表单

```powershell
node .agents/skills/form_creator/scripts/add_form_to_app.js --appId <应用ID> --form "<字段清单.md路径>" [--appName "<应用显示名称>"]
```

| 参数 | 必填 | 说明 |
|------|------|------|
| `--appId` | ✅ | 宜搭应用ID（如 APP_XXXXXXXX，从组织及应用信息.md读取真实值） |
| `--form` | ✅ | 字段清单Markdown文件路径 |
| `--appName` | ❌ | 应用显示名称（仅用于输出信息） |

与创建新应用的区别：

| 功能 | create_from_markdown.js | add_form_to_app.js |
|------|------------------------|--------------------|
| **目标** | 创建新应用 + 所有表单 | 向已有应用添加单个表单 |
| **应用ID** | 自动生成 | 必须提供已有应用ID |
| **表单数量** | 支持多个表单 | 只支持单个表单 |
| **关联表单** | 自动处理依赖关系 | 关联字段需手动配置（确保目标表单已存在） |

注意：需要有该应用的编辑权限；创建完成后平台可能需要几分钟同步数据。

### 字段清单格式

两个脚本使用相同的字段清单格式（表格格式推荐 / 列表格式兼容）。格式规范、字段类型判断规则、括号/中括号标注解析、完整示例见 [references/field-type-rules.md](references/field-type-rules.md)。

最小示例（表格格式）：

```markdown
### (一) 表单名称「普通表单」（或「流程表单」）

| 字段名称 | 字段类型 | 字段说明 | 字段状态 | 是否必填 |
|----------|----------|----------|----------|----------|
| 字段1    | 单行文本 | 说明     | 编辑     | 是       |
| 供应商   | 关联表单 | 关联-->供应商信息；填充：当前字段=源字段 | 编辑 | 是 |
```

## 核心安全约束（速查）

1. **源文件保护**：绝不修改/删除 `流程及字段梳理/` 及 `01需求梳理/` 源文件目录下的任何文件，绝不在其中生成文件
2. **输出目录**：优先使用用户指定目录；业务模块目录与 01需求梳理 同级，**禁止**自动创建 `03-表单配置` 等额外子目录（详见 [references/workflow-details.md](references/workflow-details.md)）
3. **项目名称**：从Markdown第一行标题提取（仅用于本地目录/文档），不使用文件名；宜搭应用名称一律用项目文件夹名（硬规则4）
4. **严格按字段清单生成**：只生成字段清单中明确列出的表单，绝对禁止生成清单之外的表单；生成的JSON数量必须与清单表单数一致
5. **临时文件自动删除（强制）**：生成成功后立即用 DeleteFile 自动删除 `field_config.js`、`generate_project.js` 等中间 `.js` 配置文件，绝不询问用户、绝不要求用户手动删除
6. **每个表单的流水号字段不超过1个**
