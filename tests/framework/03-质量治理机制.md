# 质量治理机制（宜搭版）

**版本：** 1.0
**定位：** 四元统计、宜搭版伪问题9类、伪问题熔断、归档门禁、Smoke门禁

---

## 一、四元统计口径

### 1.1 四元定义

| 结果 | 含义 | 宜搭使用场景 |
|------|------|---------|
| ✅ PASS | 通过 | 表单提交成功、公式计算正确、校验规则生效、关联数据正确、流程流转正常 |
| ❌ FAIL | 失败（发现真实 BUG） | 字段为空、公式错误、校验未触发、关联错配、流程卡死 |
| ⏭️ SKIP | 前置条件不满足，跳过 | 字段未创建、公式未配置、规则未启用、关联表单无数据 |
| ⏳ PENDING | 自动化证据不足，待人工判定 | UI 视觉效果、权限可见性需人工确认、流程审批需人工操作 |

### 1.2 统计规则

- 每个用例必须标注四元之一，禁止仅用二元 PASS/FAIL
- **SKIP 上限 20%**：SKIP 数量不得超过总用例数的 20%，超过即批次作废重提
- **负面用例执行**：至少 2 个负面用例已执行（非 SKIP）
- 统计格式：`PASS: X / FAIL: Y / SKIP: Z / PENDING: W（总 N 项）`
- **SKIP 率：** Z/N（上限 20%）

### 1.3 为什么需要四元而非二元

| 二元问题 | 四元解决 |
|---------|---------|
| SKIP 被算入 FAIL → 虚高失败率 | SKIP 独立统计 |
| 证据不足的被算入 PASS → 虚高通过率 | PENDING 独立统计 |
| 无法区分"不能测"和"测了没过" | 四元清晰区分 |

## 二、伪问题分类体系（宜搭版）

### 2.1 通用伪问题（伪-1 ~ 伪-5）

| 类别 | 名称 | 宜搭版判定标准 | 违反自检项 |
|------|------|--------------|-----------|
| 伪-1 | fabricated（凭空捏造） | 报告了字段清单/规则清单中根本不存在的字段/公式/规则/功能 | ② 源码确认、⑤ 现象可复现 |
| 伪-2 | 未读源码 | 报告"字段未创建/公式未配置/规则未启用"前未读字段清单/规则清单，实际已配置 | ② 源码确认 |
| 伪-3 | 未理解产品设计 | 以管理员测试普通成员权限；或不理解宜搭权限组/流程节点/数据联动设计 | ④ 产品设计理解 |
| 伪-4 | 时序问题 | 在宜搭表单提交/公式计算/流程流转/数据填充未完成时抓取，导致"未计算/未流转/未填充"误判 | ③ 异步等待、⑤ 现象可复现 |
| 伪-5 | 用例库问题 | 用例预期与字段清单/规则清单/Schema 不符，需反馈出题方修订用例 | ① API 实证（间接） |

### 2.2 范式类伪问题（伪-6 ~ 伪-9）

> **这四类的根因是测试方按"传统思维"测试宜搭应用有意不做的能力。**

| 类别 | 名称 | 宜搭版判定标准 | 典型表现 | 违反自检项 |
|------|------|--------------|---------|-----------|
| 伪-6 | 范式越界 | 测试宜搭应用有意不做的能力 | 测试宜搭平台自身bug；要求AI工具有手动编辑器；测试未配置的功能 | 范式三问①② |
| 伪-7 | 角色错位 | 把应由宜搭平台/用户完成的工作当成AI工具应该做的来测试 | 要求AI工具替代宜搭设计器；要求data-tester替代用户审批流程 | 范式三问③ |
| 伪-8 | 重量级预期 | 要求简单宜搭表单提供复杂企业级功能 | 要求简单CRUD表单有复杂权限矩阵引擎；要求普通表单有BI分析能力 | 范式三问① |
| 伪-9 | 平衡失调 | 混淆"宜搭设计器手动配置"和"AI自动生成" | 要求AI生成的公式有手动编辑器；要求宜搭设计器自动生成代码 | 范式三问①③ |

### 2.3 伪问题处理规则

```
ISS 提交 → 修复方核验
    ↓
伪问题预筛
    ├─ 真问题 → 进入修复流程
    │   ├─ 工具链层问题 → 修改 skill 脚本（分配 FW 编号）
    │   ├─ 应用配置问题 → 生成修复产物 + 粘贴指引（规则25）
    │   └─ 数据问题 → data-tester 重新提交或清理
    └─ 伪问题 → 按 9 类分类 + 标注违反自检项 → 退回核验方
```

## 三、伪问题率熔断机制

### 3.1 熔断阈值

| 伪问题率 | 必须执行的动作 |
|---------|--------------|
| ≤ 30% | 正常归档，伪问题退回核验方复核即可 |
| > 50% | 沟通记录标注"⚠️ 测试方方法论待复盘"，要求下一批次前提交方法论复盘报告 |
| > 80% | 建议用户暂停测试方资格 1 轮，重新学习自检后再恢复；本批次伪问题全部退回，不计入统计 |

### 3.2 熔断后的复盘要求

复盘报告必须包含：
- 每个伪问题的类别编号
- 违反的自检项编号
- 简要证据
- 根因分析（为什么会制造伪问题）
- 正确做法
- 方法论改进承诺（下一批次将如何避免）
- 新教训追加到反模式库

## 四、ISS 提交前自检（宜搭版）

### 4.1 五项自检（硬性约束）

每个 ISS 提交前，测试方必须逐项回答以下 5 个问题，任一项不通过则**不得提交该 ISS**：

| 自检项 | 宜搭版要求 | 违反后果 |
|--------|----------|---------|
| ① API 实证 | 报告宜搭 API 错误码前，必须**实际调用该 API**（通过 data-tester）并记录完整响应。禁止凭推断报告错误码 | ISS 退回，不计入统计 |
| ② 源码确认 | 报告"字段未创建/公式未配置/功能未实现"前，必须**读字段清单/Schema/规则清单确认**。禁止凭 UI 表面现象判定"未实现" | ISS 退回，不计入统计 |
| ③ 异步等待 | 报告"公式未计算/流程未流转/数据未填充"前，必须**等待异步操作完成**（宜搭表单提交、公式计算、流程流转均为异步，需等待 networkidle + 至少 2 秒）。禁止在 loading 态抓取 | ISS 退回，不计入统计 |
| ④ 产品设计理解 | 测试权限/流程节点/数据联动前，必须**读字段清单和规则清单理解产品设计**。禁止以管理员测试普通成员权限；禁止不理解权限组就测试权限拦截 | ISS 退回，不计入统计 |
| ⑤ 现象可复现 | 报告的异常现象必须能通过**明确步骤复现**。禁止报告无法复现或依赖缓存/时序的问题 | ISS 退回，不计入统计 |

### 4.2 范式三问（与五项自检并列）

| 范式三问 | 宜搭版要求 | 违反后果 |
|---------|----------|---------|
| ① 该"缺失功能"是否在宜搭应用能力分层清单的"应有"范围内？ | 必须查询应用能力分层清单，明确标注所属类别 | ISS 退回，视为伪-6 范式越界 |
| ② 若在"有意不做"范围内，是否有用户明确要求新增？ | 不能凭"应该有"推断；必须有用户明确书面要求 | ISS 退回，视为伪-6 范式越界 |
| ③ 测试预期是否按宜搭应用范式编写？ | 不能按与宜搭范式冲突的思维编写预期（如要求AI工具有手动编辑器） | ISS 退回，视为伪-7 角色错位 |

### 4.3 三层验证关系

```
三问验证法（轻量预筛）→ 5 项自检（证据链验证）→ 范式三问（范式合规验证）
                                                        ↓
                                              全 ✓ 才正式提交 ISS
```

## 五、用户归档门禁

### 5.1 九项审核清单（宜搭版）

批次完成后，用户在归档前必须审核以下 9 项，全部通过才能点头归档：

| 审核项 | 通过标准 |
|--------|---------|
| 1. 四元统计完整性 | PASS/FAIL/SKIP/PENDING 四元齐全 |
| 2. SKIP 上限 | SKIP ≤ 总用例数的 20% |
| 3. 负面用例执行 | 至少 2 个负面用例已执行（非 SKIP） |
| 4. 证据链完整性 | 每个 FAIL/PENDING 都有诊断信息（API响应/DOM状态/截图） |
| 5. 修复回归零回退 | 所有 ISS 已验证，无新增问题 |
| 6. 工具链健康检查通过 | `npm test` 执行通过（Jest 单元测试） |
| 7. Smoke 回归通过 | 核心 Smoke 集已执行并通过 |
| 8. 数据清理 | 测试数据已清理（data-tester/data-clean）或保留原因已说明 |
| 9. 状态更新 | 当前最新状态章节已更新 |

### 5.2 归档操作

用户点头后，修复方执行归档：
1. 将 `[进行中]` 前缀的文件重命名为 `[已完成]` 前缀
2. 移动到 `[已完成]测试归档/` 目录
3. 更新能力覆盖矩阵和测试历史

**如用户任一项不通过，不得归档，必须回到核验或修复步骤补全。**

## 六、Smoke 回归门禁

### 6.1 Smoke 集定位

- 每次**工具链 skill 修改后**快速确认核心链路没被破坏
- 每次**发给测试方重测前**优先执行
- 每次**归档前**作为最终快速验证

### 6.2 Smoke 集构成（宜搭版）

Smoke 集包含两部分：

| Smoke 类型 | 内容 | 执行方式 |
|-----------|------|---------|
| 工具链 Smoke | 运行 `npm test`（现有 Jest 单元测试） | `npm test` |
| 应用 Smoke | 应用核心 P0 场景（表单提交/公式计算/关联数据/流程启动） | data-tester / js-action-tester |

### 6.3 Smoke 集规模与选取

- 规模：30~40 项，不无限膨胀
- 选取原则：P0 优先、用户路径优先、核心能力优先、回归价值高、可稳定执行
- **负面 Smoke 占比 ≥ 15%**

### 6.4 Smoke 门禁规则

| Smoke 类型 | 归档门禁 |
|-----------|---------|
| 工具链 Smoke（npm test） | 必须 100% PASS |
| 应用核心 Smoke | 必须 100% PASS |
| 负面 Smoke | 必须 100% PASS |
| 专项 Smoke | 按修改模块执行，必须 PASS |
| SKIP 率 | ≤ 20% |
| 任何 FAIL | 不得归档 |

## 七、教训累积机制

### 7.1 累积原则

- 每次出现误判、伪问题、过度修复、资源浪费的情况，必须追加新教训
- **教训不可删除，只能累积**
- 每条教训记录：错误行为、正确做法、违反的自检项

### 7.2 触发条件

- **强制触发**：本批次伪问题率 > 30%，或触发熔断后
- **可选触发**：伪问题率 ≤ 30%，但出现 ≥ 2 个相同类别的伪问题
- **用户指定**：用户认为有必要复盘时

### 7.3 复盘产出

- 新教训追加到 `07-反模式与教训库.md`
- 若触发熔断，复盘报告必须包含"方法论改进承诺"
- 每个伪问题归入 9 类分类体系，标注违反自检项
