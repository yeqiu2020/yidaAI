# 宜搭应用测试与反馈迭代框架

**版本：** 1.0
**定位：** 适配宜搭低代码开发的 AI 测试方法论框架，让 AI 系统性测试"由 AI 工具链构建出的宜搭应用"
**来源：** 从 `docs/test-framework-kit/`（MindFlow 测试方法论 v1.0）适配而来，针对宜搭开发测试逻辑重构
**适用范围：** 用户通过本工具链（form_creator / formula-generator / code-expert / business-rule 等 skill）构建出的宜搭应用

---

## 这是什么

这是一套**为宜搭低代码开发量身定制的 AI 测试与反馈迭代框架**，核心解决一个问题：

> **用户通过 AI 工具构建出宜搭应用后，如何让 AI 系统性地测试应用、发现问题、修复缺陷、迭代优化，从而免去用户手动测试和修复的工作？**

本框架与原方法论（`docs/test-framework-kit/`）的关系：

| 维度 | 原方法论（test-framework-kit） | 本框架（tests/framework/） |
|------|------------------------------|--------------------------|
| 测试对象 | 通用软件项目（框架代码） | AI 构建的宜搭应用 + 工具链 skill 脚本 |
| 公共代码层 | framework/src/ | AI 工具链 skill（form_creator / data-tester 等） |
| 项目配置层 | schema/配置 | 宜搭应用字段/公式/规则/流程（受规则25约束） |
| 测试方工具 | 通用 AI + 浏览器 | data-tester / js-action-tester / playwright-cli |
| 修复方式 | 直接改代码 | 工具链层直接改脚本；应用层生成修复产物 + 用户粘贴指引 |
| 范式 | AI-first | 低代码平台 + AI 生成 |

## 与现有 tests 的关系

本框架位于 `tests/framework/`，与现有 tests 目录的关系如下：

```
tests/
├── core/           ← 现有：工具链核心模块单元测试（Jest，保留不动）
├── features/       ← 现有：工具链特性单元测试（Jest，保留不动）
└── framework/      ← 本框架：宜搭应用测试与反馈迭代方法论
    ├── README.md                ← 本文件
    ├── 01-方法论核心.md
    ├── 02-角色与工具协作.md
    ├── 03-质量治理机制.md
    ├── 04-测试场景设计原则.md
    ├── 05-应用适配流程.md
    ├── 06-分层修复原则.md
    ├── 07-反模式与教训库.md
    ├── 08-提示词模板/
    ├── 09-文档模板/
    └── 10-工具链映射/
```

**结合方式：**

1. **分层互补**：现有 `tests/core` + `tests/features` 是"工具链层"的 Jest 单元测试；本框架是"应用层"的测试方法论。两者覆盖不同层级，互不冲突。
2. **Smoke 门禁整合**：本框架的 Smoke 回归集包含"运行 `npm test`"作为工具链健康检查项，确保工具链自身代码质量。
3. **能力覆盖矩阵**：矩阵同时追踪"工具链能力"（由现有 Jest 测试覆盖）和"应用能力"（由本框架覆盖）。

## 核心机制速览

### 多工具协作链路（适配宜搭的五方分离）

```
[1. 发起方/协调方 主AI session] → 协调全流程，读取应用配置
    ↓
[2. 出题方 独立session] → 从用例库提取用例（含负面用例）
    ↓
[3. 测试方 多工具]
    ├─ data-tester (API模式)    → 表单数据提交、公式计算、校验规则、关联数据
    ├─ js-action-tester (UI模式) → 表单JS动作、字段联动、条件显示
    └─ playwright-cli (E2E)      → 完整用户路径、流程审批、权限可见性
    ↓
[4. 修复方 多工具]
    ├─ 工具链层修复：直接修改 skill 脚本（分配 FW 编号，所有应用受益）
    └─ 应用层修复：生成修复产物（公式/代码/配置）→ 输出粘贴指引 → 用户手动粘贴（规则25）
    ↓
[5. 核验方 测试工具回查]
    ├─ data-tester 回查验证 → 字段是否写入、关联是否正确
    └─ js-action-tester 回归 → JS动作是否生效
    ↓
[6. 用户归档] → 审核9项门禁后点头
    ↓
[批次完成]
```

### 11 项硬约束（适配宜搭版）

1. **四元统计口径**（PASS/FAIL/SKIP/PENDING）
2. **Session 隔离**（出题/测试/修复/核验/归档分离，文件传递）
3. **用户归档门禁**（用户最终点头，AI 不代为归档）
4. **负面用例强制**（每批次至少 2 个，带可量化断言）
5. **SKIP 上限 20%**（超过即批次作废）
6. **测试方扩展权**（可追加 1-2 步扩展验证）
7. **跨厂商模型制衡**（测试方与修复方不同 AI 厂商）
8. **角色 KPI 互斥**（出题不考核通过率，测试不考核速度）
9. **问题修复强制**（所有真问题必须修复，应用层修复受规则25约束时输出粘贴指引）
10. **伪问题率熔断**（>50% 复盘，>80% 暂停资格）
11. **ISS 自检强制**（5 项自检 + 范式三问）

### 宜搭特有约束（新增）

- **规则25约束**：禁止通过 API 修改已有应用的表单字段内容，应用层修复只能"本地生成 → 用户手动粘贴"
- **真实数据原则**：测试数据必须真实可信（data-tester 规范），禁止"测试数据/test"等假数据
- **关联字段6步闭环**：关联表单字段必须走识别→查询→映射→选取→自查→回查的6步流程
- **工具链与应用分层**：问题必须区分是工具链skill缺陷还是应用配置问题

## AI 使用入口（核心）

> **当用户说"测试应用"、"测试宜搭应用"、"测试我构建的应用"时，AI 按以下步骤执行：**

### Step 0：理解方法论（必读）

完整阅读以下文档：

1. `01-方法论核心.md` — 测试目的、原则、11 项硬约束（宜搭版）
2. `02-角色与工具协作.md` — 多工具协作链路、skill 与角色映射
3. `03-质量治理机制.md` — 四元统计、伪问题9类（宜搭版）、熔断、归档门禁
4. `04-测试场景设计原则.md` — 宜搭测试用例设计原则
5. `05-应用适配流程.md` — **核心：如何分析宜搭应用并构建测试用例库**
6. `06-分层修复原则.md` — 工具链层 vs 应用层、规则25约束下的修复方式
7. `07-反模式与教训库.md` — 宜搭特有反模式与伪问题

### Step 1：分析待测应用

1. 读取应用的项目目录（如 `进销存/`）
2. 读取 `系统配置清单.md`（应用ID、表单UUID、组件ID）
3. 读取 `字段清单.md`（表单与字段结构）
4. 读取 `规则清单.md`（公式、业务规则、字段联动）
5. 读取 `组织及应用信息.md`（应用列表、原型地址）

### Step 2：执行应用适配流程

按 `05-应用适配流程.md` 中的流程逐步执行：

```
应用分析 → 能力域识别 → 范式定义 → 测试边界划定
→ 用例库生成 → Smoke集选取 → 能力矩阵 → 提示词适配 → 文档初始化
```

### Step 3：输出适配报告

适配完成后，输出包含以下内容的报告，供用户审核：

- 应用架构摘要（表单清单 / 流程清单 / 报表清单 / 自定义页面清单）
- 能力域清单
- 范式定义与能力分层清单
- 测试边界决策树
- 生成的用例库文件清单（含用例数和负面用例数）
- Smoke 回归集
- 能力覆盖矩阵
- 工具链映射（哪些测试用哪个 skill 执行）

### Step 4：用户审核后开始测试

用户确认适配结果后，按以下流程执行测试：

```
1. 发送 08-提示词模板/1-提取用例.md 给出题方（独立 session）
2. 发送 08-提示词模板/2-执行测试.md 给测试方（独立 session，跨厂商模型）
   - 测试方根据用例类型调用对应 skill：
     · 数据/公式/校验/关联 → data-tester
     · JS动作/字段联动/条件显示 → js-action-tester
     · 完整用户路径/流程/权限 → playwright-cli
3. 发送 08-提示词模板/3-核验修复.md 给修复方（当前 session）
4. 发送 08-提示词模板/4-回归验证.md 给核验方（同测试 session）
5. 发送 08-提示词模板/5-归档门禁.md 给修复方（协助用户检查）
```

## 共享用例模式库（11-目录）使用指南

> **核心理念：** 测试用例**每个应用单独生成**，但不是从零开始——从 `11-共享用例模式库/` 选取模式 → 填充占位符 → 输出到 `{应用目录}/测试文档/测试用例库/`

### 模式库概览

| 模式文件 | 模式数 | 能力域 | 模式 ID 范围 |
|---------|--------|--------|-------------|
| 01-数据提交模式.md | 3 | 数据提交 | P01-P03 |
| 02-公式与联动模式.md | 7 | 公式与联动 | P04-P10 |
| 03-流程与规则模式.md | 5 | 流程审批/业务规则/校验与规则 | P11-P15 |
| 04-关联与子表模式.md | 5 | 关联与填充/子表单 | P16-P20 |
| 05-UI与负面模式.md | 10 | UI交互/校验/流程/权限 | P21-P23, P24-N~P30-N |
| 06-工具链与专项模式.md | 5 | 工具链 | P31-P35 |

**统计：** 正向 23 + 负面 7 + 工具链 5 = 35 个模式，负面占比 20%

### 实例化示例

```bash
# 1. AI 读取目标应用的字段清单 + 规则清单 + 系统配置清单
# 2. 选取适用的模式（如进销存应用需要 P01,P04,P07,P13,P16,P18,P24-N...）
# 3. 替换占位符 → 输出到 {应用目录}/测试文档/测试用例库/
#    P01 → YD-FORM-01（普通表单数据提交成功）
#    P04 → YD-FORMULA-01（"采购订单.合计金额"公式计算正确）
#    P16 → YD-REL-01（"库存信息.选择仓库"关联6步闭环）
```
